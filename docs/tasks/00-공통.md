## 5. 장애 주입 설정 (`Report.chaos`, API의 `ChaosConfig`)

```json
{"enabled": true, "probability": 0.5, "errorTypes": ["timeout", "server_error", "bad_output"],
 "workers": null, "scope": "primary", "seed": 123456}
```

- 요청(`POST /api/reports`)에서는 `enabled`만 필수. 기본값: `probability` 0.5, `errorTypes` 셋 다, `workers` null(전부), `scope` `"primary"`, `seed`는 서버가 정해 저장한다.
- `scope`: `"primary"`는 **주 모델 호출만** 실패시킨다 (→ 대체 모델로 복구되는 것을 보인다). `"all"`은 대체 모델까지 실패시킨다 (→ 필수·선택 정책을 시험한다).
- 주입은 `healing.py`의 호출 함수 안, 실제 호출 직전에서만 한다. 판정은 **재현 가능**해야 한다: `random.Random(f"{seed}:{worker_id}:{model}:{attempt}").random() < probability`.
- 주입된 실패는 Trace `details.injected = true`. 주입은 리포트 워크플로우에만 적용되고 모의 주문·계좌와 무관하다. 대체 모델 호출 비용은 한도에 포함된다.

## 6. Worker 인터페이스 (2가 만들고, 3·4가 부른다) — `backend/reports/agents/base.py`

```python
class WorkerError(Exception):
    """LLM이 아닌 이유로 실패 (필수 자료 없음 등). 메시지는 사용자에게 보여도 되는 말로."""

@dataclass
class WorkerContext:
    report_id: int
    task_id: str                     # "report-<id>"
    symbol: str
    name: str
    market: str                      # "KR" | "US"
    worker_id: str
    attempt: int                     # 이 Worker를 몇 번째 실행하는지 (검토 RETRY로 다시 쓰면 2)
    inputs: dict[str, dict]          # Join Guard가 골라 준 앞 단계 결과 {worker_id: 결과}. 조사 Worker는 {}
    instructions: str | None         # 검토의 수정 지시 (RETRY 재작성일 때만)
    handoff: dict | None             # Handoff로 불렸을 때의 전달 데이터 (8절)
    llm: "LlmCaller"                 # 4가 만든 호출기. ctx.llm(system, user, contract="MarketResult") → LlmReply
    deadline: float                  # time.monotonic() 기준. 넘기면 멈춘다
    cfg: Config                      # engine_config()
    client: BrokerClient | None      # broker_client() (조회 불가면 None)

class Worker(Protocol):
    id: str
    output_contract: str             # "MarketResult" 등
    def run(self, ctx: WorkerContext) -> dict: ...
```

규칙:
- `run`은 **출력 계약 형식의 dict**를 돌려준다. State(`state.*`)를 직접 바꾸지 않고 Trace도 남기지 않는다 (Orchestrator와 호출기가 남긴다).
- **LLM 호출은 `ctx.llm` 한 번**이 원칙이다 (자료 모으기 → 프롬프트 → 호출 한 번). 두 번 이상 부르면 안 되는 건 아니지만 Trace가 길어진다.
- 자료 조회 실패: 선택 자료(뉴스·증권사 리포트·공시 일부)는 빼고 프롬프트에 "자료 없음"을 적는다. 필수 자료(시세·일봉)가 없으면 `WorkerError`.
- `ctx.deadline`을 지나면 조회를 멈추고 가진 것으로 간다. 외부 조회는 `timeout`을 짧게(10초 안).
- 프롬프트에 API 키·비밀번호·사용자 아이디를 넣지 않는다. 뉴스·공시 본문은 Guard(3의 `guards.py`의 `clean_text`)를 거친 것만 넣는다.
- `agents/__init__.py`에 `WORKERS: dict[str, Worker]` (id → 인스턴스). Orchestrator는 이것만 본다.

## 7. LLM 호출기 (4가 만들고, 3이 Worker마다 만들어 `ctx.llm`에 넣고, 2가 부른다) — `backend/reports/healing.py`

```python
class ErrorType(str, Enum): TIMEOUT = "timeout"; SERVER_ERROR = "server_error"; BAD_OUTPUT = "bad_output"; UNKNOWN = "unknown"

@dataclass
class LlmReply:
    data: dict            # 응답 JSON (contract를 줬으면 검증·정리를 통과한 것)
    provider: str
    model: str            # 실제로 답한 모델
    attempts: int         # 이 호출에 쓴 시도 수 (1이면 한 번에 성공)
    recovered: bool       # attempts > 1
    latency_ms: int       # 첫 시도 시작부터 성공까지
    recovery_ms: int | None   # 첫 실패부터 성공까지 (실패가 없었으면 None). agent_completed.details.recoveryMs가 된다
    cost_usd: float

class LlmGaveUp(Exception):
    error_type: ErrorType; attempts: int; last_model: str; message: str   # 모든 모델이 실패

class LlmCaller:
    """리포트 하나의 Worker 하나에 묶인 호출기. Orchestrator가 만들어 ctx.llm에 넣는다."""
    calls: list[LlmReply]          # 성공한 호출 기록 (Orchestrator가 agent_completed의 attempts·model을 여기서 읽는다)
    cost_usd: float
    def __call__(self, system: str, user: str, *, contract: str | None = None,
                 timeout: float | None = None) -> LlmReply: ...

def make_caller(report: Report, worker: dict, chaos: dict | None, client: LlmClient, deadline: float) -> LlmCaller
```

호출 순서 (한 번의 `ctx.llm(...)`): `[model] + fallbacks` 순서로, 모델마다 최대 `MAX_ATTEMPTS_PER_MODEL = 2`번, 전체 `MAX_ATTEMPTS = 4`번, `deadline` 안에서.
- 실패 분류: `LlmTimeout` → `timeout` (같은 모델로 다시 하지 않고 다음 모델로), HTTP 429·5xx·연결 실패 → `server_error` (`RETRY_BACKOFF_SEC = 2` 쉬고 같은 모델 재시도),
  JSON 아님·빈 응답·출력 계약 위반 → `bad_output` (오류 내용을 user 끝에 붙여 같은 모델 재요청), 그 밖 → `unknown`.
- **Circuit Breaker**: 모델별로 연속 실패 `BREAKER_FAILURES = 3`회면 `BREAKER_OPEN_SEC = 300`초 동안 그 모델을 건너뛴다 (`agent_failover`의 `reason: "circuit_open"`). 엔진 프로세스 안의 메모리에 둔다. 주입된 실패도 셈한다 (시연에서 "연속 실패 → 차단"을 보일 수 있다).
- 출력 계약 검증은 `contracts.validate(name, data)`(2)를 부른다. 통과한 dict를 `LlmReply.data`로 준다.
- 성공·실패마다 Trace를 남긴다 (9절). 호출기는 `state.record`만 쓴다 (`add_result`·`add_error`는 Orchestrator).
- 실제 호출은 `engine/paper_engine/llm.py`에 4가 더하는 **`LlmClient.complete_json_once(model, system, user, timeout) -> tuple[dict, float]`**(응답, 이번 호출 비용. 안에서 재시도하지 않는다)를 쓴다.

## 8. Orchestrator가 지키는 것 (3) — `orchestrator.py`, `guards.py`, `runner.py`

- 진입점 `orchestrator.run_report(report, *, workers=None, llm_client=None, now=None) -> Report`. `state.start`로 시작해 `state.finish`로 끝낸다. 예외를 밖으로 내지 않는다 (실패도 `finish(failed)`).
- 단계 실행: `plan.steps` 순서대로 `set_step` → `mode: parallel`이면 `ThreadPoolExecutor`로 Worker들을 같이, `sequential`이면 차례로. 단계 `timeoutSec`가 Worker의 `deadline`이다.
- Worker 하나의 실행 = `agent_started` → `WORKERS[id].run(ctx)` → 결과를 `contracts.validate`로 다시 확인 → `add_result` + `agent_completed`. 실패(`LlmGaveUp`·`WorkerError`·시간 초과·예외) → `add_error` + `agent_failed(final: true)`.
- **Join Guard** (`guards.join(report, step, plan) -> JoinDecision(ok, inputs, reason)`): `join: true`인 단계 앞에서. 필수 Worker 결과가 모두 있고 계약을 통과했는지 확인 → 실패 결과 제외 → 다음 Worker에 줄 **최소 Context**(`inputs`)를 고른다. 막으면 `join_blocked` + 뒤 단계 Worker 전부 `agent_skipped` + `workflow_failed` + `finish(failed)`.
- **부분 실패 정책** (`failurePolicy`): `required_optional`(기본) = 필수 실패면 그 단계에서 멈춤, 선택 실패는 빼고 계속. `fail_fast` = 아무 실패에도 멈춤. `best_effort` = 끝까지 가고 결과 있는 것으로 작성.
- **검토 반복**: `review_agent` 결과 `verdict`가 `RETRY`면 `review_retry` 사건을 남기고 `retry.target`(report_agent)을 `instructions`를 넣어 다시 실행(attempt+1), 다시 검토. `maxRounds`를 넘으면 `FAIL`로 본다. `FAIL`이면 `finish(failed)`, `PASS`면 계속.
- **Handoff**: `review_agent` 결과의 `handoff`가 있고 `plan.handoffs`에 그 경로가 있으면 `guards.handoff(...)`로 확인(허용 경로, `hop_count < maxHops`, 전달 데이터에 비밀 값 없음) → `handoff_started` → `risk_agent` 실행 → `handoff_completed`. 거절이면 `handoff_blocked` + 계속(리스크 점검 없이 완료).
  전달 데이터(`ctx.handoff`): `{"task_id", "trace_id", "from_agent", "to_agent", "objective", "inputs": {"memory_refs": [결과 키]}, "constraints": [...], "expected_output": "RiskResult", "attempt", "user_id", "hop_count"}` (`TEAM_DEV_PLAN.md` 4-3).
- **입력 Guard** (`guards.clean_text(text) -> tuple[str, list[str]]`, 3이 만든다): 뉴스·공시 본문에서 지시문("이전 지시를 무시", "시스템 프롬프트", "API 키를 출력" 등)과 비밀 값 모양(`sk-…`, 긴 토큰)을 지우고 (정리된 본문, 지운 사유 목록)을 돌려준다.
  Worker(2)는 외부 자료를 프롬프트에 넣기 전에 이 함수를 거치고, 지운 사유가 있으면 `run` 결과에 **`_guarded: [사유, ...]`** 키로 붙인다.
  Orchestrator는 결과에서 `_`로 시작하는 키를 **계약 검증 전에 꺼내** `agent_completed`의 `details.guarded`로 남긴다 (DR-SEC-01의 "차단 기록"이 이것이다).
- 리포트 본문 = `report_agent` 결과의 `markdown` (+ `risk_agent`가 있으면 그 경고를 맨 위에). `workflow_completed` → `finish(completed, content)`.
- **실행기** `runner.tick()`: `requested` 리포트를 하나 잡아(`select_for_update(skip_locked=True)`, 오래된 것부터) 백그라운드 스레드에서 `run_report`. **동시에 하나만** (`MAX_CONCURRENT = 1`, 비용 상한). `runner.recover()`: 엔진이 뜰 때 `running`으로 남은 리포트는 주인이 없다 (엔진 루프는 하나만 돈다). 아직 `running`이라 Trace를 남길 수 있으니 `record("orchestrator", "workflow_failed", "failed", details={"reason": "engine_restarted"})` 뒤 `finish(failed)`. (`add_error`는 Worker id만 받으므로 쓰지 않는다. 화면은 마지막 `workflow_failed.details.reason`으로 사유를 보여 준다.) `runner.shutdown()`: 도는 스레드가 끝나길 최대 10초 기다린다.
- 스레드에서 DB를 쓰면 끝날 때 `connections.close_all()`.
- 끝난 뒤 `runner`가 `auto.after_finish(report)`(1)를 부른다 (`source == "auto"`일 때 PDF·Discord. 2026-10-04 합의 B7: `source == "user"`이고 `completed`면 신청자에게 리포트 완성 알림 — `docs/API.md` "리포트 끝 알림"). 1이 만들기 전에는 없는 함수라 `getattr`로 있으면 부른다.
- 실패로 끝나면(`workflow_failed`·`recover()`) 4의 `healing.notify_failure(report, reason)`를 한 번 부른다 (B7: 실패 알림은 이 한 곳, kind `report_failed`). 부르는 자리는 runner — `run_report`가 failed로 끝난 뒤와 `recover()`.

## 9. Trace 사건 (누가 어떤 사건을 남기나. 화면·지표·PDF가 이 표로 읽는다)

`state.record(report, actor, action, status, provider, model, latency_ms, details)`. status는 `started`·`completed`·`failed`·`blocked`·`skipped`만.

| action | actor | status | 남기는 쪽 | details |
|---|---|---|---|---|
| `workflow_started` | orchestrator | started | 3 | `{"chaos": bool, "source"}` |
| `agent_started` | Worker id | started | 3 | `{"attempt": n, "step": step id}` |
| `agent_failed` | Worker id | failed | **4**(호출 실패마다) | `{"errorType", "attempt": 전체 시도 번호, "injected": bool, "final": false}` + provider·model·latency_ms |
| `agent_retry` | Worker id | started | 4 | `{"attempt": 다음 번호, "reason"}` (같은 모델로 다시) |
| `agent_failover` | Worker id | started | 4 | `{"from": 모델, "to": 모델, "reason": errorType 또는 "circuit_open"}` |
| `agent_completed` | Worker id | completed | 3 | `{"attempts", "recovered", "recoveryMs", "costUsd", "guarded": [...]}` + 실제 답한 provider·model·latency_ms. review_agent는 `"verdict"`, `"score"`도 |
| `agent_failed` | Worker id | failed | 3 (포기) | `{"errorType", "attempts", "final": true, "message"}` |
| `agent_skipped` | Worker id | skipped | 3 | `{"reason": "join_blocked" \| "fail_fast" \| "review_failed"}` |
| `join_completed` / `join_blocked` | join_guard | completed / blocked | 3 | `{"step": Join하는 step id, "required": [...], "missing": [...], "inputs": [결과 키]}` |
| `review_retry` | orchestrator | started | 3 | `{"round": n, "target": Worker id, "issues": [...], "instructions"}` |
| `handoff_started` / `handoff_completed` / `handoff_blocked` | handoff_guard | started / completed / blocked | 3 | `{"from", "to", "hopCount", "reason"}` (`to`는 꼭) |
| `workflow_completed` / `workflow_failed` | orchestrator | completed / failed | 3 | `{"reason", "costUsd", "durationMs"}`. `workflow_failed`의 `reason`은 아래 실패 사유 코드만 |

**리포트 실패 사유 코드** (`workflow_failed.details.reason`. 2026-10-04 합의, 컨셉 계획 4-4·9장 — 미구현, 담당 3):
3은 **이 목록에서만** 낸다. 화면(5의 `lib` 문장 표)·실패 알림 본문(4의 `notify_failure`)·자동 리포트 실패 글(1의 T1-5)이 이 코드로 사용자 문장을 고른다.
새 경우가 생기면 `exception`으로 뭉개지 말고 이 표에 코드를 더하는 PR을 먼저 올리고 5에게 알린다 (화면 문장 표와 같이).

| 코드 | 언제 | 남기는 곳 | 쉬운 문장 (컨셉 계획 4-4, 5가 다듬는다) |
|---|---|---|---|
| `join_blocked` | Join Guard가 막음 (필수 Worker 실패·계약 위반) | `orchestrator` (T3-5) | 자료를 모으는 AI가 응답하지 않아 리포트를 쓸 수 없었어요 |
| `review_failed` | 검토 `FAIL`, 또는 `RETRY`가 `maxRounds`를 넘음 | `orchestrator` (T3-6) | 검토 AI가 근거와 맞지 않는 주장을 찾아 완성하지 않았어요 |
| `timeout` | 단계 시간(`timeoutSec`)을 넘겨 멈춤. 필수 Worker의 시간 초과를 `join_blocked`·`timeout` 중 어느 쪽으로 낼지는 3이 T3-5에서 정해 이 칸에 적는다 | `orchestrator` (T3-5) | 시간이 너무 오래 걸려 멈췄어요 |
| `engine_restarted` | 엔진이 다시 떠 `running`으로 남은 리포트를 정리 | `runner.recover()` (T3-4) | 서버가 다시 시작돼 중단됐어요 |
| `exception` | 그 밖의 예상하지 못한 예외 (`run_report`가 잡음) | `orchestrator` (T3-3) | 예상하지 못한 오류로 멈췄어요 |

`agent_skipped.details.reason`(`join_blocked`·`fail_fast`·`review_failed`)은 건너뛴 Worker의 사유라 이 목록과 따로다.

**장애·복구의 셈법** (4의 `stats.py`와 5의 화면이 같은 규칙):
- Worker의 **실행(run)** = 그 actor의 `agent_started`부터 다음 `agent_completed` 또는 `agent_failed(final: true)`까지.
- **장애 1건** = 한 run 안의 **첫** `agent_failed(final: false)`. 같은 run의 뒤 실패는 같은 건의 시도다.
- **복구됨** = 그 run이 `agent_completed`로 끝남. **복구 시간** = `agent_completed.at − 첫 agent_failed.at`.
- **자동 복구율** = 복구된 건 ÷ 장애 건 × 100. **평균 복구시간** = 복구된 건의 복구 시간 평균.
  이 셈법의 이름은 **호출 장애 자동 복구율**(관리자 화면 `/ops`의 복구 지표)이다. 평가 가이드 정의의 **시나리오 자동 복구율**(장애 시험 DR 결과표)과 섞지 않고 보고서·발표에 이름으로 나눠 적는다 (2026-10-04 합의, 컨셉 계획 12장).
- `injected`는 장애 건의 첫 실패가 주입이면 true.

## 10. 출력 계약 (2가 `contracts.py`에 만든다. 모두 JSON 객체. 모르는 키는 지우고, 빠진 필수 키·틀린 형·범위는 `ContractError`)
