## 4. 실행 계획 스키마에 더하는 것 (3이 10/5 오전에)

`worker_definitions.yaml`의 Worker에 `fallbacks: [모델, ...]`(없으면 `[]`. 2026-10-07: 호출기는 이 값을 쓰지 않고 `healing.FALLBACK_POOL`에서 고른다 — 7절.
2026-10-08: 화면에 보이는 값이라 호출기가 실제로 고르는 대체 모델 하나와 같게 둔다 — `tests/orchestration/test_registry.py`가 확인). `team_definitions.yaml`의 step에
`retry: {target: <Worker id>, max_rounds: 2}`(검토 단계에만 — 2026-10-07: 출력 계약이 `ReviewResult`인 Worker 하나만 있는 순차 단계. RETRY 판정이면 `target`을 다시 실행, 최대 `max_rounds`번).
`registry.py`가 검증해 `Worker.fallbacks`, `PlanStep.retry`(`{target, maxRounds}` 또는 `null`)로 낸다. 검증: fallbacks의 중복·주 모델과 겹침 금지,
`retry.target`은 앞 단계(`depends_on`)에 있는 Worker여야 한다.

모델 배정 **초안** (2가 비용을 보고 확정한다. `.env`의 `ANALYSTS`·`APPROVER`에 있는 모델만). 2026-10-07: 이 초안대로 `worker_definitions.yaml`에 넣었다 (선정 팀은 조사 3개 gemini-3.8-flash, `selector_agent` gpt-5.6-luna, `selection_review_agent` claude-opus-5-5).
단계 `timeout`은 모두 180초로 바꿨다 (7절의 호출 한 번 60초 → 재시도 → 대체 모델이 들어가게).

| Worker | provider | model | fallbacks |
|---|---|---|---|
| market_agent, fundamental_agent, news_agent | devpass | gemini-3.8-flash | gpt-5.6-luna |
| report_agent | devpass | gpt-5.6-luna | gemini-3.8-flash |
| review_agent | devpass | claude-opus-5-5 | gpt-5.6-luna |
| risk_agent | devpass | deepseek-v4.1-flash | gpt-5.6-luna |
| news_screen_agent, filing_screen_agent, flow_agent (선정 팀) | devpass | gemini-3.8-flash | gpt-5.6-luna |
| selector_agent (선정 팀) | devpass | gpt-5.6-luna | gemini-3.8-flash |
| selection_review_agent (선정 팀) | devpass | claude-opus-5-5 | gpt-5.6-luna |

fallbacks 열은 2026-10-08에 실제 대체 모델로 맞췄다 (`FALLBACK_POOL` 순서에서 주 모델이 아닌 첫 모델. 그전 초안의 report_agent → claude-opus-5-5,
risk_agent → gemini-3.8-flash, 조사 Worker의 두 번째 모델은 화면에만 보이고 쓰이지 않았다).

## 5. 장애 주입 설정 (`Report.chaos`, API의 `ChaosConfig`)

```json
{"enabled": true, "probability": 0.5, "errorTypes": ["timeout", "server_error", "bad_output"],
 "workers": null, "scope": "primary", "seed": 123456}
```

호출 순서 (한 번의 `ctx.llm(...)` — **2026-10-07 담당 4 결정**, 쟁점 Q1·Q2. **2026-10-08 timeout 규칙 바뀜** — 주 모델 timeout은 같은 모델을 다시 기다리지 않고 바로 대체 모델, 대체 모델 timeout은 같은 모델로 한 번 더): 주 모델(YAML `model`) → **대체 모델 하나**. 모델마다 최대 2회 `MAX_ATTEMPTS_PER_MODEL = 2`(첫 시도 + 같은 모델 재시도 1회), 전체 **최대 4회** `MAX_ATTEMPTS = 4`(첫 시도 + 재시도 3회 — 주 모델 2회 + 대체 모델 2회), `deadline` 안에서.

## 8. Orchestrator가 지키는 것 (3) — `orchestration/orchestrator.py`·`runner.py`, `guardrails/guards.py`

- 진입점 `orchestrator.run_report(report, *, workers=None, llm_client=None, now=None) -> Report`. `state.start`로 시작해 `state.finish`로 끝낸다. 예외를 밖으로 내지 않는다 (실패도 `finish(failed)`).
- 단계 실행: `plan.steps` 순서대로 `set_step` → `mode: parallel`이면 `ThreadPoolExecutor`로 Worker들을 같이, `sequential`이면 차례로. 단계 `timeoutSec`가 Worker의 `deadline`이다.
- Worker 하나의 실행 = `agent_started` → `WORKERS[id].run(ctx)` → 결과를 `contracts.validate`로 다시 확인 → `add_result` + `agent_completed`. 실패(`LlmGaveUp`·`WorkerError`·시간 초과·예외) → `add_error` + `agent_failed(final: true)`.
- **Join Guard** (`guards.join(report, step, plan) -> JoinDecision(ok, inputs, reason)`): `join: true`인 단계 앞에서. 필수 Worker 결과가 모두 있고 계약을 통과했는지 확인 → 실패 결과 제외 → 다음 Worker에 줄 **최소 Context**(`inputs`)를 고른다. 막으면 `join_blocked` + 뒤 단계 Worker 전부 `agent_skipped` + `workflow_failed` + `finish(failed)`.
- **부분 실패 정책** (`failurePolicy`): `required_optional`(기본) = 필수 실패면 그 단계에서 멈춤, 선택 실패는 빼고 계속. `fail_fast` = 아무 실패에도 멈춤. `best_effort` = 끝까지 가고 결과 있는 것으로 작성.
- **검토 반복**: 검토 Worker(`review_agent`·`selection_review_agent`) 결과 `verdict`가 `RETRY`면 `review_retry` 사건을 남기고 `retry.target`(report_agent·selector_agent)을 `instructions`를 넣어 다시 실행(attempt+1), 다시 검토.
  다시 도는 검토 Worker에는 `ctx.retry`(`{round, review: 직전 ReviewResult, draft: 그 검토가 본 target 초안}`)를 준다 (target에는 주지 않는다 — 2026-10-12).
  `FAIL`이거나 `maxRounds`를 넘긴 `RETRY`는 `review_failed`로 `finish(failed)`이고, 남은 지적 줄(`claim — problem` 줄들을 " / "로 이은 것, 300자. 지적이 없으면 "검토 판정 FAIL" 또는 "검토 판정 RETRY")은 `workflow_failed.details.message`에 넣는다. `PASS`면 계속.
  Orchestrator는 그대로 `verdict`만 본다 (점수는 쓰지 않는다).
  선정 검토는 마지막 검토(attempt > `maxRounds`)에서 코드 점검(후보 표 밖 종목·공시 위험 high·reason·summary의 권유 표현·가격·목표가) 문제가 없으면
  LLM의 `RETRY`를 `PASS` + `acceptedWithNotes: true`로 바꿔 낸다 — 남은 지적은 issues·instructions에 기록으로 남는다 (2026-10-12, `docs/DECISIONS.md` 30장). 종목 리포트 검토는 그대로다.
- **Handoff**: `review_agent` 결과의 `handoff`가 있고 `plan.handoffs`에 그 경로가 있으면 `guards.handoff(...)`로 확인(허용 경로, `hop_count < maxHops`, 전달 데이터에 비밀 값 없음) → `handoff_started` → `risk_agent` 실행 → `handoff_completed`. 거절이면 `handoff_blocked` + 계속(리스크 점검 없이 완료).
  전달 데이터(`ctx.handoff`): `{"task_id", "trace_id", "from_agent", "to_agent", "objective", "inputs": {"memory_refs": [결과 키]}, "constraints": [...], "expected_output": "RiskResult", "attempt", "user_id", "hop_count"}` (`docs/plans/TEAM_PAPER_TRADING_PLAN.md` 부록 A4-3).
- **입력 Guard** (`guards.clean_text(text) -> tuple[str, list[str]]`, 3이 만든다): 뉴스·공시 본문에서 지시문("이전 지시를 무시", "시스템 프롬프트", "API 키를 출력" 등)과 비밀 값 모양(`sk-…`, 긴 토큰)을 지우고 (정리된 본문, 지운 사유 목록)을 돌려준다.
  Worker(2)는 외부 자료를 프롬프트에 넣기 전에 이 함수를 거치고, 지운 사유가 있으면 `run` 결과에 **`_guarded: [사유, ...]`** 키로 붙인다.

  `_changed`(선정 Worker가 검토 RETRY로 다시 쓴 곳, 2026-10-12)는 `details.changed`로.

| action | actor | status | 남기는 쪽 | details |
|---|---|---|---|---|

(2026-10-12) 선정 검토가 마지막 검토에서 지적을 남긴 채 통과하면 `"acceptedWithNotes": true`. 결과에 `_changed`가 있으면 `"changed"` (선정 Worker가 다시 쓴 곳: `"구성·순위"`·`"<코드> reason"`·`"<코드> evidence"`·`"summary"`, `[]`이면 고친 곳 없음) |

새 경우가 생기면 `exception`으로 뭉개지 말고 이 표에 코드를 더하는 PR을 먼저 올리고 5에게 알린다 (화면 문장 표와 같이).

**`timeout`과 `join_blocked`의 판정** (T3-12, 2026-10-07 정함): 필수 Worker가 실패하면 — 그 실패가 **단계 제한 시간(`timeoutSec`) 초과**면 `timeout`(Join 단계 앞이어도 이것이 먼저),
아니고 다음 단계가 `join: true`면 Join Guard가 막아 `join_blocked`, 그 밖이면 `agent_failed`. LLM 호출의 시간 초과(60초)가 재시도·대체 모델 뒤에도 실패한 것은 Worker 실패(`LlmGaveUp`)라 `join_blocked`·`agent_failed` 쪽이다.
선정 팀이 실패하면 하루 파이프라인은 규칙 점수 상위로 Fallback하고, 선별 결과의 `fallbackReason`에 이 코드(후보가 0개면 `no_candidates`)가 남는다.

`agent_skipped.details.reason`(`join_blocked`·`fail_fast`·`review_failed`)은 건너뛴 Worker의 사유라 이 목록과 따로다.

**장애·복구의 셈법** (4의 `stats.py`와 5의 화면이 같은 규칙):
- Worker의 **실행(run)** = 그 actor의 `agent_started`부터 다음 `agent_completed` 또는 `agent_failed(final: true)`까지.
- **장애 1건** = 한 run 안의 **첫** `agent_failed(final: false)`. 같은 run의 뒤 실패는 같은 건의 시도다.
- **복구됨** = 그 run이 `agent_completed`로 끝남. **복구 시간** = `agent_completed.at − 첫 agent_failed.at`.
- **자동 복구율** = 복구된 건 ÷ 장애 건 × 100. **평균 복구시간** = 복구된 건의 복구 시간 평균.
  이 셈법의 이름은 **호출 장애 자동 복구율**(관리자 화면 `/ops`의 복구 지표)이다. 평가 가이드 정의의 **시나리오 자동 복구율**(장애 시험 DR 결과표)과 섞지 않고 보고서·발표에 이름으로 나눠 적는다 (2026-10-04 합의, 컨셉 계획 12장).
- `injected`는 장애 건의 첫 실패가 주입이면 true.

- PR 설명에 **어느 문서의 어느 항목**을 만든 것인지 적는다 (예: "부록 A2 T2-3"). CI 통과 + 다른 담당 1명이 보면 합친다. 급하면 1(통합 담당)이 합친다.
- 매일 아침 `main`을 자기 브랜치에 합친다(rebase 또는 merge). 10/5 오전에 3절·4절·6절·7절의 **뼈대 PR**(함수 서명만 있는 빈 구현)이 먼저 들어가야 다른 사람이 import할 수 있다.
- 새 설정 키(`.env`)가 생기면 `.env.example`, `deploy/.env.docker.example`에 더하고 1에게 알린다. 새 외부 패키지는 `backend/`에만 (엔진은 표준 라이브러리).

### 주의

- 병렬 스레드에서 `state.record`를 동시에 불러도 step 번호는 겹치지 않는다 (잠금·재시도가 들어 있다). 스레드마다 Django DB 연결이 따로 생기니 끝날 때 닫는다.
- 실패한 결과를 빈 값이나 고정된 성공으로 바꾸지 않는다. 앞이 실패하면 뒤는 실행하지 않고 `skipped`.

- 비용 상한: `MAX_CONCURRENT = 1`. 테스트에서 실제 LLM을 부르지 않는다. 실제 실행은 T3-10에서 1~2건만.
- `run_engine.py`는 `trading` 앱 파일이다. 한 줄씩만 더하고, 1이 뒤에 `auto.tick()`을 더한다.

### 주의

- **주입은 호출 직전 한 곳**에서만. 복구 코드에 "주입이면 이렇게"라는 분기를 두지 않는다 (복구 로직은 진짜 장애와 같은 길을 탄다). 주입 여부는 Trace의 `injected`에만 남긴다.
- 무한 재시도 금지: 시도 수(호출 한 번 최대 4회)와 `deadline` 둘 다로 막는다. 대기 시간 상수는 모듈 상수로 두어 테스트가 0으로 바꾼다.
- 호출기는 `state.record`만 부른다. `add_result`·`add_error`·`finish`는 Orchestrator 몫.
- `agent_failed`에 `final: false`를 **꼭** 넣는다 (화면·지표가 포기(`final: true`)와 구분한다).
- Circuit Breaker 상태는 웹 프로세스에서 보이지 않는다 (엔진 프로세스 메모리). 지표 화면에는 Trace의 `circuit_open` 사유로만 나타난다.
  장애 주입 리포트는 그 리포트 전용 Breaker에서 센다 (2026-10-08, `00-공통.md` 5절) — 주입한 실패가 다른 리포트의 모델을 막지 않는다.
- 주입한 timeout은 기다리지 않아 그 `agent_failed`의 `latencyMs`·복구 시간이 거의 0이다. T4-7 지표·장애 복구 보고서에서는 주입 건의 복구 시간을 따로 보거나 주석을 단다.
- 비용 기록: `LlmReply.cost_usd`는 게이트웨이가 준 값. 주입으로 실패한 시도는 비용 0.
- `views.py`의 `ReportsView.post`는 2(한도)도 고친다. 4가 먼저(chaos), 2가 그 뒤에 한도를 넣는다.

3. **활성화 카드**: 투자 금액(내 자금 % 또는 원, 필수 — 2026-10-11) → 리스크 엔진 미리 보기(수량·매수 금액·목표 도달 이익·손절 손실과 자산 대비 %) → "계획 활성화".
4. **Discord**: 채널에 온 추천 메시지의 "계획 활성화" 링크를 다른 팀원이 누름 → 로그인 → 같은 화면(파란 띠 "Discord에서 연 활성화 링크") → 활성화 → `via: discord`.
5. **내 자동매매**: 워크플로우(활성화 → 리스크 점검 → 진입 주문 → 체결 대기 → 보유 감시 → 청산)와 사건 타임라인. 정규장이면 지정가 도달 시 체결 → 목표·손절 시 청산, 단계마다 종·Discord 알림.

6. "계획 중단": 체결 대기면 주문 취소, 보유 중이면 전량 매도(정규장 밖이면 매도 예약).

### 알려진 한계 (문서·발표에 그대로 적는다)

- Discord 활성화는 버튼이 아니라 **링크**다 (Webhook은 보내기만 된다. 봇은 만들지 않았다 — `docs/DECISIONS.md` 12-4). 링크를 눌러도 웹 로그인은 필요하다.
- 시연 추천은 AI가 아니다 (일봉 ATR 규칙). 화면·Discord·추천 내용에 늘 표시한다. 확률 0.45는 가정 값이다.
- 계획 하나 = 모의 주문 하나 = 포지션 하나. 같은 종목에 진행 중인 계획·주문이 있으면 활성화하지 않는다. 분할 매수·추가 매수는 없다.
- 알림은 팀 채널 하나로 간다 (개인 DM 없음). 멘션은 본인이 넣은 Discord ID를 믿는다 (소유 확인 없음).
- (B5) 실행 확인 체크리스트는 서버가 강제하지 않는다. `acknowledged`는 기록일 뿐이고, 체크리스트 없이 시작되지 않는 것은 화면 테스트로 보장한다.
