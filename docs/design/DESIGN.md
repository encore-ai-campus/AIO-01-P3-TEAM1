# 설계: 모의매매 엔진 · 키움 API · 화면 배치

엔진(`engine/paper_engine`)의 설계. 증권사에는 조회만 하고 매매는 모의 계좌에서 체결한다.
여러 작업자가 같이 따르는 결정(설정 키, 클라이언트 인터페이스, 모의 계좌 표·체결 규칙, Redis 키)은 `docs/DECISIONS.md`,
키움 TR·필드·호출 제한은 부록 A, 화면별 배치와 근거는 부록 B가 기준이다 (2026-10-12 합침 — `docs/DECISIONS.md` 32장).

## 목표

여러 AI의 교차검증으로 가장 가능성 높은 매매 시나리오를 선별하고, 예상 수익과 리스크를 팀 채널에 알린다.
주문은 증권사에 내지 않고 **팀 공용 모의 계좌**(가상 현금)에서 체결을 흉내 낸다. 모든 예측과 결과를 기록해
어떤 모델·규칙이 맞는지 추적한다.

## 결정 사항

| 항목 | 결정 |
|---|---|
| 시장 | `MARKETS`(기본 `KR`). 키움 미국 시세를 확인하면 `KR,US` |
| 매매 주기 | 스윙 전용 (보유 3~20거래일). 장기 투자 시나리오는 받지 않는다 |
| 증권사 | 키움 REST API **조회만** (시세·호가·일봉·종목·순위·환율). 계좌·주문 TR은 만들지 않는다 |
| 주문 | 모의 계좌(`paper_account`, 초기 자금 `PAPER_CAPITAL_KRW`)에서 엔진이 체결 |
| AI | 역할별 모델을 `.env`에서 관리. DevPass(LLM Gateway) 키 하나로 호출 |
| 알림 | openclaw → 팀 Discord 채널(`OPENCLAW_TARGET`), 알림만. 없으면 콘솔 |
| 사용자 조작 | 웹(4C 이후). 그 전에는 CLI(`account`, `buy`, `sell` 등) |

설정은 모두 `.env`(환경 변수가 우선)로 받고, 실행 데이터 위치는 `PAPER_ROOT`로 바꿀 수 있다.

## 원칙

- AI는 제안만 한다. 금액 계산, 한도, 체결 여부는 결정론적 코드(리스크 엔진, 모의 체결기)가 판단한다.
- AI가 숫자를 계산하지 않는다. 지표는 코드가 계산해서 넘기고, AI가 근거로 든 숫자는 코드가 원본과 대조한다.
- 실주문 코드는 없다 (주문 TR, 실주문 스위치, 사용자 컨펌 절차 모두 삭제).
- 엔진 내부 데이터 형식은 토스 응답 형식을 유지하고, 키움 응답 변환은 `data/kiwoom.py` 안에서만 한다.
- 엔진은 표준 라이브러리만 쓴다.

## 파이프라인

```
데이터 수집 → 웹 조사 → 시나리오 제안 → 사실 검증 → 검증 → 판정 → 최종 컨펌 → (모의 주문)
   코드        AI 3종      AI 분석가       코드      AI 분석가  코드    AI 승인자      코드
```

| 역할 | 설정 (`.env`) | 하는 일 |
|---|---|---|
| 조사자 | `RESEARCHERS` | 웹 검색으로 최근 사실을 모은다 |
| 분석가 | `ANALYSTS` | 시나리오를 제안하고, 다른 분석가의 시나리오를 채점한다 |
| 승인자 | `APPROVER` | 판정을 통과한 시나리오만 검토해 승인 또는 거부한다 ("최종 컨펌"은 이 AI 승인이다) |
| 핵심 모델 | `REQUIRED_MODELS` | 시간 초과되면 분석을 중단할 모델 목록 |
| 실행 | - | AI를 쓰지 않는다. 승인된 시나리오를 모의 주문으로 옮긴다 (`analyze --buy`, 전략 `paper`) |

모델 이름은 코드에 쓰지 않고 `.env`에서만 관리한다.

### 공유 컨텍스트

종목 데이터(스냅샷 + 웹 조사)와 데이터 읽는 법은 종목당 한 번만 만들어 모든 AI 호출의 앞부분에 똑같이 넣는다
(`agents/context.py`). 에이전트마다 다른 내용(역할, 검토할 시나리오)은 그 뒤에 붙인다.

### 호출 수와 제한 시간

- 종목당 호출 수는 조사자 수 + 분석가 수 × 2 + 통과한 시나리오 수다. 시나리오 수에 비례해 늘지 않는다.
- 호출당 제한 시간은 90초(웹 조사와 승인자는 150초)이고, 시간 초과는 다시 시도하지 않는다.
- 시간 초과가 한 번이라도 난 모델은 그 종목 분석의 이후 단계와 의결에서 뺀다.
  - 남은 모델끼리 의결권을 다시 나눈다.
  - 그 모델이 이미 낸 시나리오는 남기고, 제안자로서의 자기 평가 점수만 뺀다.
  - `REQUIRED_MODELS`에 있는 핵심 모델이 시간 초과되면 그 종목의 분석을 오류로 중단한다.
- 시간 초과가 아닌 실패(서버 오류, 형식 오류)는 모델을 제외하지 않고, 그 단계에 참여하지 않은 것으로만 센다.
- 여러 종목은 동시에 분석한다 (최대 4종목).
- 단계별 소요 시간과 비용은 실행 기록의 `stages`에 남는다.

### 1. 데이터 수집

- 키움 REST API (`data/kiwoom.py`, 세부는 부록 A): 일봉, 현재가, 호가, 종목 정보, 매수 유의사항,
  투자자별 매매동향(국내), 거래대금·등락률 순위(당일만), 환율. 응답은 엔진 내부 형식(토스 응답 형식)으로 바꿔 돌려준다.
- 장 운영 시간은 `data/calendar.py`가 만든다 (국내 09:00~15:30 + 공휴일(`DATA_GOKR_API` 특일 정보) + KRX 연말 휴장,
  미국 NYSE 규칙 + 서머타임).
- 뉴스는 Google News RSS에서 최근 7일 제목 15개를 가져온다 (키 불필요, 본문 없음).
- 증권사 리포트도 Google News RSS 헤드라인에서 모은다 (`data/broker_reports.py`, 스냅샷의 `brokerReports`).
  `"{종목명}" 목표주가`(미국은 `"{영문명}" price target`)로 최근 30일 제목을 받아, 목표가 언급이 있고 종목을
  가리키는 제목만 정규식으로 증권사·목표가·방향(상향·하향·유지)을 뽑는다. 제목 기반이라 누락·오류가 있을 수
  있고 리포트 본문은 없다. 실패하면 빈 목록이며 분석은 계속한다.
  네이버 금융(finance.naver.com)은 robots.txt로 자동 수집을 막고 있어 쓰지 않는다.
- 국내 종목의 재무와 공시는 DART에서 가져온다 (`DART_API_KEY`).
  - 공시된 값을 그대로 쓰는 것: 매출·영업이익·순이익, EPS, ROE, 부채비율, 순이익률, 매출총이익률, 유동비율.
  - 코드로 구하는 것: 최근 12개월(TTM) 합산, PER(현재가 ÷ TTM EPS), PBR(현재가 ÷ 주당순자산), 영업이익률, 성장률.
    PER과 PBR은 주가에 따라 바뀌어 증권사 API와 DART 어디에도 없다.
  - DART의 ROE와 이익률은 최신 보고서 기간의 누적 기준이다. 반기 보고서면 반기 실적 기준이며 연환산 값이 아니다.
  - 최근 5년 연간 실적 추이(매출·영업이익·순이익·자산·부채·자본·부채비율)는 공공데이터포털의
    금융위원회_기업 재무정보(`DATA_GOKR_API`, 요약재무제표)에서 가져와 `fundamentals.annualHistory`에 넣는다.
    연간 자료만 있어 DART를 대신하지 않는다. DART 재무 조회가 실패하면 최근 연간 실적으로 fundamentals를 채운다.
    조회 키인 법인등록번호는 DART 기업개황(`jurir_no`)에서 얻어 `.cache/dart_jurir_no.json`에 캐시한다.
- 미국 종목의 재무와 공시는 SEC EDGAR에서 가져온다 (`SEC_CONTACT_EMAIL`. SEC가 요청자 연락처를 요구한다).
  - SEC는 비율을 제공하지 않아 PER, PBR, ROE, 순이익률, 부채비율은 제출된 값으로 구한다 (최근 12개월 기준).
- 영업외 항목(금융수익·비용, 기타손익, 지분법손익, 세전이익, 법인세)도 넘긴다. 순이익이 영업 외 손익으로
  크게 달라진 경우 PER, EPS, ROE가 영업 실적을 대표하지 못하기 때문이다.
- 공시는 최근 30일 제목만 넘긴다.

### 2. 웹 조사

- 조사자들이 각자 웹을 검색해 최근 실적, 사건, 목표주가 변화, 예정 일정을 모은다.
- 조사자는 R1, R2...로만 표시한다. 어느 모델인지는 실행 기록에만 남긴다.
- 웹에서 온 내용은 검증되지 않은 정보다. 코드에서 다음을 처리한다.
  - 문장 길이를 제한하고 링크를 지운다.
  - 미래 날짜와 형식이 틀린 날짜를 버린다.
  - 게이트웨이가 돌려준 검색 인용 목록에 출처 주소가 있는지 확인한다 (`sourceVerified`).
    인용 목록을 주지 않는 모델은 확인 불가(null)로 표시된다.
- 비용의 대부분이 이 단계에서 나온다 (종목당 약 $0.2, 나머지 단계는 합쳐서 약 $0.07).
- `analyze --no-web`으로 이 단계를 건너뛸 수 있다.

### 3. 시나리오 제안과 사실 검증

- 분석가들이 서로의 결과를 보지 못한 채 같은 컨텍스트로 시나리오를 낸다. 제안하지 않는 것도 정상적인 답이다.
- 출력 형식은 `Scenario`(judge/scenario.py)로 고정한다. 투자 기간은 `SWING`만 받고 모델당 시나리오는 1개다.
  `LONG_TERM`은 과거 기록을 읽기 위해 형식에만 남아 있다.
- 스윙 기준 (제안·검증·승인 프롬프트 공통): 근거의 중심은 보유 기간 안에 가격을 움직일 수 있는 것
  (가격·거래량 구조와 추세, 변동성, 수급, 기간 안의 재료와 일정)이다. 재무는 거르는 조건이지 매수 이유가 아니다.
  뚜렷한 하락 추세에서는 데이터에 반전의 구체적 근거가 있어야 한다.
- 조건 검증 (코드, `judge/fact_check.py`): 투자 기간이 `SWING`이 아니거나 보유 기간이 3~20거래일
  (`SWING_MIN_DAYS`, `SWING_MAX_DAYS`)을 벗어나면 사실 검증 단계에서 탈락시킨다. 프롬프트의 숫자도 이 상수로 만든다.
- 목표가 도달 가능성 점검 (코드, `judge/reach.py`): 목표까지 거리 ÷ (ATR14 × √보유일수)를 계산해 시나리오 카드에
  표시하고 검증자와 승인자에게 `reachCheck`로 넘긴다. 1.5배(`HARD_RATIO`)를 넘으면 "주의"로 표시한다.
  **표시용이며 통과·탈락 판정에는 쓰지 않는다.** 1.5는 초기값이고 예측 추적 기록으로 보정한다.
- 코드가 근거로 인용한 값을 종목 데이터와 대조한다. 숫자는 0.5% 이내, 문장은 원문 그대로여야 한다.
  틀리면 탈락. 진입가가 현재가에서 5% 넘게 벗어나도 탈락.

### 4. 검증과 판정

- 분석가마다 한 번의 호출로, 자기 제안을 뺀 시나리오 전체를 채점한다.
  제안자가 누구인지와 제안자의 자기 평가 점수는 보지 못한다.
- 각 모델은 0~100점과 자기 확률 추정을 낸다. 점수 기준(`SCORE_RUBRIC`)은 모든 모델에 똑같이 준다.
- 의결권은 모델 크기별 가중치다. 크기는 `ANALYSTS`에서 모델마다 정하고,
  크기별 비중은 `config.py`의 `SIZE_WEIGHTS`(large 4, medium 2, small 1)에 있다.
- 최종 점수와 합의 확률은 의결권 가중 평균이다. 응답하지 못한 모델은 평균에서 뺀다.
- 통과 조건 (`judge/verdict.py`):
  - 최종 점수 60점(`PASS_SCORE`) 이상
  - 평가에 참여한 모델의 의결권 합이 60%(`QUORUM`) 이상
  - 리스크 엔진 통과

### 4-1. 최종 컨펌

- 통과한 시나리오만 승인자가 검토한다. 통과한 시나리오가 없으면 승인자를 부르지 않는다.
- 승인자는 승인 또는 거부만 한다. 가격을 고치거나 새 시나리오를 내지 않는다.
- 응답을 받지 못하거나 형식이 틀리면 승인하지 않은 것으로 본다.

실행 기록은 `runs/`에 JSON으로 남는다 (스냅샷, 시나리오, 검토, 판정, 단계별 시간과 비용).

### 5. 리스크 엔진

- 기대값 = 확률 × 예상 수익 − (1 − 확률) × 예상 손실 − 비용
- 예상 손실은 손절가가 아니라 손절가 −1%(`STOP_LIMIT_BUFFER`)로 계산한다. 손익비와 수량이 손절가 아래 체결을 반영한다.
- 수량 = (자산 × 건당 위험 비율) ÷ (진입가 − 손절가×0.99). 총 금액 한도, 매수 가능 금액, 유동성으로 상한을 둔다 (`assess` — 엔진 CLI·엔진 자체 계좌).
- 웹의 계획 활성화는 2026-10-11부터 `assess_budget`을 쓴다 (`docs/DECISIONS.md` 28장): 수량 = 사용자가 정한 금액 ÷ (진입가 × (1 + 수수료)).
  손익비·기대값·매수 유의·일일 한도는 `assess`와 같은 점검이고, 매수 가능 금액·총 금액 한도는 줄이지 않고 막는다 (`cash_short`·`total_limit`), 1주 미만이면 `budget_too_small`.
- 종목당 비중 한도는 두지 않는다. 한 종목의 크기는 건당 위험 한도(스윙은 자산의 1%)가 정한다.
- 총 금액 한도 (`MAX_TOTAL_INVEST_KRW`, 기본 없음): 진행 중 모의 주문(보유 + 체결 대기)의 매수 금액 합계
  (`records/account.invested_krw`)에 새 주문을 더한 값이 한도를 넘지 않게 수량을 줄인다. 모의 계좌는 현금이 상한이라 기본으로 두지 않는다.
- 소수점 방식 (`assess(..., fractional=True)`, 미국 종목만): 정수 주로 1주 이상 살 수 있으면 정수 주를 쓰고,
  못 사면 금액(센트 단위 내림) ÷ 진입가만큼 소수점 수량으로 산다. 최소 금액은 1달러다.
- 입력(`AccountContext`)은 모의 계좌에서 만든다 (`PaperExecutor.account_context`): 총자산 = 평가액(현금 + 보유 평가액),
  매수 가능액 = 현금 − 대기 매수 금액 (시나리오 통화로 환산, 전략 한도가 있으면 그 값으로 줄인다),
  수수료율 = `PAPER_COMMISSION_KR|US`, 기존 보유 평가액, 오늘 확정 손실·주문 수, 자동 관리 금액.
  `analyze --equity`를 주면 모의 계좌 대신 가상 자산으로 평가한다.
- 최소 손익비는 스윙 1.5다 (2026-10-07에 2.0에서 낮췄다. 장기 2.5는 과거 기록 평가용으로만 남아 있다). 이 기준은 AI에 알려주지 않는다 (기준에 맞춰 목표가를 부풀리는 것을 막기 위해).
- **손절가는 AI가 아니라 코드가 정한다** (2026-10-07, `judge/stops.py`): 최근 완성 봉 10개의 최저가 − ATR14×0.5를
  기준가 − ATR14×2 ~ 기준가 − ATR14×1 안으로 맞추고 호가 단위로 내린다. 기준가는 분석할 때의 가격(엔진 분석은 `lastPrice`,
  AI 리포트는 직전 정규장 종가)이다. 엔진 분석은 제안 전에 종목 데이터의 `stopRule`로 모든 AI에 보여 주고, 제안된 `stopPrice`를 이 값으로 바꾼다
  (`pipeline.apply_stop`). 일봉·ATR이 모자라 정하지 못하면 시나리오를 거른다. AI 리포트는 시세 조사(`market_agent`)의 `stop`을 작성 AI에 주고
  초안의 `targets.stop`을 그 값으로 바꾼다.
- 탈락 조건: 손익비 미달, 기대값 0 이하, 매수 유의 종목, 일일 손실 한도 도달, 수량 1주 미만.

### 6. 리포트와 팀 채널 알림

- 팀 채널에는 **매수 추천(판정 통과 + 승인자 승인)만** 보낸다. 추천 카드(`format_recommendation`)에는 조건
  (진입·목표·손절가, 수량, 예상 수익, 최대 손실, 점수, 확률, 손익비, 목표 도달 점검)과 AI 추론 요약이 들어간다.
  추론 요약은 ① 제안 근거 3개 ② 검증 점수 범위와 검증자별 주요 약점, 총평 ③ 최종 컨펌(AI 승인) 사유와 남은 위험이다.
  이미 있는 값을 줄여 쓰고 AI를 다시 부르지 않는다.
- 나머지 평가 자료는 리포트(PDF)로 첨부한다 (`report.py`): 요약 표, 종목별 지표와 뉴스·증권사 리포트, 모든 시나리오 카드
  (탈락 사유, 모델별 점수와 약점 전부, 승인자 의견), 웹 조사, 오류, 단계별 시간과 비용, 종목 선별 결과
  (규칙 통과·탈락·제외). 분석이 끝나면 한 줄 요약과 함께 보낸다. 추천이 없어도 리포트는 보낸다.
- 리포트는 실행 기록과 같은 이름으로 `runs/`에 남는다 (`runs/*.pdf`). HTML을 만들어 Chrome(headless)으로 PDF로
  바꾼다 (파이썬 의존성을 늘리지 않기 위해). Chrome이 없으면 HTML을 보낸다. `report runs/x.json [--send]`로 다시 만든다.
- 상세 내용(전체 카드, 웹 조사, 모의 주문 없이 기록만 할 때의 주문 계획)은 콘솔 로그에만 남긴다 (`notifier.log`).
- 알림은 `Notifier` 인터페이스(`send`, `log`, `send_file`)로 분리한다 (`notify.py`). 명령·컨펌은 받지 않는다.
  - `OPENCLAW_TARGET`(`channel:<팀 채널 ID>`)이 있으면 `openclaw message send --channel discord --target <대상>`
    (`OPENCLAW_BIN`)으로 보내고, 없으면 콘솔에 출력한다. 2000자를 넘으면 줄 단위로 나눈다.
  - 파일은 `--media`로 첨부한다. 실패하면 파일 위치를 글로 보낸다.
  - 전송에 실패해도 모의 체결 흐름은 멈추지 않는다 (콘솔 기록은 남는다). `serve`는 openclaw 없이도 돈다.
  - 보내는 것: 매수 추천, 모의 주문 접수·체결·청산·취소, 예약 등록·실행, 전략 실행 결과, 일일 리포트 PDF, 오류.
  - openclaw는 EC2에 설치한 팀용 Discord 봇을 쓴다 (계획서 3-3).

### 7. 모의 체결 (`agents/executor.py`, `records/account.py`)

AI를 쓰지 않고 증권사에 주문을 내지 않는다. 표·열·상태·체결 규칙은 `docs/DECISIONS.md` 4장이 기준이다.
`PaperExecutor`는 가격·환율·시각·정규장 여부를 인자로 받는 순수 로직이라 클라이언트 없이 시험한다.
가격은 엔진이 조회한 **확인 가격**(`confirmed_prices`: 현재가, 최우선 매수·매도호가의 중간값)이다.
현재가 한 건은 시간외 비정상 체결로 크게 튈 수 있어서다.
호가를 받지 못한 종목은 그 확인에서 건너뛴다.

계좌: 팀 공용 1개(`paper_account` id=1, "팀 공용"). 없으면 `PAPER_CAPITAL_KRW`로 만든다. 현금은 원화만 두고,
달러 종목은 체결 시점 환율(`exchange_rate`)로 환산해 넣고 뺀다. 매수 주문 하나가 포지션 하나다 (전량 청산).

```
ENTRY_PENDING ──체결──▶ EXIT_WATCHING ──목표·손절·기한·사용자 매도──▶ CLOSED
      └──지정가 당일 미체결·사용자 취소·체결 시점 현금 부족──▶ CANCELED
```

- 시장가 매수: 정규장이면 받은 확인 가격에 바로 체결. 정규장 밖 시장가는 체결기가 받지 않고 `Desk`가 다음 정규장 예약으로 넣는다.
- 지정가 매수 (호가 단위로 내림): 확인 가격 ≤ 지정가면 그 **확인 가격**으로 체결. 접수 뒤 처음 끝나는 정규장까지 안 되면 취소
  (`sync`의 `last_close`: 가장 최근에 끝난 정규장 종료 시각보다 먼저 접수한 대기 주문은 취소). 정규장 밖에 접수하면 다음 정규장까지 유효.
- AI 시나리오 (`submit_plan`): 실행 직전 점검을 통과하면 사용자 컨펌 없이 진입가 지정가로 접수한다. 목표·손절·기한은 `make_plan`.
- 목표가·손절가·기한: `_check_local_exit` 방식이다. 조건이 **2회 연속**(`LOCAL_EXIT_CONFIRMATIONS`) 확인되면 두 번째 확인 가격으로
  전량 매도한다. 중간에 조건이 풀리면 처음부터 센다. 기한은 `expire_date`가 지난 뒤 첫 정규장에서 판다. 목표·손절이 없으면 보유만 한다.
- 정규장 밖에는 체결·청산하지 않는다 (`open_markets`에 없는 시장은 건너뛴다).
- 비용: 수수료 = 금액 × `PAPER_COMMISSION_KR|US` (매수·매도 각각), 국내 매도는 거래세 `SELL_TAX_RATE["KR"]`(0.2% 가정) 추가.
  현금은 매수 −(금액 + 수수료) × 환율, 매도 +(금액 − 수수료 − 세금) × 환율. 실현 손익은 종목 통화(`pnl`)와 원화(`pnl_krw`, 환율 변화 포함).
  체결 하나마다 `paper_fills`에 남기고, 체결 내역·현금·주문 상태는 한 트랜잭션으로 바꾼다.
- 매수 가능액 = 현금 − 대기 매수 금액 (수량 × 지정가(시장가는 진입가) × 환율 × (1 + 수수료율)). 평가액 = 현금 + 보유 평가액.
  환율을 조회하지 못하면 보유는 체결 환율, 대기 주문은 가장 최근 달러 체결 환율로 환산한다 (원화 종목만 있으면 환율이 필요 없다).
- 매수를 막는 경우 (`OrderRejected`): 중단 스위치, 정규장 밖 시장가, 수량 0 이하, 국내 소수점 수량, 목표·손절 한쪽만,
  손절가 < 기준가(지정가 또는 현재가) < 목표가가 아님, 1억원 이상, 매수 가능액 부족, 같은 종목에 진행 중 주문(종목당 포지션 하나).
- 중단 스위치(`data/HALT`, `halt`/`resume`)는 새 모의 매수 접수만 막는다. 이미 접수한 지정가의 체결과 청산은 계속한다.
- 사용자 매도(`sell`): 보유 중이면 확인 가격에 전량 매도(`MANUAL`), 체결 대기면 취소. 정규장 밖이면 `Desk`가 예약으로 넣는다.
- 수정(`modify`): 진행 중 주문의 목표가·손절가·기한. 손절가 < 현재가 < 목표가, 기한이 지나지 않았을 것. 연속 확인 횟수는 다시 센다.

실행 직전 점검 (`pre_trade_checks`, AI 시나리오):
- 중단 스위치가 꺼져 있을 것
- 판정 통과와 승인자 승인
- 분석한 지 30분 이내
- 현재가가 손절가와 목표가 사이에 있고, 진입가에서 2% 이내
- 주문 금액 1억원 미만, 1주 이상(소수점은 1달러 이상)
- 같은 종목에 진행 중인 모의 주문이 없을 것

`sync`(CLI) 또는 `serve`가 진행 중인 주문을 확인한다. 주기: 운영 시장의 정규장 시작 전후 2분은 10초, 거래 시간(시간외 포함)
중에는 1분, 그 밖에는 5분 (`--sync-every-burst`, `--burst-window`, `--sync-every-open`, `--sync-every`).
변화(접수, 체결, 청산, 취소)만 팀 채널에 알리고, 조회 오류는 처음 실패와 복구만 알린다.

한계:
- 부분 체결과 부분 매도는 없다 (한 주문 = 한 포지션, 전량 체결·전량 청산).
- 체결은 확인 주기(정규장 중 1분)만큼 늦고, 체결 가격은 확인 가격이다 (실제 호가 잔량·슬리피지는 흉내 내지 않는다).
- 지정가는 확인 가격이 지정가 이하일 때만 체결된다. 확인 사이에 잠깐 닿았다 올라간 가격은 놓친다.
- 시간외(장전·애프터마켓) 체결은 하지 않는다. 밤사이 갭은 다음 정규장 첫 확인 가격으로 청산된다.

### 7-1. 모의 주문 요청 (`trading.Desk`, CLI)

웹(4C)이 생기기 전 임시 조작 수단은 CLI다. 같은 `Desk`를 serve의 예약 실행과 이후 작업 큐(4C)가 쓴다. 요청자는 `--by`(기본 `cli`).

```
python -m paper_engine account                       # 현금, 평가액, 초기 자금 대비 손익, 매수 가능액, 보유
python -m paper_engine orders [--all]                # 진행 중(기본)·전체 모의 주문
python -m paper_engine fills [--limit N]             # 체결 내역
python -m paper_engine buy <종목코드|이름> <수량> [--limit P] [--target P --stop P [--days N]] [--by NAME]
python -m paper_engine sell <주문번호> [--by NAME]     # 전량 매도 (체결 대기면 취소)
python -m paper_engine cancel <주문번호> · modify <주문번호> [--target P] [--stop P] [--days N]
python -m paper_engine reservations [--cancel ID]
python -m paper_engine sync                          # 체결·청산을 지금 한 번 확인
```

- 매수할 종목은 종목코드나 정확한 종목명으로만 찾는다 (운영 시장의 전체 종목 목록, 하루 한 번 캐시, `symbols.resolve_listed`).
  거래 가능 상태가 아니면 받지 않는다. 미국 종목(소수점 수량 가능)은 `MARKETS`에 `US`가 있을 때만 받는다.
- 목표·손절을 주고 기한을 주지 않으면 기한은 30일(달력 일수, 최대 180일)이다.
- `account`, `orders`, `fills`, `cancel`, `modify`, `reservations`, `halt`, `resume`은 키움 키 없이도 돈다
  (`account`는 현재가 없이 체결가로 평가). 조회가 필요한 명령(`buy`, `sell`, `sync` 등)만 키를 요구한다.

예약 주문 (`scheduler.ReservationBook`, Redis `paper:reservation:*`):
- 정규장 밖 시장가 매수·매도를 넣는다. 예약할 때 즉시 주문과 같은 점검을 하고(매수), 예약한 뒤 처음 시작하는 정규장 시작 때
  `serve`가 실행한다. 실행 때는 다시 묻지 않는다. 매수는 실행 때 확인 가격이 예약 때보다 10% 넘게 움직였으면 취소한다.
  매도는 그 포지션이 아직 보유 중일 때만 판다. 요청자(`requested_by`)는 예약에 남아 모의 주문에 그대로 기록된다.
- 실행이나 취소 시 먼저 목록에서 빼므로 한 번만 실행된다. 4C에서 DB `reservations` 표로 옮긴다.

### 7-2. 전략과 개장 전 종목 선별

전략은 자동매매 규칙 묶음이다 (`strategies.py`, Redis `paper:strategy:*`, 4C에서 DB로). 정하는 것:
- 시장 (KR | US), 후보 수 (규칙 점수를 매길 종목 수, 기본 30), AI 분석 수 (기본 3, 종목당 약 $0.3)
- 실행: `notify`("알림만") | `paper`("모의 자동 매수": 승인된 시나리오를 실행 직전 점검 후 요청자 `strategy:<번호>`로 모의 주문).
  옛 값 `confirm`(컨펌 후 주문)은 읽을 때 `paper`로 바꾼다
- 소수점 (미국만): 1주를 못 사는 종목을 소수점 수량으로 산다 (5절). 기본은 off
- 리포트 후보: 최근 증권사 리포트 헤드라인의 종목도 선별 후보에 넣는다. 기본은 off (기본 전략도 off)
- 한도: 종목당 매수 금액 상한. 리스크 엔진의 매수 가능 금액을 이 값으로 줄여 수량 상한을 건다.

`serve`는 운영 시장(`MARKETS`)의 활성 전략마다 정규장 시작 1시간 전(국내 08:00, 미국 21:30 또는 22:30)에 하루 한 번 돌린다.
휴장일에는 돌지 않는다. 같은 날 두 번 돌지 않도록 Redis에 기록한다 (`paper:scan:s{전략}:{날짜}`).
처음 `serve`를 켜면 운영 시장의 기본 전략(알림만)이 만들어진다.

한 번 실행:
1. 거래대금 상위 100개(전일, 투자 유의 제외) → ETF·ETN·레버리지 등 제외 → 후보 수만큼 일봉으로 규칙 점수
   (`judge/screen.py`: 60일선 위, RSI 40~75, ATR 비율 1.5~8%, 추세·모멘텀·RSI·변동성 점수) → 상위 10개 알림.
   - 리포트 후보가 켜져 있으면 최근 2일 리포트 헤드라인(`broker_reports.candidates`: 국내 `목표주가`,
     `리포트 브리핑 목표가`, 미국 `price target raised`, `analyst price target`)에서 전체 종목 목록과 이름(미국은 티커도)이
     정확히 하나로 맞는 종목만 종목별 최신 헤드라인 하나로 모은다. 여러 종목이 맞거나 모호하면 버린다.
   - 중복 제거: 거래대금 상위에서 이미 점검한 종목, 모의 계좌 보유 종목, 체결 대기 모의 주문 종목, 최근 24시간 안에 전략·수동·
     일일 분석한 종목(`daily.recent_analyses(include_daily=True)`)은 뺀다 (`exclusions`).
   - 남은 것 최대 10개(`REPORT_CANDIDATES`)를 ETF 등 제외 규칙과 같은 규칙 점수에 태운다. 거래대금은 마지막 완성
     일봉으로 어림한다. pick과 탈락에는 출처(`origin`: 거래대금 상위 | 증권사 리포트)와 증권사·목표가·방향·제목을
     붙이고, 결과의 `reportCandidates`에 가져온 목록과 제외 사유, 점검·통과·탈락 수를 남긴다.
2. 상위 N개를 AI 교차검증(`analyze`)한다. 리포트 후보가 켜져 있고 상위 N개에 리포트 출처가 없으면 마지막 자리를
   통과한 리포트 pick 중 점수가 가장 높은 것으로 바꾼다 (최소 1개는 검토). `paper` 전략이면 승인된 시나리오를 실행 직전 점검 후
   진입가 지정가로 모의 주문한다 (7절. 정규장 전 접수는 그날 정규장 끝까지 유효).
   - AI 분석 대상은 최근 24시간 안에 분석된 종목(일일 리포트 분석 포함, `recently_analyzed`)을 빼고 다음 순위로
     채운다 (리포트 후보 여부와 무관, `scan`도 같다). 건너뛴 pick에는 `skipped`에 사유("이미 분석됨 (기록 파일 시각)")를
     붙이고 결과의 `skipped`에 모은다. 알림 줄 끝에 `[분석 제외: 이미 분석됨 07:05]`, 리포트 표에 "분석 제외" 열.
     보유·주문 종목은 리포트 후보에서만 빼고, AI 분석 대상에서는 24시간 안에 분석 기록이 있을 때만 뺀다
     (일일 분석이 없던 날에는 전략이 분석한다). 리포트 출처 최소 1개 규칙도 건너뛰지 않은 pick 안에서 적용한다.
3. 결과(통과 종목과 지표, 탈락·제외 사유, 분석 기록 파일)를 Redis에 저장한다 (`paper:scanresult:*`, 30일).
   웹·`info`가 선정 이유를 보여 줄 때 읽는다.

전략 만들기·바꾸기는 웹(4C)에서 한다. `info strategies`로 보고,
`scan KR|US [--no-ai] [--reports]`는 전략 없이 바로 돌린다 (모의 주문 없음).

### 7-3. 읽기 전용 조회 (`info.py`)

`python -m paper_engine info strategies|scans|stock|holdings|orders` (JSON). 웹(4C)의 화면과 같은 자료다.
`stock <종목>`은 그 종목의 선별 결과(선정·탈락 이유), 최근 AI 분석 기록(분석가별 점수·비판, 승인자 의견), 모의 주문, 예약을 모은다.

### 8. 엔진 생존 신호

`serve`는 루프마다 Redis `paper:engine:heartbeat`에 지금 시각(ISO)을 `EX 120`으로 쓴다. 웹은 이 키가 없으면 엔진이 멈춘 것으로 본다.

### 9. 기록

- 사실 검증을 통과한 시나리오는 선별 여부와 무관하게 모두 예측 추적으로 기록한다 (`trades`·`predictions`, `data/trading.db`, SQLite).
  모의 계좌 주문(`paper_orders`)과는 별개다 (승인돼 모의 주문한 시나리오는 `paper_orders.trade_id`로 연결된다).
  탈락시킨 판단이 옳았는지 확인하기 위해서다.
- `track`은 완성된 일봉으로 체결과 청산을 판정한다. 규칙은 `paper.py` 상단 참고. 애매하면 불리한 쪽으로 본다.
- `stats`는 선별·탈락별 손익과 모델별 확률 예측 성적(Brier)을 보여준다.

### 10. 백업

- `serve`가 매일 06시 이후 첫 루프에서 한 번 백업한다 (`records/backup.py`). `backup` 명령으로 바로 할 수도 있다.
- SQLite는 온라인 백업 API로 사본을 만들고, Redis는 `paper:*` 키를 JSON으로 내보낸다 (남은 TTL 포함).
- 위치는 `data/backups/` (`.env`의 `BACKUP_DIR`로 변경, 다른 디스크 권장). 14일 지난 백업은 지운다.
- 복원: SQLite는 `serve`를 멈추고 백업 파일을 `data/trading.db`로 복사. Redis는 `backup --restore-redis <파일>`.
- `runs/` 분석 기록과 `.env`는 백업하지 않는다.

### 11. 시장 기록과 일일 리포트

- 시장 기록 (`records/market_log.py`): 시장별로 정규장 종료 15분 뒤부터 다음 정규장 시작 전까지 하루 한 번
  거래대금 상위 100(투자 유의 제외), 등락률 상위·하위 30, 종목 정보(securityType), 벤치마크 일봉(KR 069500, US SPY),
  환율을 `data/trading.db`의 `market_days`, `rankings` 표에 남긴다. `serve`가 1분마다 운영 시장(`MARKETS`)만 확인하고,
  `record`로 바로 할 수 있다. 환율 조회가 실패해도(국내만 운영하면 필요 없다) 환율 없이 기록한다. 키움 순위는 당일만이라 집계 기준 시각은 비어 있다.
- 일별 자산 (`equity_daily`): 국내 시장 기록 직후 하루 한 번 모의 계좌 평가액(현금 + 보유 평가, 보유는 현재가=종가)을 남긴다.
  일일 리포트의 전일 대비에 쓴다.
  - 목적: 백테스트의 유니버스 편향 제거 (과거 시점 랭킹은 API로 받을 수 없어 매일 쌓는다), 일일 리포트의 시장 동향.
  - 다음 정규장이 시작한 뒤에는 전일 것을 기록하지 않는다 (랭킹이 이미 그 날 값이라 날짜가 어긋난다).
- 일일 리포트 (`daily.py` → `report.build_daily_html`): 매일 7시(KST, 미국장 마감과 시장 기록 뒤) 이후 첫 확인에서
  `data/reports/daily-YYYYMMDD.pdf`를 만들어 요약 2~4줄과 함께 팀 채널로 보낸다. `daily-report [--days N] [--send]`로 바로 만든다.
  - 구성: 모의 계좌(총자산 = 현금 + 보유 평가, 초기 자금 대비 손익, 전일 대비(`equity_daily`), 매수 가능액, 보유 종목과 요청자),
    진행 중 모의 주문(체결가, 현재가, 목표·손절·기한, 예상 손익, 요청자), 기간 내 종료 주문(청산 사유, 손익), 누적 성적(통화별 손익·승률),
    시장 동향(운영 시장만: 벤치마크 10일, 거래대금·상승·하락 상위 10), 기록(전략, 기간 내 분석 실행, 예약, 예측 추적 성적, 중단 스위치,
    최근 백업, 시장 기록 일수).
  - 모의 계좌 다음에 AI 분석 섹션(종목, 역할, 결과, 최고 점수, 추천 시나리오 진입·목표·손절·확률·기간, 사유)이 있다.
    그 외 섹션은 AI를 쓰지 않는다. 현재가·환율 조회가 실패하면 체결가·체결 환율로 평가하고 메모를 남긴다. 값이 없는 섹션도 "없음"으로 남긴다.
- 예측 추적 자동 갱신: `serve`가 시장 기록을 남긴 직후(정규장 마감 후 일봉이 완성된 시점)와 매일 자동 리포트 직전에
  `__main__.track_paper`(= `track`)를 돌려 결과(목표·손절·만료)를 채운다. 리포트 기록 절의 "예측 기록 현황"에
  시나리오·청산 수, AI 확률 대 실제 도달률, 모델별 적중률·Brier가 나온다 (`Store.prediction_summary`, `model_stats`).
- 일일 AI 분석 (`daily.analysis_symbols` → `__main__.run_daily_analysis` → `cmd_analyze`, 모의 주문 없음, 웹 조사 포함):
  - 대상: 모의 계좌 보유 종목 → 진행 중 모의 주문 종목 → 시장별 최신 시장 기록의 거래대금 상위 3개(ETF 제외) 순서로,
    중복을 빼고 최대 20종목. 역할은 이어 붙인다(예: "보유·모의 주문"). 보유 종목 정보에는 종목 유형이 없어
    이름(ETF, ETN, TIGER, KODEX 등)으로 ETF를 거른다. 이름에 표시가 없는 ETF는 분석된다 (비용만 더 든다).
    시장 기록이 없는 시장은 건너뛰고 리포트에 메모를 남긴다.
  - 중복 제외: 최근 24시간 안의 실행 기록(`runs/*.json`, startedAt 기준. 일일 분석 기록과 모델 응답 에러로 중단된 종목은
    빼고)에 있는 종목은 보유·주문 종목이라도 다시 분석하지 않고, 그 기록의 결과를 표에 "이미 분석됨 (기록, 시각)"으로
    보여 준다 (한도 20에 세지 않는다). AI 분석을 하는 활성 전략(Redis, status=active, 분석 수 > 0)이 있는 시장은
    거래대금 상위 그룹을 통째로 뺀다 (전략이 매일 정규장 1시간 전에 분석한다). Redis가 없으면 그룹을 넣는다.
  - 보유 종목도 매수 시나리오 기준으로 평가한다. 보유 유지·매도 판단의 참고용이며 주문은 내지 않는다.
    승인된 시나리오는 다른 분석처럼 예측 추적 후보로 기록된다.
  - 기록은 `runs/YYYYMMDD-HHMMSS-daily.json` (역할도 넣는다). 분석 리포트 PDF와 요약은 `[일일 분석]`으로 따로 보낸다.
  - 재사용: 같은 날 일일 분석 기록이 있으면 자동 발송과 `daily-report`는 다시 분석하지 않고 그 결과를 넣는다
    (리포트에 "재사용" 표시). 새로 분석하는 것은 `daily-report --analyze`(이후 웹의 리포트 요청)뿐이다.
    기록이 없고 분석을 요청하지 않았으면 분석 없이 보낸다.
  - 스레드: 분석은 10~20분 걸리므로 메인 루프는 리포트 스레드를 띄우기만 한다 (전략 실행과 같은 방식).
    AI 분석을 하는 리포트는 잠금으로 한 번에 하나만 돈다 (중복 비용 방지).
  - 분석이 실패해도(AI 설정 없음, 대상 없음, 오류) 리포트는 보내고 이유를 AI 분석 섹션에 남긴다.
    리포트 스레드 오류는 알린다 (자동 발송은 1분마다 다시 시도하므로 같은 날 처음 실패만).

## 제약과 가정

- 키움 토큰·호출 제한·TR별 필드는 부록 A. 토큰은 파일 캐시(`KIWOOM_TOKEN_CACHE`)로 공유한다.
- 순위는 당일만 받는다. 백테스트 유니버스는 당일 상위 100 + 시장 기록 누적분이다 (`backtest/README.md`).
- 장중에는 오늘자 일봉이 미완성 상태로 내려온다. 장 달력으로 정규장 마감 전 봉은 제외한다 (`calendar.drop_incomplete`).
- 미국 시세·환율은 키움 지원을 확인한 뒤 `MARKETS=KR,US`로 켠다. `MARKETS=KR`이면 엔진은 미국을 부르지 않고,
  환율 조회가 실패해도 시장 기록·일일 리포트·리스크 평가가 멈추지 않는다.
- 재무가 비어 있는 경우: ETF, 미국에 상장한 해외 기업(TSMC 등. 국제회계기준으로 제출해 형식이 다르다).
- 주식 종류가 여러 개인 미국 회사(버크셔 등)는 주당순자산과 PBR을 비운다. EPS를 주식 종류별로 내는 회사는 PER도 빈다.
- 금융회사는 매출·영업이익 계정이 일반 기업과 달라 영업이익률과 성장률이 비어 있다.
- Claude는 게이트웨이의 JSON 모드를 지원하지 않는다. 프롬프트로 JSON을 요구하고 코드에서 파싱한다.
- 투자자별 매매동향 등 수급 데이터는 국내 종목만 제공된다.
- 국내 매도 거래세율은 `risk.py`의 `SELL_TAX_RATE`에 0.2%로 가정해 두었다 (모의 체결도 같은 값을 쓴다). 실제 세율 확인이 필요하다.
- AI가 내는 확률은 실적이 쌓이기 전까지 검증되지 않은 값이다.

### A2. 토큰 (au10001)

- `POST /oauth2/token`, 본문 `{"grant_type": "client_credentials", "appkey": ..., "secretkey": ...}`.
- 응답 `{"token": "...", "token_type": "bearer", "expires_dt": "20241107083713", "return_code": 0}`. `expires_dt`는 KST `YYYYMMDDHHMMSS`.
- 폐기는 `au10002`(`/oauth2/revoke`) — 쓰지 않는다.
- 오류 코드: `8001`·`8002` 앱키·시크릿 검증 실패, `8005` 토큰 무효, `8010` **토큰을 발급받은 IP와 요청 IP가 다름**, `8030`·`8031` 실전/모의 구분 불일치,
  `8040`·`8050` (지정)단말기 인증 실패, `8103` 토큰·단말기 인증 실패.
- 구현: 토큰 파일 캐시(`KIWOOM_TOKEN_CACHE`, 권한 0600, 원자적 교체)를 프로세스끼리 공유한다. 캐시에는 토큰·만료 시각·도메인·앱키 지문(sha256 앞 16자)만
  남기고 앱키·시크릿은 쓰지 않는다. 도메인이나 앱키가 다르면 캐시를 쓰지 않는다. 만료 5분 전부터 재발급.
  HTTP 401 또는 `8005`·`8031`·`8103`(본문 또는 메시지 안)이면 캐시 파일을 다시 읽어 다른 프로세스가 새로 받은 토큰이 있으면 그것을,
  없으면 한 번만 재발급해 다시 보낸다 (공식 클라이언트와 같은 코드 집합).

### A3. 호출 제한 (출처 3)

| 구분 | 공식 한도 (계좌·토큰별) |
|---|---|
| 국내주식 | 조회 TR 초당 5회, 주문 TR 초당 5회 |
| 미국주식 | 조회 초당 5회, 주문 초당 10회, 환전 초당 1회. **피크(09~10시 KST)** 조회·주문 초당 3회. 미국 전체 초당 50회, 차트 전체 초당 20회, 종목리스트(`usa10099`) **분당 5회** |
| 모의투자 | 국내 TR 1개당 초당 1회 |

- 초과 오류: `1700`(API별), `1701`(전체), `1702`(그룹). HTTP 429도 올 수 있다 (공식 MCP 안내).
- 구현: 클라이언트 하나 안에서 모든 TR 사이 0.25초(초당 4회), 미국 TR은 피크 시간 0.34초, `ust31301` 1.1초, `usa10099` 12.5초 간격을 둔다.
  잠금 안에서 다음 호출 시각을 예약하고 잠금 밖에서 기다리므로 serve의 여러 스레드가 같이 써도 된다.
  429·`1700`~`1702`는 `Retry-After`(없으면 1·2·4초) 뒤 최대 3번 다시 보낸다.
- **주의**: 한도는 토큰 단위인데 간격 조절은 프로세스 안에서만 한다. 엔진 serve와 CLI 명령을 동시에 돌리면 합쳐서 초당 5회를 넘을 수 있다
  (그때는 재시도로 흡수). 웹(Django)은 키움을 직접 부르지 않는다 (DECISIONS 1·6장).

- `screen.eligible`은 `STOCK`·`FOREIGN_STOCK`·`DEPOSITARY_RECEIPT`만 통과시키므로 위 특수 유형과 `SPAC`은 선별에서 빠진다
  (스윙 대상이 아니라 뺐다).
- 외국기업(`companyClassName`=외국기업)·DR 구분은 아직 하지 않는다 → `STOCK`.
- `status`: 목록·조회에 있으면 `ACTIVE`. `koreanMarketDetail.krxTradingSuspended` = `state`에 "거래정지",
  `liquidationTrading` = `orderWarning=2` 또는 `state`에 "정리매매".
- `leverageFactor`: ETF·ETN 이름으로 추정 (레버리지·2X → `"2"`, 3X → `"3"`, 인버스 → `"-1"`, 인버스2X·곱버스 → `"-2"`). 주식은 `None`.
- 목록에 없는 종목(당일 신규 상장 등)은 `ka10100`의 `marketCode`를 같은 표로 읽고, 모르는 코드는 `UNKNOWN`(선별 탈락).
- 미국: `usa10098`의 `isEtf`=Y → `ETF`, 아니면 `STOCK`. `englishName` = `stk_enm`. ETN·DR 구분은 없다.

#### 매수 유의 (`warnings`, `exclude_caution`)

국내 `ka10099`/`ka10100`의 세 필드로 만든다. 하나라도 있으면 리스크 엔진이 매수를 막는다 (`judge/risk.py`).

| 근거 | 값 | `warningType` |
|---|---|---|
| `orderWarning` | `1` ETF투자주의요망, `2` 정리매매, `3` 단기과열, `4` 투자위험, `5` 투자경고 | `ETF_INVESTMENT_CAUTION`, `LIQUIDATION_TRADING`, `SHORT_TERM_OVERHEATED`, `INVESTMENT_RISK`, `INVESTMENT_WARNING` |

순위의 `exclude_caution`도 같은 기준으로 거른다 (국내는 추가로 요청 옵션으로 관리종목 제외). 미국은 유의 정보가 없어 `warnings`가 `[]`이고 거르지 않는다.
일별 "투자주의" 지정이 `auditInfo`에 실제로 들어오는지는 미확인이다.

화면 배치를 바꾸면 이 문서의 해당 줄도 함께 고친다.

### B0. 배치 원칙 (모든 화면 공통)

1. **여정 순서**: 서비스 여정은 ① 만들기(리포트) → ② 검토 → ③ 실행(모의 자동매매)이다. 화면마다 지금 사용자의 **다음 한 걸음**이 첫 화면에 온다.
2. **결론 먼저**: 리포트·분석·복기는 결과 → 행동 → 근거 순서다. 근거는 행동 아래나 접힘 안에 둔다.
3. **다시 온 사람의 첫 질문**: "내가 시킨 일이 어떻게 됐나"(만드는 중인 리포트·진행 중인 자동매매)를 팀 피드·참고 자료보다 위에 둔다.
4. **빈도와 위험**: 자주 쓰는 것은 위·엄지 영역에, 한 번 정하면 끝나는 설정은 아래에 둔다. 위험한 동작(멈추기·로그아웃)은 이동 링크와 떼어 맨 아래에 두고, 누르기 전에 결과를 한 줄로 말한다.
5. **모바일 엄지 영역**: 주 행동은 화면 가운데 아래·하단 탭 바로 위에 둔다. 시트·폼의 제출 버튼과 금액 확인은 바닥에 붙여 입력하는 동안에도 보이게 한다. 키보드가 아래 절반을 덮는 화면(검색)은 입력칸과 첫 결과를 위에 둔다.
6. **PC 2단 문법**: 왼쪽 넓은 열은 보기·읽기·감시, 오른쪽 340~380px 열은 하기·상태·다음 행동이다. 같은 탭 안의 화면은 같은 문법을 쓴다.
   오른쪽 열을 따라오게(sticky) 할 때는 화면 높이 안에 들어올 때만 그렇게 하고, 길면 열 안쪽 스크롤이나 바닥 고정으로 주 버튼이 화면 밖에 묶이지 않게 한다.
7. **DOM 순서 = 모바일 순서**: PC 2단은 grid 배치로만 바꾸고 `order-*`로 순서를 뒤집지 않는다. 키보드·화면 읽기 순서가 화면 순서와 같아야 한다.
8. **자리를 고정한다**: 있고 없음에 따라 섹션이 생기고 사라지면 아래가 밀린다. 비어도 한 줄을 남기고(예: "진행 중인 모의 자동매매가 없어요"), 늦게 오는 안내는 펼침(Collapse)으로 들어온다.
9. **같은 기능은 같은 자리·같은 말**: 보기 전환(쉬운↔전문가), '전체 보기 ›', 섹션 머리(카드 밖 19px 제목 = 목록 섹션, 카드 안 17px = 한 덩어리 카드), 빈 상태(아이콘·제목·설명·다음 행동)를 화면마다 같게 쓴다.
10. **좁은 PC(1024~1279px)**: 2단이 본문 열을 옆 열보다 좁게 만들면(숫자가 자릿수 중간에서 줄바꿈) 그 화면은 한 열로 둔다(홈은 680px 한 열, 2단은 1280px부터).

- 홈 머리: 모바일은 서비스 이름(로고 + "모매매")을 보이고 h1 "홈"은 화면 읽기에만 둔다. 아래 탭이 이미 "홈"이라 같은 말이 겹치기 때문이다. PC는 "홈" 제목.
- 화면 머리에는 [뒤로·제목·종]만 두고, 보기 전환은 내용 쪽(리포트 머리 카드·홈 맨 아래)에 둔다 — 360px에서 긴 종목명이 잘리지 않게.
- 토스트: 모바일은 하단 탭·주문 바 바로 위(방금 누른 버튼 근처), PC는 본문 열 가운데 아래. 시트가 열려 있으면 화면 위쪽. 늘 맨 위 층.
- 연결이 끊기면 화면 아래(모바일은 하단 탭·구매 바 바로 위, PC는 본문 열 아래)에 한 줄로 알린다 — 위쪽 머리·검색칸·탭 줄을 덮지 않고 스크롤해도 늘 보이게. 아래 칸은 하단 바 → 진단 폼 바닥 → 연결 띠 → 토스트 순으로 쌓인다.
- 404: 아이콘 → 제목 → 설명·요청 주소 → 큰 '홈으로' → 보조 '리포트 보기'. 막힌 사람에게는 다음 행동이 가장 중요하다.
- 로그인: (앱을 `/`·`/login`으로 열 때 5초 인트로가 먼저 덮는다 — `docs/DECISIONS.md` 27장) 정체성(로고 56px → 워드마크 → 부제 "여러 AI가 함께 검증하는 모의투자") → 가치(설명 한 줄 + 3단계 칩) → 입력 → 결정(로그인) → 안심('실제 주문은 나가지 않아요'). 가로 가운데 정렬, 같은 말을 두 번 하지 않는다. 오류 한 줄 자리를 미리 잡아 화면이 흔들리지 않는다.

### B2. 홈 (`/`)

| 보기·기기 | 순서 |
|---|---|
| 쉬운 보기 모바일 | 머리(브랜드) → 3단계 안내(가로 스테퍼·지금 단계·CTA·예시 칩) → 만드는 중인 리포트(있을 때) → 진행 중인 모의 자동매매(늘 같은 자리, 비면 한 줄) → 최근 AI 리포트 → 오늘의 내 종목 뉴스(국내 보유가 있을 때) → 내 자산 → 최근 알림 → 랭킹 → [이 화면만 자세히 보기 · 3단계 안내 다시 보기] |
| 쉬운 보기 PC(1280~) | 왼쪽[3단계 안내 → 만드는 중 → 진행 중 → 최근 AI 리포트 → 내 종목 뉴스] \| 오른쪽 360[내 자산 → 최근 알림 → 랭킹] |
| 전문가 보기 모바일 | 머리 → 내 자산(카드 전체가 링크) → 장 상태 칩 한 줄 → 만드는 중 → 진행 중 → 새 계획 제안 → 최근 AI 리포트 → 내 종목 뉴스(요약형) → AI 교차검증 분석 4장 + 전체 보기 → 랭킹 → [이 화면만 쉽게 보기] |
| 전문가 보기 PC(1280~) | 왼쪽 360 sticky[내 자산 → 검색 → 장 상태] \| 오른쪽[만드는 중 → 진행 중 → 새 계획 제안 → 최근 AI 리포트 → 내 종목 뉴스 → 교차검증 분석 2×2 + 전체 보기 → 랭킹] |
| 1024~1279px | 모바일과 같은 순서의 680px 한 열 |

- 3단계 안내는 사용자의 진행 상태를 따라간다(✓ 한 단계 / 지금 / 다음). 지금 할 일 하나와 버튼 하나만 남겨 버튼이 엄지 높이에 온다. 다 해 보면 한 줄로 줄어든다.
- "내가 시킨 일"(만드는 중·진행 중)을 팀 피드(최근 리포트 = ② 검토 재료)보다 위에 둔다(원칙 3).
- 전문가 PC의 sticky 열에는 스크롤 내내 볼 것(돈·검색·장 상태)만 담아 680px 높이 화면에도 잘리지 않는다. 오른쪽 피드는 진행 중인 일 → 할 수 있는 일 → 참고 → 사회적 요소(랭킹) 순이다.
- 모바일 전문가 보기의 검색 막대는 뺐다 — 머리 돋보기·'종목' 탭과 입구가 겹친다.
- 보기 전환은 '이 화면을 어떻게 볼지'라는 설정이라 맨 끝에 둔다. 위로 올리면 첫 화면의 3단계 안내가 밀린다.

| 계획 제안 상세 | 머리 배지 아래 이유 한 줄. 시작할 수 없으면 실행 확인 자리에 예산·체크·버튼 대신 사유와 "다른 계획 제안 보기". 지금 가격이 사는 가격 이하(정규장)면 "시작하면 모의 계좌에서 바로 사요". 시작 토스트는 결과대로(바로 샀으면 "n주를 X원에 샀어요"). 기한이 주말이면 "금요일 장 마감까지" |
| 내 자동매매 상세 | 산 뒤 가격 사다리의 기준점은 "산 가격"(체결가), 목표·손절 %도 산 가격 기준. 평가 "(수수료·세금 빼기 전)" + 한 줄 안내. "사는 가격을 기다리는 기한"은 사기 전에만. 보유 기한은 "11월 5일(목)까지 (최대 n거래일)". 멈춰서 판 결과는 "멈추기로 모의 계좌에서 … 팔았어요" |
| 모의투자 보유 | 오늘 산 종목은 '종가'·손익 줄 대신 "오늘 산 종목 · 장 마감(15:40) 뒤에 평가돼요". 평가 기준 문구 쉬운 보기 "평가는 지난 장 마감 가격으로 해요 (오늘 산 종목은 장 마감 뒤에)" |
| 마이·랭킹 | 알림 설정: 서버에 Discord가 없으면 "지금은 웹 알림으로만 와요." + 접힘 "Discord 알림 설정 (서버 설정 전)". 1분 진단 부제 "증권사의 공식 투자 성향 검사가 아니에요". 랭킹 각주 "— 오늘 산 종목은 장 마감 뒤까지 산 가격으로" |
