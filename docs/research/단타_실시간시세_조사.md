## 1. 한 줄 결론

**분봉·폴링 수준의 당일 청산 데이트레이딩(a)은 지금 구조로 가능하다.** 키움 WebSocket 체결(0B) 기반 초단기(b)는
공식 명세상 가능하지만, 실제 키로 확인하지 않은 항목(세션 1개/토큰, 200종목의 셈법, 재접속)과 약관 확인이 남아 **조건부**이고 발표(10/13) 뒤에 할 일이다.
호가 큐 위치까지 흉내 내는 스캘핑(c)은 개별 주문 단위 데이터가 없어 **어렵다**. LLM은 틱 판단에 못 쓰고, 장 전 계획·장 후 복기에만 쓴다.

## 3. 우리 구조에 붙이는 설계안 (설계 수준, 코드 없음)

### 3-1. 지금 구조 (출발점)

- 시세 = 폴링 (`docs/DECISIONS.md` 8-2): 웹이 현재가를 1초 캐시(`backend/trading/market.py`의 `trading:price:{symbol}`), 화면은 1초마다 받는다.
- `run_engine` 5초 루프(`--interval 5.0`): 체결·청산 확인, 예약, 일별 자산, AI 작업, 추천·자동매매, 알림.
- 체결 규칙(`engine/paper_engine/agents/executor.py`): 지정가는 확인 가격 ≤ 지정가면 그 확인 가격으로 체결, 처음 끝나는 정규장까지 안 되면 취소.
  목표·손절은 **2회 연속 확인**(`LOCAL_EXIT_CONFIRMATIONS = 2`) 뒤 확인 가격으로 전량 매도. 수수료 0.015%(`DEFAULT_COMMISSION`), 국내 매도 거래세 0.2%(`SELL_TAX_RATE["KR"]`), 손절 주문가 버퍼 1%(`STOP_LIMIT_BUFFER`).
- 키움 조회 한도 토큰당 초당 5회를 엔진·웹이 나눠 쓴다. 키움은 **아직 실제 키로 호출해 본 적이 없다** (`docs/KIWOOM.md` 머리말).

### 3-2. 실시간 수신 프로세스

```
키움 WS ──(0B·0D·0s·1h)──> [ticker 프로세스] ──> Redis (paper:*) ──> run_engine(틱 체결기) ──> DB(주문·체결)
                                 ▲   │                         └────> 웹 market.py (현재가 캐시 대체) ──> 화면
         paper:rt:want (원하는 구독) ┘   └─> paper:rt:status (생존 신호·마지막 수신 시각)
```

- **별도 프로세스·컨테이너** `ticker`(운영 `deploy/docker-compose.yml`에 서비스 하나 추가, 로컬은 `scripts/dev.sh`가 같이 띄움). 웹·엔진 루프와 생명주기를 분리해야 끊김·재접속이 다른 일을 멈추지 않는다.
- **의존성 위치**: 엔진은 표준 라이브러리만 쓴다는 규칙 때문에 WebSocket 통신(예: `websockets` 패키지)은 `backend/`에 둔다 (Django 관리 명령 `run_ticker` 형태).
  대신 **키움 FID → 내부(토스) 형식 변환은 규칙대로 `engine/paper_engine/data/kiwoom.py` 안의 순수 함수**(네트워크 없음)로 두고, 토스는 `data/toss.py`에 같은 이름·반환 형식의 함수를 둔다.
  `make_client` 단일 진입점·두 클라이언트 공개 메서드 동일 규칙을 실시간에도 적용한다 (예: `realtime_spec()` → 접속 주소·구독 메시지 생성, `decode_realtime(msg)` → 내부 틱 목록). 이름은 구현 시 확정.
- **토큰**: 키움은 "토큰별 세션 1개"[3]이고 토큰은 발급 IP에 묶인다(`8010`, `docs/KIWOOM.md` 7장). → 실시간 세션은 **한 서버의 한 프로세스만** 연다. 다른 프로세스(엔진 CLI 등)가 세션을 열면 안 된다.
  토큰 파일 캐시(`KIWOOM_TOKEN_CACHE`)는 REST와 공유하되, REST 쪽 재발급이 기존 토큰(=WS 세션)을 무효로 만드는지 모른다(`docs/KIWOOM.md` 8장 1번) → 재발급 시 WS 재로그인을 전제로 설계.

### 3-3. Redis 버퍼 (`paper:` 접두사만)

| 키 (제안) | 형식 | 내용 |
|---|---|---|
| `paper:tick:{symbol}` | Hash | 마지막 체결(가격·수량·부호·체결시간·최우선 매도/매수호가·수신 시각) — 웹 현재가 캐시가 먼저 읽는다 |
| `paper:book:{symbol}` | Hash | 마지막 10단계 호가 (0D 등록 종목만) |
| `paper:ticks:{symbol}:{YYYYMMDD}` | Stream (`XADD MAXLEN ~ N`) | 당일 체결 틱. 틱 체결기가 `XREAD`로 마지막 ID부터 읽는다. 장 마감 뒤 1분봉으로 접어 DB에 남기고 지운다 |
| `paper:rt:want` | Sorted Set (점수 = 우선순위) | 구독하고 싶은 종목. 웹·엔진이 쓰고 ticker가 읽어 등록·해지 |
| `paper:rt:view:{symbol}` | String + TTL | 화면에서 보고 있는 종목 임대(화면 폴링마다 TTL 연장) |
| `paper:rt:status` | Hash + TTL | 연결 여부, 마지막 수신 시각, 등록 수, 재접속 횟수 — 생존 신호 |
| `paper:rt:events` | Stream | 0s 장운영·1h VI 사건 |

원본 `toss_trading`의 `toss:*` 키는 쓰지 않는다. 데이터 양은 지어내지 않는다: **하루 메시지 수 ≈ 구독 종목들의 당일 체결 건수 합(0B) + 호가 변경 건수(0D)**. 첫 실측일에 `paper:rt:status`에 하루 메시지 수·바이트를 세어 MAXLEN과 보관 정책을 정한다.

### 3-4. 누구의 종목을 구독할지 (공식 200종목/세션 [3], 토스 100건/연결 [11])

우선순위 높은 순으로 채우고 남는 자리만 다음 순위에 준다. **200이 종목×항목이면(0B와 0D를 따로 센다면) 예산이 반으로 준다** → 모든 종목은 0B만, 0D는 1순위 종목만.

1. 당일 청산 모드의 **진행 중 주문·보유 종목** (체결·손절이 걸려 있음 — 빠지면 안 됨)
2. 활성화된 자동매매 계획(`backend/autotrade`)의 종목
3. 화면에서 지금 보고 있는 종목 (`paper:rt:view:*` 임대가 살아 있는 것)
4. 장 전 AI 관심 종목 목록
5. `0s`(장운영), `1h`(VI, 전체)는 `item=""`로 항상 등록

자리가 모자라 빠진 종목은 지금처럼 REST 폴링(1초 캐시·5초 루프)으로 처리한다 — **실시간은 "추가 경로"이고 폴링은 항상 남는 대체 경로**다.

### 3-5. 틱 기반 모의 체결 규칙 (제안)

| 상황 | 규칙 | 근거·비고 |
|---|---|---|
| 시장가 매수/매도 | 접수 시점 최우선 매도(매수)호가(0B `27`/`28` 또는 0D `41`/`51`)로 체결. 수량이 1단계 잔량보다 크면 0D 10단계를 따라 내려가며 가중평균(호가를 다 먹으면 나머지는 마지막 단계 가격 + 슬리피지) | 0D 없는 종목은 최우선호가 + 슬리피지 상수(호가 단위 n틱) |
| 지정가 매수 | 접수 뒤 **체결가 < 지정가인 틱**이 오면 지정가로 전량(또는 부분) 체결. 체결가 = 지정가인 틱만 오면 큐 앞 순서를 모르므로 (a)·(b) 단계에서는 **체결하지 않는 보수적 규칙** | 지금 규칙(확인 가격 ≤ 지정가 → 확인 가격으로 체결)보다 보수적. 틱이 지정가를 "뚫고 지나가야" 체결 |
| 부분 체결 | 한 틱에서 체결되는 수량 ≤ 그 틱의 거래량(0B `15`) × 참여율 상수. 나머지는 다음 틱으로 | 참여율 값은 설계 파라미터(출처 없음), 시연은 100%로 시작 가능 |
| 손절·목표 | 체결 틱이 손절가 이하(목표가 이상)가 되면 즉시 시장가 청산 규칙 적용. "2회 연속 확인"은 튀는 폴링 값 대비였으므로 틱 모드에서는 "틱 1개 + 최우선호가 확인"으로 바꾼다 | `LOCAL_EXIT_CONFIRMATIONS`는 스윙 모드에서 그대로 |
| VI·단일가 | `1h` 발동~해제 사이, `0s` 장시작 전·장마감 동시호가 구간에는 연속 체결 규칙을 멈추고 대기(또는 해제 직후 첫 체결가로 체결) | KRX 장 운영: 0s 코드 `2` 장마감 알림 15:20~, `4` 장마감 15:30 [1] |
| 상·하한가 | `0g` 상한가·하한가(FID 305/306)를 넘는 지정가는 거절 | |
| 비용 | 수수료·거래세는 지금 엔진 값(`DEFAULT_COMMISSION`, `SELL_TAX_RATE`)을 그대로 쓴다. 단타는 왕복 횟수가 많아 **비용이 손익을 크게 좌우**하므로 화면에 비용 합계를 따로 보인다 | 현행 거래세율 0.2%가 2026년 실제 세율과 맞는지는 별도 확인 필요 |
| 당일 청산 | 당일 청산 모드 주문은 장마감 동시호가 전(예: `0s`=`2` 15:20 알림 수신 시, 또는 그 전 설정 시각)에 남은 보유를 시장가로 강제 청산, 미체결 지정가 취소. 실시간이 죽어 있으면 REST 확인 가격으로 같은 일을 한다 | 시각은 설정값. 동시호가 참여(종가 체결) 방식은 후속 선택지 |
| NXT | 1차는 **KRX만**(`item`에 접미사 없음)으로 지금 체결 규칙·장 달력과 맞춘다. NXT 프리·애프터는 후속 | 지금 엔진은 KRX 코드만 쓴다 (`docs/KIWOOM.md` 1장) |

### 3-6. 지금 5초 루프·1초 캐시와의 관계

- **웹 현재가**: `market.py`가 `paper:tick:{symbol}`의 수신 시각이 몇 초 안이면 그것을 쓰고, 아니면 지금처럼 REST(1초 캐시). → 화면이 많아도 REST 호출이 줄어 초당 5회 예산이 남는다 (8-2의 "묶음이 늘면 한도에 가까워진다" 문제 완화).
- **체결 확인**: 스윙 주문은 지금 5초 루프 그대로. 당일 청산 주문은 `run_engine` 안의 짧은 주기(또는 `XREAD BLOCK`) 틱 체결기가 처리한다.
  **DB에 주문을 쓰는 프로세스는 계속 `run_engine` 하나**로 둔다 (`select_for_update`·`trading.service` 경로 유지, 엔진 루프 하나 전제 8-6). ticker는 Redis에 쓰기만 한다.
- 화면 갱신은 지금 폴링(1초)으로도 충분하다. 틱을 화면에 흘리려면 SSE가 이미 `backend/reports`에 있으므로 같은 방식으로 붙일 수 있다 (후속).

### 3-7. 장애(끊김) 시 복구 — AutoHealing과의 연결

| 장애 | 감지 | 복구 | 최종 실패 시 |
|---|---|---|---|
| 연결 끊김 | 수신 루프 종료·예외 | 지수 백오프로 재접속 → LOGIN → `paper:rt:want`로 REG 재등록 | 시도 수 상한 넘으면 "실시간 꺼짐" 상태 → 폴링만으로 동작 + 담당자 알림 (`notifications.service.notify`) |
| 조용한 끊김 (연결은 살았는데 데이터가 안 옴) | 장중(`0s`로 판단)인데 거래 많은 구독 종목의 마지막 수신이 N초 넘음 | 강제 재접속 | 위와 같음 |
| 로그인 실패 (토큰) | LOGIN 응답 `return_code≠0`, `8005` 등 | 토큰 캐시 재확인 → 재발급 1회 (공식 클라이언트와 같은 방식 [1]) | 알림 |
| 등록 거절 (한도) | REG 응답 `return_code=1`, `1702` | 우선순위 낮은 종목부터 빼고 다시 등록 | 빠진 종목은 폴링 |
| 끊긴 구간 | 재접속 시 마지막 틱 시각과 현재 시각 차 | **진행 중 주문이 있는 종목만** `ka10084`(시각 지정) 또는 `ka10079`로 구간을 메워 체결 판정을 다시 돌림. 메우지 못한 구간은 체결하지 않음(보수적) | 사용자 화면에 "시세 지연 구간" 표시 |
| 토스(개발) 서버 배포 | `server-shutdown` 프레임 [11] | 재연결·재선언 | — |

- 지금 AutoHealing 과제(`docs/tasks/04-autohealing.md`)는 **LLM 호출 장애만** 다룬다 ("복구 로직은 리포트 워크플로우에만 해당"). 실시간 시세 끊김은 새 장애 유형(예: DR-FEED-01 끊김, 02 조용한 끊김, 03 토큰 무효)으로 **같은 틀(감지 → 재시도 → 대체 경로 → Circuit Breaker → 알림, 장애 주입·복구 지표)을 재사용**할 수 있다.
  대체 경로가 "REST 폴링"으로 분명하다는 점이 장애 복구 시연에 좋다. 단, 발표 전 일정에는 넣지 않는 것을 권한다 (4장).

## 4. 단계별 판정과 작업 목록

### (a) 분봉·폴링 수준의 "데이트레이딩(당일 청산)" — **가능**

- 근거: 지금 1초 현재가 캐시·5초 루프·지정가 당일 유효 규칙이 이미 있고, 분봉은 키움 `ka10080`(1·3·5…60분, `base_dt`) [1]·토스 `candles?interval=1m`(최대 200봉) [13]로 받을 수 있다. 새 연결·새 의존성이 필요 없다.
- 작업:
  1. 주문·계획에 "당일 청산" 표시 (모델 열 + `docs/API.md` 먼저 고침)
  2. 장 마감 전 강제 청산·미체결 취소 (`run_engine`, 시각 설정값)
  3. 분봉 차트 API·화면 (`lightweight-charts`가 이미 있음), 분봉용 엔진 메서드(`KiwoomClient`·`TossClient` 같은 이름) + 가짜 클라이언트 테스트
  4. 단타용 리스크 파라미터(손절 폭·하루 최대 손실·하루 최대 거래 수) — 리스크 엔진이 정한다
  5. 비용(수수료·세금) 합계 표시
- 위험: 5초 루프 + 2회 연속 확인이라 손절이 늦게(최대 10초 이상) 잡힌다 → 시연 문구로 "분 단위 데이트레이딩"이라고 정확히 말해야 한다. 초당 5회 예산을 분봉 조회가 나눠 쓴다(종목당 1분 캐시 필요).
- 일정: 기술적으로는 발표 전 가능한 크기지만, 팀 일정(10/5~10/9 AutoHealing·리포트, 10/12 리허설, `TEAM_DEV_PLAN.md`)과 겹친다. **발표 전에는 하지 않거나 1~3번만** 하는 것을 권한다. 평가 주제가 AutoHealing이기 때문이다.

### (b) WebSocket 체결 기반 "초단기" — **조건부**

- 근거: 키움 명세에 0B·0D·0s·1h, 등록·해지·PING 규칙이 공식으로 있고 [1], 세션당 200종목 [3]은 팀 5명 규모에 충분해 보인다. 개발은 토스 WS(100건/연결, 2연결) [11]로 같은 설계를 먼저 돌려 볼 수 있다.
- 조건(모두 5장 실측 뒤): 200의 셈법, 토큰당 세션 1개와 REST 재발급의 상호작용, 재접속 동작, NXT 수신 여부, 약관상 팀 웹 표시 가능 여부. **키움 키 자체가 아직 한 번도 실측되지 않았다**는 점이 가장 큰 위험이다.
- 작업:
  1. `docs/DECISIONS.md`에 실시간 결정 장 추가(8-2 "실시간 = 폴링" 개정, 토스 WS 예외 3-1, 구독 우선순위, 체결 규칙), `docs/API.md`
  2. `data/kiwoom.py`·`data/toss.py` 실시간 변환 순수 함수 + 녹화한 틱으로 테스트 (외부 호출 없음)
  3. `backend`의 `run_ticker` 관리 명령 + 운영 compose 서비스 + `scripts/dev.sh` + CI·`.env.docker.example` 설정 키
  4. Redis 키(3-3), 구독 관리자(3-4)
  5. 틱 체결기(3-5)를 `run_engine`에 — 스윙 경로와 분리, 기존 executor 규칙은 고치지 않고 새 모드로
  6. 복구(3-7) + 장애 주입 시나리오 + 지표
  7. 화면: 실시간 상태 표시, 시세 지연 구간 표시
- 위험: 연결 장애가 체결 결과를 바꾼다(끊긴 구간 처리 규칙을 정직하게 보여야 함), LOSSY 시세(토스 명시 [11], 키움은 명시 없음), 운영 서버 IP·토큰 1세션 제약, 약관.
- 일정: **발표 뒤.** 실측 하루 + 구현·테스트 1~2주 규모로 추정(추정치).

### (c) 호가·큐 위치까지 흉내 내는 "스캘핑" — **어려움**

- 근거: 0D는 호가 단계별 **잔량 합계** 스냅숏이고 개별 주문(큐 순서)·취소 흐름이 없다 [1]. 큐 위치는 "내 주문 앞 잔량 − 그 가격의 체결량 − 추정 취소량"으로 근사할 수밖에 없고 취소량은 알 수 없다.
  시세 프레임 유실 가능성(토스 LOSSY [11]), 우리 서버까지의 지연, 0B+0D를 모두 받으면 등록 예산이 줄어드는 문제가 겹친다.
  모의 결과가 현실과 크게 달라질 수 있어(유리한 체결 착시) 교육·시연 가치가 낮다.
- 작업(한다면): (b) 전부 + 큐 근사 모델 + 지연·유실 보정 + 실제 체결과 비교 검증 데이터. 검증할 실계좌 데이터가 없다(실주문 0건 규칙).
- 판정: 과제 범위에서 **하지 않는 것을 권한다.**

## 5. 확인 필요 항목 (실제 키로 다시 볼 것)

키를 받으면 `scripts/kiwoom_check.py`(REST 읽기 전용)와 같은 원칙(키·토큰 출력 금지, 계좌 실시간 `00`·`04` 등록 금지)으로 실시간 점검 스크립트를 따로 만들어 본다.

1. **200종목의 셈법**: 종목 수인가, 종목×항목(0B, 0D 각각) 수인가. 201번째 등록 시 응답(`return_code`, `1702` 여부).
2. **토큰당 세션 1개**: 두 번째 세션을 열면 첫 세션이 끊기는가, 두 번째가 거절되는가. REST 호출과 WS 세션이 같은 토큰으로 공존하는가. REST 쪽 토큰 재발급이 WS 세션을 끊는가.
3. 서버 `PING` 주기, 무응답 시 끊기는 시간, 장 마감 뒤·주말에 세션이 유지되는가.
4. `grp_no`를 여러 개 쓰면 등록 한도가 늘어나는가(아니라고 추정).
5. `0B` 수신 빈도: 체결 1건당 1메시지인지 묶여 오는지, 하루 메시지 수·바이트(데이터 양 산정).
6. NXT: `_NX`·`_AL` 등록 시 프리(08:00~08:50)·애프터(15:30~20:00) 체결이 오는지, KRX 코드만 등록하면 NXT 체결은 빠지는지 (0B `9081` 거래소구분 값).
7. `1h` VI를 `item=""`로 등록하면 전 종목 VI가 오는지, 등록 한도에 세는지.
8. `ka10079` 한 쪽 행 수(블로그 900)와 조회 가능한 과거 범위(당일만?), `ka10084`로 몇 분 전까지 메울 수 있는지, `ka10080` `base_dt`로 며칠 전까지 되는지.
9. 키움 「오픈 API 서비스 이용 약관」 원문에서 시세 이용 범위·제3자 제공 조항 (현재 폴링 서비스에도 해당). 토스 Open API 약관의 같은 조항.
10. KIS·LS 공식 포털의 실시간 등록 한도(대안 검토 시에만).
11. 현행 국내 증권거래세율이 엔진 값 0.2%와 맞는지.

## 부록. AI의 역할 (조사 항목 7)

- **LLM은 틱 판단에 못 쓴다.** 근거: 지금 AI 리포트는 멀티 Agent로 한 건에 수 분이 걸리고(과제 배경), 한 종목 분석 비용이 약 $0.3(`AGENTS.md` 엔진 CLI 설명)이며, 팀 전체 하루 분석 한도가 `AI_DAILY_BUDGET_USD ÷ 0.3`(기본 33회, `DECISIONS.md` 8-4)이다.
  틱은 초 단위로 오고 판단도 초 단위여야 한다. 또 "AI는 제안만, 수량·한도·체결은 결정론적 코드" 규칙(`AGENTS.md`)상 장중 판단은 원래 규칙 엔진 몫이다.
- 현실적인 역할 분담:

| 시간 | 누가 | 무엇을 |
|---|---|---|
| 장 전 (08:00~09:00) | **AI** | 관심 종목 5~10개와 종목별 계획: 진입 가격대·조건(예: 전일 고가 돌파, VWAP 회복), 무효화 가격, 목표 구간, "오늘 하지 말 것". 지금 리포트·추천 흐름(AI 추천 → 계획 활성화)을 "당일 계획"으로 쓴다 |
| 장 전 | **리스크 엔진** | 계획마다 수량·하루 최대 손실·최대 거래 수를 확정. 최소 손익비 등은 AI에 노출하지 않음 (기존 규칙) |
| 장중 | **결정론적 규칙 + 틱/분봉 체결기** | 계획의 조건이 틱·분봉에서 충족되면 모의 주문, 손절·목표·당일 청산 집행. VI·장운영 사건 반영. AI 호출 없음 |
| 장중 (선택) | AI (비동기) | 큰 사건(VI 발동, 하루 손실 한도 근접) 때 사람에게 보내는 **설명 문장**만 — 판단·주문에 끼지 않음 |
| 장 후 | **AI** | 복기 리포트: 계획 대비 실제 체결, 규칙 위반·놓친 기회, 비용(수수료·세금) 영향, 다음 날 계획 수정 제안. 사실(체결·손익)은 DB 값을 그대로 쓰고 AI는 해석만 |

- 이 분담은 서비스 컨셉(초보자도 리포트를 만들고·검토하고·실행하는 AI 매매 서비스, 최근 커밋 `47c6492`)과도 맞는다: AI는 "계획과 복기", 실행은 규칙.
