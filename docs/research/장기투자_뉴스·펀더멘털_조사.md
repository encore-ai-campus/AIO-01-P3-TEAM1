## 1. 한 줄 결론

**둘 다 국내 종목 기준으로 지금 자료로 거의 다 만들 수 있다.** 빠진 것은 ① 지수·업종 시세 TR 2개(키움에 있음, 아직 안 씀),
② 종목→업종 연결(`ka10100.upName`, 받지만 버림), ③ 영업현금흐름(DART에서 이미 받는 응답 안에 있는데 안 꺼냄) 정도다. 가장 큰 위험은
**뉴스 출처의 이용 조건**이다. 저장소가 쓰는 Google 뉴스 RSS는 피드 안에 "개인 피드 리더에서 개인·비상업 용도로만, 그 밖의 이용은 금지"라고 적혀 있다.
다른 위험은 인과 단정과 투자 권유로 오해받는 것이다. 그래서 등락은 숫자로 먼저 나누고(결정론), LLM은 근거 목록 안에서 "관련 있을 수 있는 소식"만 말하게 한다.
펀더멘털 점검은 회사 자신의 매수 시점 값과 비교하는 규칙(✓·△·✗)을 기본으로 한다. 장기 보유는 지금도 웹 수동 매수(목표·손절·기한 없이)로 할 수 있다.
다만 AI 추천·자동매매·리스크 엔진은 스윙(3~20거래일)에만 맞춰져 있으므로, 장기 보유는 **자동 청산 없는 별도 보유 방식**으로 나누는 것이 맞다.

```
장 마감(15:30) ─▶ 16:30 KST, 거래일만 (data/calendar.py)
  ① 대상: 모든 팀원 계좌의 보유 종목(EXIT_WATCHING) 합집합 → 종목별로 1번만
  ② 숫자 분해 (결정론, LLM 없음) ── 종목별 캐시 DailyMoveNote(symbol, day) 유일
  ③ 근거 목록 모으기 (공시·뉴스 제목·증권사 헤드라인·수급) → guards.clean_text
  ④ 설명 필요 여부 판단 (결정론) ─ 아니면 템플릿 문장, LLM 호출 없음
  ⑤ LLM 1회 (근거 안에서만) → 출력 계약 검증 + 문장 규칙 검사
  ⑥ 사용자별 묶음 알림 1개 (웹 + Discord): "오늘 내 종목 3개: …"
```

### 4-2. 등락 분해 (숫자 먼저, 결정론)

| 성분 | 계산 | 자료 |
|---|---|---|
| 종목 등락 `r` | 오늘 종가 ÷ 전일 종가 − 1 | `ka10081` 일봉 (이미 사용) |
| 시장 `r_m` | 코스피 종목은 `001`, 코스닥 종목은 `101` 지수 등락률 | `ka20001`(당일 `flu_rt`) 또는 `ka20006`(일봉) — **새로 붙임**. 임시 대안: 코스피는 KODEX 200(`069500`) 기록값, 코스닥은 없음 |
| 업종 `r_s` | 종목 `upName` → `ka10101` 업종명 → 업종코드 → 업종 등락률 | `ka10100`/`ka10099`의 `upName`(받지만 버리고 있음) + `ka10101` + `ka20001` — **새로 붙임**. 매칭 실패면 업종 성분 생략 |
| 시장 몫 | v1: `r_m` 그대로 (β=1 가정). v2: 최근 120거래일 일봉으로 β 추정 후 `β × r_m` | 종목·지수 일봉 |
| 업종 몫 | `r_s − r_m` (업종이 시장보다 더/덜 움직인 만큼) | |
| 종목 고유 몫 | `r − 시장 몫 − 업종 몫` | |
| 수급 | 개인·외국인·기관 순매수 수량 ÷ 그날 거래량 (%), 최근 20일 같은 비율과 비교 | `ka10059` (이미 사용) |
| 거래량 | 그날 거래량 ÷ 20일 평균 | 일봉 |

- 초보자 화면은 **세 숫자**만 보여 준다: "코스피 −1.2% · 반도체 업종 −2.0% · 삼성전자 −2.4% → 시장·업종을 빼면 −0.4%(종목 고유)".
- β는 추정 오차가 커서(특히 상장 짧은 종목) v1은 β=1로 하고 "시장 대비 초과 등락"이라고만 부르는 것을 권한다.
- 분해는 **회계식 분해이지 인과가 아니다.** 화면 문구도 "시장이 이만큼, 업종이 이만큼 같이 움직였다"로 쓴다.

### 4-3. 근거 목록 (LLM에 넘기는 것)

각 항목에 ID(`E1`, `E2` …)를 붙인다. LLM은 이 ID로만 말한다.

| 종류 | 자료 | 신뢰 | 비고 |
|---|---|---|---|
| 공시 | DART `list.json` (종목, 그날) — 제목·시각 | 높음 (사실) | 제목 키워드로 종류 분류(실적·잠정실적, 유상증자, 자기주식, 단일판매·공급계약, 최대주주 변경 등)는 코드로 |
| 수급 | 4-2의 숫자 | 높음 (숫자) | "외국인이 거래량의 12%를 순매수" 같은 문장 재료 |
| 증권사 헤드라인 | `stock_reports(days=1)` | 중간 (제목 파싱) | 목표가 상향·하향 |
| 뉴스 제목 | `fetch_news(days=1, limit=15)` | 낮음~중간 | 같은 이름의 다른 회사 기사가 섞인다 → 제목에 종목명이 정확히 있는 것만 |
| 시장·업종 | 4-2의 숫자 + 상승·하락 종목 수(`ka20001`) | 높음 | "오늘 코스피 하락 종목이 상승의 3배" |

### 4-4. 설명이 필요한지 (LLM 비용을 줄이는 결정론 규칙)

- **LLM 생략**: 종목 고유 몫이 작고(제안: |고유 몫|이 1%p 미만이면서 그 종목의 20일 일간 변동성(`volatility20`)보다도 작을 때 — 값은 팀이 정한다) 그날 공시·헤드라인이 없으면
  → 템플릿 "오늘은 시장·업종과 비슷하게 움직였습니다 (코스피 −1.2%, 업종 −2.0%, 내 종목 −2.4%)."
- **LLM 호출**: 고유 몫이 크거나, 그날 공시가 있거나, 수급 비율이 평소보다 크게 튀었을 때.
- 이 규칙만으로 많은 날·종목이 LLM 없이 끝난다 (비율은 실측 필요).

### 4-5. LLM 출력 계약과 문장 규칙

출력 계약(가칭 `DailyMoveResult`, 리포트 `contracts.py` 형식에 맞춤):

```
headline: str (60자)              "시장 하락과 함께 내렸고, 같은 날 실적 공시가 있었습니다"
summary: str (300자)
drivers: [ {kind: "market"|"sector"|"stock"|"flow", text: str(120자), evidence: ["E1", ...]} ] (4)
uncertain: bool                    근거가 약하면 true → 화면에 "뚜렷한 소식을 찾지 못했습니다"
```

결정론 검사 (리포트의 `fact_check`처럼, 위반이면 1번 다시 요청 → 또 위반이면 템플릿으로 대체):
1. `evidence`의 ID가 모두 근거 목록에 있다. `market`·`sector`가 아닌 driver는 근거가 최소 1개.
2. 문장에 나온 숫자(%, 원)가 넘겨준 숫자와 일치 (반올림 허용).
3. **금지 표현**: 인과 단정("때문에", "덕분에", "원인은", "~로 인해 급등") → 허용 표현은 "같은 날 ~이 있었습니다", "관련 있을 수 있는 소식".
   투자 권유("사세요", "팔아야", "매수 기회", "추가 매수", "목표가 도달 예상") → 금지. 이 목록은 프롬프트와 검사에 둘 다 둔다.
4. 근거가 뉴스 제목뿐이면 `uncertain=true`를 강제한다.

화면 고정 문구: "등락의 원인을 단정하지 않습니다. 같은 날 나온 소식을 모은 것이며 투자 권유가 아닙니다."

### 4-6. 실행 시각·캐시·비용

- **시각**: 16:30 KST 거래일 1회 (`calendar.py`의 정규장 끝 15:30 이후). `ka10059`의 당일 수급이 이 시각에 확정 값인지는 **확인 필요** (8장).
  저장소의 `run_engine` 루프에 "오늘 아직 안 만들었으면 만든다" 단계 하나를 더하는 방식(자동 추천 `auto.tick`과 같은 모양)이 맞다.
- **종목별 캐시**: `DailyMoveNote(symbol, day)` 유일 제약. 여러 사람이 같은 종목을 가져도 한 번만 만들고, 사용자 알림은 이 행을 참조만 한다.
  엔진이 다시 떠도 이미 만든 (symbol, day)는 건너뛴다. 실패는 `status=failed`로 남기고 다음 tick에서 1번만 다시.
- **조회 비용**: 종목당 키움 일봉 1 + 수급 1 (+ 업종·지수는 하루 1번씩 공유), DART 공시 목록 1, 뉴스 RSS 1~2. 키움 초당 5회 한도 안에서 종목 수십 개는 수십 초.
- **LLM 비용**: 종목당 최대 1회. `LlmClient.cost`의 호출 전후 차이를 `DailyMoveNote.cost_usd`에 남긴다 (분석의 `AnalysisRun.cost_usd`와 같은 방식).
  금액은 요금표가 저장소에 없어 **첫 주 실측으로 정한다**. 참고로 저장소의 다중 모델 교차검증 분석은 "종목당 AI 비용 약 $0.3"(`daily.py` 주석)인데,
  이 기능은 짧은 입력·출력에 빠른 모델 1번이라 그보다 훨씬 작을 것으로 **예상만** 한다. 하루 상한(종목 수 `MAX`, 금액 `BUDGET`)을 설정 키로 둔다.
  **(2026-10-04 추정)** 공개 가격표와 프롬프트 길이로 어림하면 1회 약 $0.002~0.04(중간 가정: 입력 3천·출력 1.2천 토큰 — 빠른 모델 $0.002~0.018, Opus급 $0.036)라 $0.3보다 1~2자리 작다. 근거·계산은 8장 9번. 게이트웨이 청구액(`usage.cost`)은 공개가와 다를 수 있어 첫 주 실측은 그대로 필요하다.
- **알림**: 사용자당 하루 1개로 묶는다 (종목마다 보내지 않는다). 새 `NotificationKind` `"daily_move"`(docs/API.md 먼저 수정).
  Discord는 기존 보낼 편지함으로. 등락이 큰 종목(예: |r| ≥ 5%, 팀 결정)만 제목에 올린다.

### 4-7. 리포트 Agent 워크플로우 재사용 vs 가벼운 단일 Agent

| 기준 | 리포트 워크플로우 재사용 (`00-공통.md`: 조사 Worker 3개 → report → review → risk Handoff) | 가벼운 단일 Agent (권장) |
|---|---|---|
| LLM 호출 | 종목당 최소 5번 (market·fundamental·news·report·review, risk는 선택) | 종목당 0~1번 |
| 실행 방식 | `runner`가 **동시에 1개만** (`MAX_CONCURRENT = 1`) — 보유 종목 수십 개를 장 마감 뒤에 돌리기엔 느리다 | 종목별 순차/소수 병렬, 실패는 템플릿으로 |
| 맞는 질문 | "이 종목을 살까?" (깊은 분석, 매수 판단) | "오늘 왜 움직였지?" (짧은 사실 요약) |
| 재사용할 부품 | — | `healing.LlmCaller`(재시도·대체 모델), `contracts.validate`, `guards.clean_text`, Trace 대신 `DailyMoveNote`에 모델·비용·시도 수 |
| 결합 | 2·3·4 담당 작업(10/5~)이 끝나야 쓸 수 있다 | 그 부품이 없으면 `LlmClient.complete_json`으로 먼저, 나중에 호출기만 바꾼다 |

**권장: 단일 Agent.** 부품(호출기·계약 검증·입력 Guard)만 리포트 쪽 것을 쓰고, Orchestrator·Join·Review·Handoff는 쓰지 않는다.
"이 종목 더 깊게 보기" 버튼으로 기존 리포트 신청(`POST /api/reports`)을 이어 주면 두 기능이 자연스럽게 나뉜다.

## 5. 펀더멘털 점검 — 설계 (코드 없음)

### 5-1. 지표와 규칙 (저장소 자료로 계산 가능한 것만)

원칙: **절대 기준보다 "산 때와 비교한 변화"를 먼저 본다.** 업종마다 정상 범위가 너무 달라서(예: 영업이익률, 부채비율) 절대 기준은 최소한만 둔다.
아래 기준값은 출처가 있는 한계기업 기준을 빼면 **팀이 정할 제안값**이다 (근거 = 이유 설명, 숫자의 공식 출처 아님).

| 지표 | 계산 (자료) | ✓ | △ | ✗ | 이유·한계 |
|---|---|---|---|---|---|
| 매출 성장 | 최신 보고서 누적 매출의 전년 같은 기간 대비 (`interimRevenueGrowth`, 없으면 `annualRevenueGrowth`) + 5년 추이 (`annualHistory`) | ≥ 0% | −10% ~ 0% | < −10% 또는 2개 보고서 연속 감소 | 성장주 논리였다면 핵심. 계절성은 누적·전년 동기 비교로 줄였다 |
| 영업이익 성장 | `interimOperatingIncomeGrowth` / `annualOperatingIncomeGrowth` | ≥ 0% | −20% ~ 0% | < −20% 또는 **적자 전환** | 전기가 0 이하면 증가율 없음(`_growth`) → 흑자·적자 전환으로 판정 |
| 영업이익률 (TTM) | `ratios.operatingMargin`, 기준선 = 매수 시점 값 | 기준선 −1%p 이내 | −1 ~ −3%p | −3%p 넘게 하락 또는 음수 | 업종 차이가 커서 **자기 기준선 대비 변화만** 본다 |
| ROE | DART 공시 `reported.roe` (M210000) | 기준선 −2%p 이내이고 > 0 | 하락 폭 더 큼 | ≤ 0 | 2023년 3분기 이후만 제공 [S4]. 분기 보고서 값은 누적 기준이고 연환산이 아니다 (`annualized: False`) — 연간과 섞어 비교하지 않는다 |
| 부채비율 | DART `reported.debtRatio` + 5년 `annualHistory[].debtRatio` | 기준선 대비 +20%p 이내 | +20 ~ +50%p | +50%p 넘게 증가 | 금융업(은행·보험·증권)은 구조상 높다 → **금융업은 이 지표 제외** |
| 유동비율 | DART `reported.currentRatio` | ≥ 100% | 80 ~ 100% | < 80% | 업종 차이 있음 — 보조 지표로만 |
| 이자보상배율 | 영업이익 ÷ **금융비용**(`nonOperating.financeCosts`) — 근사 | ≥ 3 | 1 ~ 3 | < 1 (그리고 3년 연속이면 "한계기업 기준 해당" 문구) | 한계기업 = 3년 연속 1 미만 [S13]. 금융비용은 이자비용보다 넓어(외환손실 등 포함 가능) **배율을 낮게 본다** → 표시는 "근사"로. 정확한 이자비용 계정은 확인 필요. **(2026-10-04 확인: 확인한 13개 회사의 손익계산서·포괄손익계산서에는 `ifrs-full_InterestExpense`가 없고(0곳) `ifrs-full_FinanceCosts`(금융비용·금융원가)만 있다. 이자지급은 현금흐름표에 `InterestPaid…` 태그로 있으나 영업활동·재무활동 분류가 회사마다 갈린다 — 8장 7번 [S14])** |
| 이익의 질 | 순이익÷영업이익 (`netIncomeToOperatingIncome`), 영업외 손익 비중 (`nonOperatingShareOfPretaxIncome`) | — | 영업외 비중이 커서 순이익이 영업이익과 크게 다름 | — | 경고만 (△). 일회성 이익을 성장으로 착각하지 않게 |
| 영업현금흐름 | 현금흐름표 영업활동현금흐름 (`fnlttSinglAcntAll`의 `sj_div=CF`) | > 0 이고 순이익과 같은 부호 | 순이익은 흑자인데 OCF가 적자 (1회) | 2회 연속 | **지금 꺼내지 않는다** — 이미 받는 응답에서 파싱만 더하면 된다 (작업 S). data.go.kr에는 현금흐름표가 없다 [S12]. **(2026-10-04 확인: 확인한 13개 회사 모두 현금흐름표(`sj_div=CF`)에 표준 ID `ifrs-full_CashFlowsFromUsedInOperatingActivities`로 온다 — 8장 7번 [S14])** |
| 목표가 방향 (보조) | 증권사 헤드라인 최근 30일 하향 건수 | — | 하향 2건 이상 | — | 제목 파싱 자료라 ✗로 쓰지 않는다 |

종합 표시: ✗ 하나라도 → "점검 필요", △ 2개 이상 → "주의", 나머지 → "견조". 금융업·ETF·리츠는 "이 점검은 일반 기업용이라 적용하지 않습니다" (업종은 `upName`, 유형은 `securityType`).

### 5-2. "산 이유(투자 논리)"를 저장하고 대조하는 방식

새 모델 `InvestmentThesis` (가칭, 계좌·종목별 1개, 매수 시점에 만든다):

| 필드 | 내용 | 어디서 |
|---|---|---|
| `source` | `report` / `recommendation` / `manual` | |
| `reasons` | 산 이유 문장 (최대 3) | 리포트 `ReportDraft.reasons`, 추천 `Recommendation.reasons`, 수동 매수는 체크박스(성장 / 수익성 / 재무 안정 / 기타 한 줄) |
| `pillars` | 점검할 축 — 예: `["growth", "profitability", "balance_sheet"]` | 리포트 `FundamentalResult.metrics`가 좋았던 항목 또는 사용자가 고른 체크박스 → 5-1의 지표로 연결 |
| `baseline` | 매수 시점 펀더멘털 스냅샷: 보고서 기간(`reported.period`), TTM 영업이익률, ROE, 부채비율, 매출·영업이익 성장률, OCF | `dart.fundamentals(...)` 결과를 그대로 (JSON) |
| `checks` | 점검 기록 [{at, period, items: {지표: ✓/△/✗, 값, 기준선}, summary}] | 점검 때마다 추가 |

- 대조는 **결정론**이다: 새 보고서 값 vs `baseline` → 5-1 규칙. "산 이유" 축에 걸린 지표의 ✗는 제목에 올린다 ("성장 논리 점검 필요: 영업이익 −35%").
- LLM은 선택: 결과를 쉬운 말 2~3줄로 바꿀 때만 (근거 = 지표 표, 4-5와 같은 금지 표현). 정기공시 때만 부르므로 종목당 1년 4번 수준.
- 리포트·추천에서 산 경우가 아니면 이유가 없다 → 수동 매수 화면에 "왜 샀나요?" 체크박스를 두고, 비워 두면 3축 모두 점검한다.

## 6. 장기투자와 지금 구조의 충돌, 해결안

| 지금 구조 | 장기 보유와 맞나 | 근거 (코드) |
|---|---|---|
| AI 추천은 **스윙만**: `TRADABLE_HORIZONS = ("SWING",)`, 보유 3~20거래일. 사실 검증이 `LONG_TERM`을 거른다. 제안 프롬프트도 SWING만 | ✗ | `judge/scenario.py`, `judge/fact_check.py`, `agents/proposer.py` |
| 리스크 엔진 `LIMITS["LONG_TERM"]` (건당 위험 2%, 최소 손익비 2.5, 일일 손실 3%)은 **형식만 남아 있다** ("이전 기록과 리스크 한도 때문에 남겨 둔다"). 손절가 기준 수량 계산이라 손절 없는 장기 보유엔 맞지 않는다 | △ | `judge/risk.py`, `scenario.py` 주석 |
| 자동매매 계획은 `horizon="SWING"` 고정 (2026-10-06 단타 폐기로 `horizon` 필드를 지웠다 — 계획은 늘 스윙), `Recommendation.holding_days` 1~20, 주문 기한 = `min(MAX_MANAGED_DAYS, ceil(보유일×7/5))` | ✗ (장기용 아님) | `backend/autotrade/plans/risk.py`, `executor.order_days` |
| `MAX_MANAGED_DAYS = 180`: 기한을 **줄 때만** 1~180일. 기한이 지나면 `EXPIRED`로 자동 청산 | 기한을 안 주면 문제없음 | `paper_engine/trading.py`, `agents/executor.py` |
| 엔진 CLI는 목표·손절을 주고 기한을 안 주면 `DEFAULT_MANAGED_DAYS = 30` | 장기엔 ✗ (CLI만) | `paper_engine/trading.py` |
| **웹 수동 매수는 목표·손절·기한 모두 선택**: 안 주면 자동 청산·만료 없이 보유 (`expire=None`) | ✓ 지금도 장기 보유 가능 | `backend/trading/service.buy`, `_expire` |
| 목표·손절 자동 청산 | 장기 논리와 충돌 — 가격 변동으로 손절되면 "펀더멘털이 견조한데 팔림" | `agents/executor.py` |

**해결안**

1. **보유 방식을 둘로 나눈다**: `스윙 계획`(지금 그대로: AI 추천 → 계획 → 목표·손절·기한 자동 청산) / `장기 보유`(목표·손절·기한 없음, 매도는 사용자만).
   `PaperOrder`(또는 포지션)에 `style: "swing" | "long"` 열을 두거나, 1차는 "목표가가 없으면 장기 보유"로 **유도**만 한다 (마이그레이션 없이 시작).
2. **장기 보유에는 자동 매도를 붙이지 않는다.** 펀더멘털 ✗도 알림만 (AI는 제안만 — AGENTS.md 안전 규칙과 같다).
3. **장기 보유의 수량 판단**은 손절 기반 리스크 엔진 대신 비중 한도로: `RiskLimits.max_position`이 이미 있으니 장기 매수 미리 보기에서 "계좌의 X% 이하"만 점검 (X는 팀 결정).
   `LONG_TERM` 손익비 2.5 규칙은 장기 보유에 쓰지 않는다 (목표가가 없다).
4. **AI 추천을 장기로 넓히지 않는다** (1차). 장기 "추천"은 투자 권유 오해가 가장 큰 영역이다. 대신 장기 보유자에게는 "매일 설명(4장) + 분기 점검(5장)"을 준다.
5. 두 기능의 대상: 오늘의 내 종목 뉴스 = **모든 보유 종목**(스윙 포함), 펀더멘털 점검 = **장기 보유 + 국내 일반 기업**만.
