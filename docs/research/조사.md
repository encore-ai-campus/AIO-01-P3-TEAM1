### A1. 한 장 요약

**결론 먼저**
1. **네이버 검색 API는 대안이 못 된다.** 2026-09-07 개정 검색 API 특약 2.3이 "데이터를 AI에 입력하거나 학습, 개선, 평가 및 노출 등에 활용하는 행위"를 금지한다. 2.2는 "가공 없이" 노출을 요구한다. 게다가 개발자센터의 검색 API **신규 신청은 2026-07-30 24:00에 중단**됐다(NAVER API HUB로 이관).
2. **키움 약관 원문을 찾았다.** 「오픈 API 서비스 이용약관」 제5조 ③: 시세 정보는 "개인의 업무에 한하여 이용해야 하며, 제3자에게 제공해서는 아니 된다". 팀 웹에서 다른 사람에게 시세를 보여 주는 지금 방식은 문언상 범위 밖이다.
3. **토스** 공식 FAQ "데이터 이용 정책": "비상업적인 용도라 하더라도 제 3자에게 배포하는 행위는 엄격히 금지".
4. **Google 뉴스 RSS**는 "개인 피드 리더에서 개인·비상업 용도로 결과를 보여 주는 것"만 허용한다. 여러 사람이 쓰는 서비스, LLM 입력, 제목 파싱은 모두 밖이다.
5. **OpenDART·공공데이터포털(재무·특일)은 허용**이다.
6. **저작권 위험은 낮다** — 교육용이라서가 아니라 제목·사실 정보만 쓰기 때문이다. 저작권법 제25조(학교교육)는 부트캠프 과제의 공개 배포에 기대기 어렵다.
7. **약관 위반은 교육·비상업 목적이어도 면제되지 않는다.** 현실적인 결과는 소송보다 **키 정지·접속 차단**이다. 발표(10/13)를 앞두고 이것이 가장 현실적인 위험이다.

#### A2-3. 판단

피드가 허용한 범위와 우리 이용을 하나씩 맞춰 본다.

| 피드가 허용한 범위 | 우리 | 맞나 |
|---|---|---|
| personal feed reader (사람이 읽는 피드 리더) | 서버 프로그램이 자동 수집 → 스냅샷·DB·JSON | 아니오 |
| personal use | 팀원 5명 + 팀 밖 시험자 5명 | 아니오 |
| non-commercial | 광고·유료 없음 | 예 |
| rendering Google News results (결과를 그대로 보여 주기) | LLM 입력·요약, 정규식 파싱, 리포트 HTML·PDF에 저장 | 아니오 |

- "personal, non-commercial"은 **둘 다** 갖춰야 하는 조건이다. 비상업만 맞으므로 **여러 사람이 쓰는 비상업 교육용 웹 서비스는 범위에 들어가지 않는다** (판단).
- **LLM 입력은 "rendering"이 아니다.** 목표가 파싱은 데이터 추출이다. 둘 다 "Any other use"에 해당한다 (판단).
- 피드 문구는 동의 버튼 없이 붙는 방식이라 계약으로 묶이는지 다툴 여지가 있다. 약관규제법 제3조 ④는 명시·설명 의무를 어긴 약관을 "계약의 내용으로 주장할 수 없다"고 한다 [L4]. 다만 Google 서비스 약관의 "기타 콘텐츠" 조항이 같은 방향이고, 다툴 여지가 있다는 것이 "허용"을 뜻하지는 않는다 (판단).
- robots.txt는 원래 크롤러용이고 피드 리더에도 그대로 적용되는지는 불분명하다. 그러나 문언상 `/rss`는 모든 자동 수집기에 막혀 있고, Google 약관은 robots.txt 위반 접근을 금지 행위로 든다. 위험을 조금 더한다 (판단).
- **현실적 위험은 중간**이다. 소송보다 요청 차단(429·IP 차단)이나 피드 형식 변경이 먼저 올 것이다. 공개 시연 영상에 "Google 뉴스 제목을 AI가 요약"하는 장면이 나오면 범위 밖 이용이 공개 기록으로 남는다 (판단).

2. **약관 문언 자체가 교육·비상업 예외를 두지 않거나 명시적으로 배제한다**: 토스 "비상업적인 용도라 하더라도 … 엄격히 금지", 네이버 2.3 AI 입력 금지(예외 없음), 키움 "개인의 업무에 한하여", Google "personal, non-commercial"(둘 다 필요), 공공데이터 주식시세 "상업적 목적 여부와 상관 없이".
3. 위반의 1차 결과는 소송보다 **키 정지·해지·접속 차단**이다: 네이버 9.4·12.1, Google "suspend or terminate", 키움 해지. 발표 9일 전에는 이것이 가장 현실적인 위험이다.
4. 단서: 약관규제법 제3조 ④는 명시·설명 없이 체결한 약관을 "계약의 내용으로 주장할 수 없다"고 한다 [L4]. 동의 절차가 없는 Google 피드 문구는 다툴 여지가 있지만, 키움·네이버·토스는 가입 때 동의했으므로 해당하지 않는다 (판단).

### A8. "교육용 프로젝트라 상관없나" — 결론

**아니다.** 저작권은 대체로 괜찮다 — 다만 그것은 교육용이어서가 아니라 제목·사실만 쓰기 때문이다. 약관은 교육용이어도 그대로 적용되고, 우리가 쓰는 출처 대부분(Google 뉴스 RSS, 키움, 토스, 네이버)이 **비상업 이용도 다른 사람에게 보여 주는 것을 막는다.** 소송 가능성은 낮지만 키 정지·차단은 현실적이고, 공개 URL·공개 시연 영상은 범위 밖 이용을 공개 기록으로 남긴다.

### A9. 권고와 할 일 (담당 1 기준)

#### A9-1. (a) 뉴스 출처

- **네이버 검색 API로 바꾸지 않는다.** 이유: ① 우리 핵심 용도(LLM 입력)를 특약 2.3이 명시적으로 금지한다 ② 목표가 파싱은 2.2 "가공 없이" 위반이다 ③ 개발자센터 신규 신청이 2026-07-30에 끝났고, NAVER API HUB 약관은 원문 미확인·유료 전환 예정이다. 사용자의 "네이버로 구현해도 됨"은 이 약관을 보기 전 결정이므로 다시 결정해야 한다 (`docs/plans/TEAM_PAPER_TRADING_PLAN.md` 4장 U5·E-3 갱신은 코디네이터).
- **발표(10/13)까지**: Google 뉴스 RSS를 유지하되 9-2의 표시·제한을 한다. 더 보수적으로 가려면 팀 밖 시험 기간에 뉴스 수집을 끈다(9-3 스위치).
- **발표 뒤**: LLM 근거를 OpenDART 공시 목록·재무·시세 수치 중심으로 바꾼다(공공데이터, 이용 제한 없음). 뉴스는 LLM에 넣지 않는 "원문 링크 목록"으로만 보이거나, 정식 이용 허락이 있는 출처를 검토한다. 후보: 한국언론진흥재단 빅카인즈 OPEN API(신청제, 이용 조건은 공개 페이지에서 못 읽음. 사이트 하단 "빅카인즈에서 제공되는 모든 기사는 「저작권법」의 보호를 받으며, 이를 전재, 복제, 배포하는 행위를 금합니다.") [B1].
- **해외(US)**: Google RSS는 같은 문제다. 대안으로 SEC EDGAR 공시 목록을 쓴다 — "Anyone can access and download this information for free", "Current max request rate: 10 requests/second", User-Agent 선언 필수 [E1 원문]. 8-K 등 공시 제목·날짜를 "오늘의 소식" 근거로 쓸 수 있다. 미국 뉴스 API(유·무료 플랜) 약관은 이번에 보지 않았다(10장).

#### A9-3. 코드 변경이 필요하면 (담당 1이 고른다)

#### A9-4. (c) 발표 자료 고지 문구 (제안)

슬라이드 하단 한 줄:

> 비상업 교육 과제 · 실주문 없음 · 투자 권유 아님 · 시세: 키움증권 REST API · 공시/재무: 금융감독원 OpenDART·금융위원회 공공데이터 · 뉴스 제목: Google 뉴스(각 언론사) — 권리는 각 제공자에게 있음

긴 문장(마지막 장·영상 끝):

> 본 서비스는 비상업 부트캠프 교육 과제의 모의투자 시연입니다. 실제 주문은 없고 투자 권유가 아닙니다. 시세는 키움증권 REST API(조회 전용), 공시·재무는 금융감독원 OpenDART와 금융위원회(공공데이터포털), 뉴스 제목은 Google 뉴스 검색 결과(각 언론사)에서 받았으며, 모든 권리는 각 제공자에게 있습니다.

고지는 오해를 줄일 뿐 약관 위반을 없애 주지 않는다 (판단). 9-2의 제한과 같이 한다.

### A10. 확인 못 한 것

1. **토스증권 Open API 이용약관 전문** — 공개 페이지 없음(`/terms` 404). FAQ의 "데이터 이용 정책"만 원문 확인.
2. **NAVER API HUB 이용약관** — 콘솔 가입 단계에서 동의, 원문 미확인. 유료 전환 시기·요금 미확인.
3. **한국투자증권 고객용 「오픈 API 서비스 이용 약관(고객)」** — GitHub 이슈 2차 인용뿐. KIS 포털 약관 페이지는 스크립트로 그려져 읽지 못함.
4. **Google 뉴스 RSS 전용 약관** — 지금 공식 페이지 없음. 과거 비상업 웹 게재 라이선스는 2차 언급뿐이고 현재 효력 없음.
5. **피드 문구(동의 버튼 없는 약관)의 계약 성립** — 한국 판례 확인 안 함.
6. **뉴스 "제목"만 다룬 대법원 판례** — 못 찾음. 판례는 모두 요약 사이트(2차)로 확인했고 대법원 종합법률정보 원문은 읽지 않음.
7. **부트캠프 운영기관이 저작권법 제25조 ③ 각 호(특히 4호 학점인정 원격 과정)에 해당하는지** — 운영 형태 확인 필요.
8. **키움에 교육용 다중 표시 문의 결과** — 문의하지 않음(9-2 #7).
9. **빅카인즈 OPEN API 이용 조건** — 신청제, 공개 문서 못 찾음.
10. **미국 뉴스 API(Finnhub·Alpha Vantage·NewsAPI 등) 약관** — 이번 범위 밖.
11. **공공데이터포털 이용약관 자체** — 데이터셋별 이용허락범위만 확인.
12. 네이버 특약 9/7 개정 공지 원문 — 약관 본문과 보도로 확인, 개발자센터 공지 글 자체는 읽지 않음.

### B1. 한 줄 결론

**둘 다 국내 종목 기준으로 지금 자료로 거의 다 만들 수 있다.** 빠진 것은 ① 지수·업종 시세 TR 2개(키움에 있음, 아직 안 씀),
② 종목→업종 연결(`ka10100.upName`, 받지만 버림), ③ 영업현금흐름(DART에서 이미 받는 응답 안에 있는데 안 꺼냄) 정도다. 가장 큰 위험은
**뉴스 출처의 이용 조건**이다. 저장소가 쓰는 Google 뉴스 RSS는 피드 안에 "개인 피드 리더에서 개인·비상업 용도로만, 그 밖의 이용은 금지"라고 적혀 있다.
다른 위험은 인과 단정과 투자 권유로 오해받는 것이다. 그래서 등락은 숫자로 먼저 나누고(결정론), LLM은 근거 목록 안에서 "관련 있을 수 있는 소식"만 말하게 한다.
펀더멘털 점검은 회사 자신의 매수 시점 값과 비교하는 규칙(✓·△·✗)을 기본으로 한다. 장기 보유는 지금도 웹 수동 매수(목표·손절·기한 없이)로 할 수 있다.
다만 AI 추천·자동매매·리스크 엔진은 스윙(3~20거래일)에만 맞춰져 있으므로, 장기 보유는 **자동 청산 없는 별도 보유 방식**으로 나누는 것이 맞다.

### B4. 오늘의 내 종목 뉴스 — 설계 (코드 없음)

#### B4-1. 흐름

```
장 마감(15:30) ─▶ 16:30 KST, 거래일만 (data/calendar.py)
  ① 대상: 모든 팀원 계좌의 보유 종목(EXIT_WATCHING) 합집합 → 종목별로 1번만
  ② 숫자 분해 (결정론, LLM 없음) ── 종목별 캐시 DailyMoveNote(symbol, day) 유일
  ③ 근거 목록 모으기 (공시·뉴스 제목·증권사 헤드라인·수급) → guards.clean_text
  ④ 설명 필요 여부 판단 (결정론) ─ 아니면 템플릿 문장, LLM 호출 없음
  ⑤ LLM 1회 (근거 안에서만) → 출력 계약 검증 + 문장 규칙 검사
  ⑥ 사용자별 묶음 알림 1개 (웹 + Discord): "오늘 내 종목 3개: …"
```

#### B4-2. 등락 분해 (숫자 먼저, 결정론)

| 성분 | 계산 | 자료 |
|---|---|---|
| 종목 등락 `r` | 오늘 종가 ÷ 전일 종가 − 1 | `ka10081` 일봉 (이미 사용) |
| 시장 `r_m` | 코스피 종목은 `001`, 코스닥 종목은 `101` 지수 등락률 | `ka20001`(당일 `flu_rt`) 또는 `ka20006`(일봉) — **새로 붙임**. 임시 대안: 코스피는 KODEX 200(`069500`) 기록값, 코스닥은 없음 |
| 업종 `r_s` | 종목 `upName` → `ka10101` 업종명 → 업종코드 → 업종 등락률 | `ka10100`/`ka10099`의 `upName`(받지만 버리고 있음) + `ka10101` + `ka20001` — **새로 붙임**. 매칭 실패면 업종 성분 생략 |
| 시장 몫 | v1: `r_m` 그대로 (β=1 가정). v2: 최근 120거래일 일봉으로 β 추정 후 `β × r_m` | 종목·지수 일봉 |
| 업종 몫 | `r_s − r_m` (업종이 시장보다 더/덜 움직인 만큼) | |
| 종목 고유 몫 | `r − 시장 몫 − 업종 몫` | |
| 수급 | 개인·외국인·기관 순매수 수량 ÷ 그날 거래량 (%), 최근 20일 같은 비율과 비교 | `ka10059` (이미 사용) |
| 거래량 | 그날 거래량 ÷ 20일 평균 | 일봉 |

- 초보자 화면은 **세 숫자**만 보여 준다: "코스피 −1.2% · 반도체 업종 −2.0% · 삼성전자 −2.4% → 시장·업종을 빼면 −0.4%(종목 고유)".
- β는 추정 오차가 커서(특히 상장 짧은 종목) v1은 β=1로 하고 "시장 대비 초과 등락"이라고만 부르는 것을 권한다.
- 분해는 **회계식 분해이지 인과가 아니다.** 화면 문구도 "시장이 이만큼, 업종이 이만큼 같이 움직였다"로 쓴다.

#### B4-3. 근거 목록 (LLM에 넘기는 것)

각 항목에 ID(`E1`, `E2` …)를 붙인다. LLM은 이 ID로만 말한다.

| 종류 | 자료 | 신뢰 | 비고 |
|---|---|---|---|
| 공시 | DART `list.json` (종목, 그날) — 제목·시각 | 높음 (사실) | 제목 키워드로 종류 분류(실적·잠정실적, 유상증자, 자기주식, 단일판매·공급계약, 최대주주 변경 등)는 코드로 |
| 수급 | 4-2의 숫자 | 높음 (숫자) | "외국인이 거래량의 12%를 순매수" 같은 문장 재료 |
| 증권사 헤드라인 | `stock_reports(days=1)` | 중간 (제목 파싱) | 목표가 상향·하향 |
| 뉴스 제목 | `fetch_news(days=1, limit=15)` | 낮음~중간 | 같은 이름의 다른 회사 기사가 섞인다 → 제목에 종목명이 정확히 있는 것만 |
| 시장·업종 | 4-2의 숫자 + 상승·하락 종목 수(`ka20001`) | 높음 | "오늘 코스피 하락 종목이 상승의 3배" |

#### B4-4. 설명이 필요한지 (LLM 비용을 줄이는 결정론 규칙)

- **LLM 생략**: 종목 고유 몫이 작고(제안: |고유 몫|이 1%p 미만이면서 그 종목의 20일 일간 변동성(`volatility20`)보다도 작을 때 — 값은 팀이 정한다) 그날 공시·헤드라인이 없으면
  → 템플릿 "오늘은 시장·업종과 비슷하게 움직였습니다 (코스피 −1.2%, 업종 −2.0%, 내 종목 −2.4%)."
- **LLM 호출**: 고유 몫이 크거나, 그날 공시가 있거나, 수급 비율이 평소보다 크게 튀었을 때.
- 이 규칙만으로 많은 날·종목이 LLM 없이 끝난다 (비율은 실측 필요).

#### B4-5. LLM 출력 계약과 문장 규칙

출력 계약(가칭 `DailyMoveResult`, 리포트 `contracts.py` 형식에 맞춤):

```
headline: str (60자)              "시장 하락과 함께 내렸고, 같은 날 실적 공시가 있었습니다"
summary: str (300자)
drivers: [ {kind: "market"|"sector"|"stock"|"flow", text: str(120자), evidence: ["E1", ...]} ] (4)
uncertain: bool                    근거가 약하면 true → 화면에 "뚜렷한 소식을 찾지 못했습니다"
```

결정론 검사 (리포트의 `fact_check`처럼, 위반이면 1번 다시 요청 → 또 위반이면 템플릿으로 대체):
1. `evidence`의 ID가 모두 근거 목록에 있다. `market`·`sector`가 아닌 driver는 근거가 최소 1개.
2. 문장에 나온 숫자(%, 원)가 넘겨준 숫자와 일치 (반올림 허용).
3. **금지 표현**: 인과 단정("때문에", "덕분에", "원인은", "~로 인해 급등") → 허용 표현은 "같은 날 ~이 있었습니다", "관련 있을 수 있는 소식".
   투자 권유("사세요", "팔아야", "매수 기회", "추가 매수", "목표가 도달 예상") → 금지. 이 목록은 프롬프트와 검사에 둘 다 둔다.
4. 근거가 뉴스 제목뿐이면 `uncertain=true`를 강제한다.

화면 고정 문구: "등락의 원인을 단정하지 않습니다. 같은 날 나온 소식을 모은 것이며 투자 권유가 아닙니다."

#### B4-6. 실행 시각·캐시·비용

- **시각**: 16:30 KST 거래일 1회 (`calendar.py`의 정규장 끝 15:30 이후). `ka10059`의 당일 수급이 이 시각에 확정 값인지는 **확인 필요** (8장).
  저장소의 `run_engine` 루프에 "오늘 아직 안 만들었으면 만든다" 단계 하나를 더하는 방식(자동 추천 `auto.tick`과 같은 모양)이 맞다.
- **종목별 캐시**: `DailyMoveNote(symbol, day)` 유일 제약. 여러 사람이 같은 종목을 가져도 한 번만 만들고, 사용자 알림은 이 행을 참조만 한다.
  엔진이 다시 떠도 이미 만든 (symbol, day)는 건너뛴다. 실패는 `status=failed`로 남기고 다음 tick에서 1번만 다시.
- **조회 비용**: 종목당 키움 일봉 1 + 수급 1 (+ 업종·지수는 하루 1번씩 공유), DART 공시 목록 1, 뉴스 RSS 1~2. 키움 초당 5회 한도 안에서 종목 수십 개는 수십 초.
- **LLM 비용**: 종목당 최대 1회. `LlmClient.cost`의 호출 전후 차이를 `DailyMoveNote.cost_usd`에 남긴다 (분석의 `AnalysisRun.cost_usd`와 같은 방식).
  금액은 요금표가 저장소에 없어 **첫 주 실측으로 정한다**. 참고로 저장소의 다중 모델 교차검증 분석은 "종목당 AI 비용 약 $0.3"(`daily.py` 주석)인데,
  이 기능은 짧은 입력·출력에 빠른 모델 1번이라 그보다 훨씬 작을 것으로 **예상만** 한다. 하루 상한(종목 수 `MAX`, 금액 `BUDGET`)을 설정 키로 둔다.
  **(2026-10-04 추정)** 공개 가격표와 프롬프트 길이로 어림하면 1회 약 $0.002~0.04(중간 가정: 입력 3천·출력 1.2천 토큰 — 빠른 모델 $0.002~0.018, Opus급 $0.036)라 $0.3보다 1~2자리 작다. 근거·계산은 8장 9번. 게이트웨이 청구액(`usage.cost`)은 공개가와 다를 수 있어 첫 주 실측은 그대로 필요하다.
- **알림**: 사용자당 하루 1개로 묶는다 (종목마다 보내지 않는다). 새 `NotificationKind` `"daily_move"`(docs/API.md 먼저 수정).
  Discord는 기존 보낼 편지함으로. 등락이 큰 종목(예: |r| ≥ 5%, 팀 결정)만 제목에 올린다.

#### B4-7. 리포트 Agent 워크플로우 재사용 vs 가벼운 단일 Agent

| 기준 | 리포트 워크플로우 재사용 (`00-공통.md`: 조사 Worker 3개 → report → review → risk Handoff) | 가벼운 단일 Agent (권장) |
|---|---|---|
| LLM 호출 | 종목당 최소 5번 (market·fundamental·news·report·review, risk는 선택) | 종목당 0~1번 |
| 실행 방식 | `runner`가 **동시에 1개만** (`MAX_CONCURRENT = 1`) — 보유 종목 수십 개를 장 마감 뒤에 돌리기엔 느리다 | 종목별 순차/소수 병렬, 실패는 템플릿으로 |
| 맞는 질문 | "이 종목을 살까?" (깊은 분석, 매수 판단) | "오늘 왜 움직였지?" (짧은 사실 요약) |
| 재사용할 부품 | — | `healing.LlmCaller`(재시도·대체 모델), `contracts.validate`, `guards.clean_text`, Trace 대신 `DailyMoveNote`에 모델·비용·시도 수 |
| 결합 | 2·3·4 담당 작업(10/5~)이 끝나야 쓸 수 있다 | 그 부품이 없으면 `LlmClient.complete_json`으로 먼저, 나중에 호출기만 바꾼다 |

**권장: 단일 Agent.** 부품(호출기·계약 검증·입력 Guard)만 리포트 쪽 것을 쓰고, Orchestrator·Join·Review·Handoff는 쓰지 않는다.
"이 종목 더 깊게 보기" 버튼으로 기존 리포트 신청(`POST /api/reports`)을 이어 주면 두 기능이 자연스럽게 나뉜다.

### B5. 펀더멘털 점검 — 설계 (코드 없음)

#### B5-1. 지표와 규칙 (저장소 자료로 계산 가능한 것만)

원칙: **절대 기준보다 "산 때와 비교한 변화"를 먼저 본다.** 업종마다 정상 범위가 너무 달라서(예: 영업이익률, 부채비율) 절대 기준은 최소한만 둔다.
아래 기준값은 출처가 있는 한계기업 기준을 빼면 **팀이 정할 제안값**이다 (근거 = 이유 설명, 숫자의 공식 출처 아님).

| 지표 | 계산 (자료) | ✓ | △ | ✗ | 이유·한계 |
|---|---|---|---|---|---|
| 매출 성장 | 최신 보고서 누적 매출의 전년 같은 기간 대비 (`interimRevenueGrowth`, 없으면 `annualRevenueGrowth`) + 5년 추이 (`annualHistory`) | ≥ 0% | −10% ~ 0% | < −10% 또는 2개 보고서 연속 감소 | 성장주 논리였다면 핵심. 계절성은 누적·전년 동기 비교로 줄였다 |
| 영업이익 성장 | `interimOperatingIncomeGrowth` / `annualOperatingIncomeGrowth` | ≥ 0% | −20% ~ 0% | < −20% 또는 **적자 전환** | 전기가 0 이하면 증가율 없음(`_growth`) → 흑자·적자 전환으로 판정 |
| 영업이익률 (TTM) | `ratios.operatingMargin`, 기준선 = 매수 시점 값 | 기준선 −1%p 이내 | −1 ~ −3%p | −3%p 넘게 하락 또는 음수 | 업종 차이가 커서 **자기 기준선 대비 변화만** 본다 |
| ROE | DART 공시 `reported.roe` (M210000) | 기준선 −2%p 이내이고 > 0 | 하락 폭 더 큼 | ≤ 0 | 2023년 3분기 이후만 제공 [S4]. 분기 보고서 값은 누적 기준이고 연환산이 아니다 (`annualized: False`) — 연간과 섞어 비교하지 않는다 |
| 부채비율 | DART `reported.debtRatio` + 5년 `annualHistory[].debtRatio` | 기준선 대비 +20%p 이내 | +20 ~ +50%p | +50%p 넘게 증가 | 금융업(은행·보험·증권)은 구조상 높다 → **금융업은 이 지표 제외** |
| 유동비율 | DART `reported.currentRatio` | ≥ 100% | 80 ~ 100% | < 80% | 업종 차이 있음 — 보조 지표로만 |
| 이자보상배율 | 영업이익 ÷ **금융비용**(`nonOperating.financeCosts`) — 근사 | ≥ 3 | 1 ~ 3 | < 1 (그리고 3년 연속이면 "한계기업 기준 해당" 문구) | 한계기업 = 3년 연속 1 미만 [S13]. 금융비용은 이자비용보다 넓어(외환손실 등 포함 가능) **배율을 낮게 본다** → 표시는 "근사"로. 정확한 이자비용 계정은 확인 필요. **(2026-10-04 확인: 확인한 13개 회사의 손익계산서·포괄손익계산서에는 `ifrs-full_InterestExpense`가 없고(0곳) `ifrs-full_FinanceCosts`(금융비용·금융원가)만 있다. 이자지급은 현금흐름표에 `InterestPaid…` 태그로 있으나 영업활동·재무활동 분류가 회사마다 갈린다 — 8장 7번 [S14])** |
| 이익의 질 | 순이익÷영업이익 (`netIncomeToOperatingIncome`), 영업외 손익 비중 (`nonOperatingShareOfPretaxIncome`) | — | 영업외 비중이 커서 순이익이 영업이익과 크게 다름 | — | 경고만 (△). 일회성 이익을 성장으로 착각하지 않게 |

#### B5-2. "산 이유(투자 논리)"를 저장하고 대조하는 방식

새 모델 `InvestmentThesis` (가칭, 계좌·종목별 1개, 매수 시점에 만든다):

| 필드 | 내용 | 어디서 |
|---|---|---|
| `source` | `report` / `recommendation` / `manual` | |
| `reasons` | 산 이유 문장 (최대 3) | 리포트 `ReportDraft.reasons`, 추천 `Recommendation.reasons`, 수동 매수는 체크박스(성장 / 수익성 / 재무 안정 / 기타 한 줄) |
| `pillars` | 점검할 축 — 예: `["growth", "profitability", "balance_sheet"]` | 리포트 `FundamentalResult.metrics`가 좋았던 항목 또는 사용자가 고른 체크박스 → 5-1의 지표로 연결 |
| `baseline` | 매수 시점 펀더멘털 스냅샷: 보고서 기간(`reported.period`), TTM 영업이익률, ROE, 부채비율, 매출·영업이익 성장률, OCF | `dart.fundamentals(...)` 결과를 그대로 (JSON) |
| `checks` | 점검 기록 [{at, period, items: {지표: ✓/△/✗, 값, 기준선}, summary}] | 점검 때마다 추가 |

- 대조는 **결정론**이다: 새 보고서 값 vs `baseline` → 5-1 규칙. "산 이유" 축에 걸린 지표의 ✗는 제목에 올린다 ("성장 논리 점검 필요: 영업이익 −35%").
- LLM은 선택: 결과를 쉬운 말 2~3줄로 바꿀 때만 (근거 = 지표 표, 4-5와 같은 금지 표현). 정기공시 때만 부르므로 종목당 1년 4번 수준.
- 리포트·추천에서 산 경우가 아니면 이유가 없다 → 수동 매수 화면에 "왜 샀나요?" 체크박스를 두고, 비워 두면 3축 모두 점검한다.

#### B5-3. 점검 시각과 알림

- **새 정기공시 감지 (매일 18:00 KST)**: DART `list.json`을 `pblntf_ty=A`(정기공시), 그날 하루, 고유번호 없이 불러(1~몇 쪽, `page_count` 100) 보유 종목만 거른다 [S5].
  종목별로 부르는 것보다 호출 수가 적다. 정정(`rm`에 "정")도 다시 점검한다.
- 공시가 나와도 `fnlttSinglAcnt`에 재무가 바로 들어오는지는 **확인 필요** → 감지 뒤 재무가 비어 있으면 다음 날 다시 (최대 7일).
  (2026-10-04 일부 확인: 6월 결산 법인 사업보고서 6건이 접수 6~24일 뒤 모두 조회됐다. 시차의 상한은 약 6일 이내로 좁혀졌고, 정확한 시차는 실측 필요 — 8장 6번 [S14].)
- **주 1회 (토요일)**: 모든 보유 종목 재점검 (감지 누락·정정 대비, data.go.kr 갱신 반영 [S12]).
- **몰리는 시기**: 12월 결산 법인 기준 분기·반기는 각 분기 끝 + 45일, 사업보고서는 사업연도 끝 + 90일까지라 [S6][S7] 5월·8월·11월 중순과 3월 말에 몰린다.
- **호출 수**: `fundamentals` 한 번이 DART를 최대 10번 정도 부른다(연간 ≤2, 분기 ≤3, 지표 2, 전체 재무제표 ≤2, 주식수 1). 보유 50종목 주간 점검이어도 수백 건 — 하루 20,000건 한도 [S1] 대비 작다. 단, **분석·리포트와 같은 키를 나눠 쓴다.**
- **알림**: 새 `NotificationKind` `"thesis_check"`. ✗가 새로 생기거나 종합 표시가 나빠졌을 때만 웹 + Discord. 나아졌을 때와 "변화 없음"은 웹 알림만.
  알림 문구에 매도 권유를 넣지 않는다 ("점검 필요 항목이 생겼습니다" + 지표 표 링크).

### B6. 장기투자와 지금 구조의 충돌, 해결안

| 지금 구조 | 장기 보유와 맞나 | 근거 (코드) |
|---|---|---|
| AI 추천은 **스윙만**: `TRADABLE_HORIZONS = ("SWING",)`, 보유 3~20거래일. 사실 검증이 `LONG_TERM`을 거른다. 제안 프롬프트도 SWING만 | ✗ | `judge/scenario.py`, `judge/fact_check.py`, `agents/proposer.py` |
| 리스크 엔진 `LIMITS["LONG_TERM"]` (건당 위험 2%, 최소 손익비 2.5, 일일 손실 3%)은 **형식만 남아 있다** ("이전 기록과 리스크 한도 때문에 남겨 둔다"). 손절가 기준 수량 계산이라 손절 없는 장기 보유엔 맞지 않는다 | △ | `judge/risk.py`, `scenario.py` 주석 |
| 자동매매 계획은 `horizon="SWING"` 고정 (2026-10-06 단타 폐기로 `horizon` 필드를 지웠다 — 계획은 늘 스윙), `Recommendation.holding_days` 1~20, 주문 기한 = `min(MAX_MANAGED_DAYS, ceil(보유일×7/5))` | ✗ (장기용 아님) | `backend/autotrade/plans/risk.py`, `executor.order_days` |
| `MAX_MANAGED_DAYS = 180`: 기한을 **줄 때만** 1~180일. 기한이 지나면 `EXPIRED`로 자동 청산 | 기한을 안 주면 문제없음 | `paper_engine/trading.py`, `agents/executor.py` |
| 엔진 CLI는 목표·손절을 주고 기한을 안 주면 `DEFAULT_MANAGED_DAYS = 30` | 장기엔 ✗ (CLI만) | `paper_engine/trading.py` |
| **웹 수동 매수는 목표·손절·기한 모두 선택**: 안 주면 자동 청산·만료 없이 보유 (`expire=None`) | ✓ 지금도 장기 보유 가능 | `backend/trading/service.buy`, `_expire` |
| 목표·손절 자동 청산 | 장기 논리와 충돌 — 가격 변동으로 손절되면 "펀더멘털이 견조한데 팔림" | `agents/executor.py` |

**해결안**

1. **보유 방식을 둘로 나눈다**: `스윙 계획`(지금 그대로: AI 추천 → 계획 → 목표·손절·기한 자동 청산) / `장기 보유`(목표·손절·기한 없음, 매도는 사용자만).
   `PaperOrder`(또는 포지션)에 `style: "swing" | "long"` 열을 두거나, 1차는 "목표가가 없으면 장기 보유"로 **유도**만 한다 (마이그레이션 없이 시작).
2. **장기 보유에는 자동 매도를 붙이지 않는다.** 펀더멘털 ✗도 알림만 (AI는 제안만 — AGENTS.md 안전 규칙과 같다).
3. **장기 보유의 수량 판단**은 손절 기반 리스크 엔진 대신 비중 한도로: `RiskLimits.max_position`이 이미 있으니 장기 매수 미리 보기에서 "계좌의 X% 이하"만 점검 (X는 팀 결정).
   `LONG_TERM` 손익비 2.5 규칙은 장기 보유에 쓰지 않는다 (목표가가 없다).
4. **AI 추천을 장기로 넓히지 않는다** (1차). 장기 "추천"은 투자 권유 오해가 가장 큰 영역이다. 대신 장기 보유자에게는 "매일 설명(4장) + 분기 점검(5장)"을 준다.
5. 두 기능의 대상: 오늘의 내 종목 뉴스 = **모든 보유 종목**(스윙 포함), 펀더멘털 점검 = **장기 보유 + 국내 일반 기업**만.

- 시세 = 폴링 (`docs/DECISIONS.md` 8-2): 웹이 현재가를 1초 캐시(`backend/trading/market.py`의 `trading:price:{symbol}`), 화면은 1초마다 받는다.
- `run_engine` 5초 루프(`--interval 5.0`): 체결·청산 확인, 예약, 일별 자산, AI 작업, 추천·자동매매, 알림.
- 체결 규칙(`engine/paper_engine/agents/executor.py`): 지정가는 확인 가격 ≤ 지정가면 그 확인 가격으로 체결, 처음 끝나는 정규장까지 안 되면 취소.
  목표·손절은 **2회 연속 확인**(`LOCAL_EXIT_CONFIRMATIONS = 2`) 뒤 확인 가격으로 전량 매도. 수수료 0.015%(`DEFAULT_COMMISSION`), 국내 매도 거래세 0.2%(`SELL_TAX_RATE["KR"]`), 손절 주문가 버퍼 1%(`STOP_LIMIT_BUFFER`).
- 키움 조회 한도 토큰당 초당 5회를 엔진·웹이 나눠 쓴다. 키움은 **아직 실제 키로 호출해 본 적이 없다** (`docs/design/DESIGN.md` 부록 A 머리말).

#### C3-2. 실시간 수신 프로세스

```
키움 WS ──(0B·0D·0s·1h)──> [ticker 프로세스] ──> Redis (paper:*) ──> run_engine(틱 체결기) ──> DB(주문·체결)
                                 ▲   │                         └────> 웹 market.py (현재가 캐시 대체) ──> 화면
         paper:rt:want (원하는 구독) ┘   └─> paper:rt:status (생존 신호·마지막 수신 시각)
```

- **별도 프로세스·컨테이너** `ticker`(운영 `deploy/docker-compose.yml`에 서비스 하나 추가, 로컬은 `scripts/dev.sh`가 같이 띄움). 웹·엔진 루프와 생명주기를 분리해야 끊김·재접속이 다른 일을 멈추지 않는다.
- **의존성 위치**: 엔진은 표준 라이브러리만 쓴다는 규칙 때문에 WebSocket 통신(예: `websockets` 패키지)은 `backend/`에 둔다 (Django 관리 명령 `run_ticker` 형태).
  대신 **키움 FID → 내부(토스) 형식 변환은 규칙대로 `engine/paper_engine/data/kiwoom.py` 안의 순수 함수**(네트워크 없음)로 두고, 토스는 `data/toss.py`에 같은 이름·반환 형식의 함수를 둔다.
  `make_client` 단일 진입점·두 클라이언트 공개 메서드 동일 규칙을 실시간에도 적용한다 (예: `realtime_spec()` → 접속 주소·구독 메시지 생성, `decode_realtime(msg)` → 내부 틱 목록). 이름은 구현 시 확정.
- **토큰**: 키움은 "토큰별 세션 1개"[3]이고 토큰은 발급 IP에 묶인다(`8010`, `docs/design/DESIGN.md` 부록 A7). → 실시간 세션은 **한 서버의 한 프로세스만** 연다. 다른 프로세스(엔진 CLI 등)가 세션을 열면 안 된다.
  토큰 파일 캐시(`KIWOOM_TOKEN_CACHE`)는 REST와 공유하되, REST 쪽 재발급이 기존 토큰(=WS 세션)을 무효로 만드는지 모른다(`docs/design/DESIGN.md` 부록 A8 1번) → 재발급 시 WS 재로그인을 전제로 설계.
  **(2026-10-04 확인)** 공식 FAQ #25: 토큰 만료는 발급 24시간 뒤이고, 발급 뒤 6시간 안의 재요청에는 기존 토큰을 돌려주지만 **6시간이 지난 재요청에는 새 토큰을 발급하고 기존 토큰은 폐기**한다 [34]. 폐기가 열려 있는 WS 세션을 끊는지는 문서에 없다(실측 필요) — "재발급 시 WS 재로그인" 전제는 그대로 맞다.

#### C3-3. Redis 버퍼 (`paper:` 접두사만)

| 키 (제안) | 형식 | 내용 |
|---|---|---|
| `paper:tick:{symbol}` | Hash | 마지막 체결(가격·수량·부호·체결시간·최우선 매도/매수호가·수신 시각) — 웹 현재가 캐시가 먼저 읽는다 |
| `paper:book:{symbol}` | Hash | 마지막 10단계 호가 (0D 등록 종목만) |
| `paper:ticks:{symbol}:{YYYYMMDD}` | Stream (`XADD MAXLEN ~ N`) | 당일 체결 틱. 틱 체결기가 `XREAD`로 마지막 ID부터 읽는다. 장 마감 뒤 1분봉으로 접어 DB에 남기고 지운다 |
| `paper:rt:want` | Sorted Set (점수 = 우선순위) | 구독하고 싶은 종목. 웹·엔진이 쓰고 ticker가 읽어 등록·해지 |
| `paper:rt:view:{symbol}` | String + TTL | 화면에서 보고 있는 종목 임대(화면 폴링마다 TTL 연장) |
| `paper:rt:status` | Hash + TTL | 연결 여부, 마지막 수신 시각, 등록 수, 재접속 횟수 — 생존 신호 |
| `paper:rt:events` | Stream | 0s 장운영·1h VI 사건 |

키는 `paper:` 접두사만 쓴다. 데이터 양은 지어내지 않는다: **하루 메시지 수 ≈ 구독 종목들의 당일 체결 건수 합(0B) + 호가 변경 건수(0D)**. 첫 실측일에 `paper:rt:status`에 하루 메시지 수·바이트를 세어 MAXLEN과 보관 정책을 정한다.

#### C3-4. 누구의 종목을 구독할지 (공식 200종목/세션 [3], 토스 100건/연결 [11])

우선순위 높은 순으로 채우고 남는 자리만 다음 순위에 준다. **200이 종목×항목이면(0B와 0D를 따로 센다면) 예산이 반으로 준다** → 모든 종목은 0B만, 0D는 1순위 종목만.
(2026-10-04 확인: 공식 FAQ가 "TR 종류에 상관없이 합쳐서 최대 200개"라고 답해 이 가정이 맞는 쪽으로 읽힌다 [31]. 0s·1h가 자리를 쓰는지는 실측.)

1. 당일 청산 모드의 **진행 중 주문·보유 종목** (체결·손절이 걸려 있음 — 빠지면 안 됨)
2. 활성화된 자동매매 계획(`backend/autotrade`)의 종목
3. 화면에서 지금 보고 있는 종목 (`paper:rt:view:*` 임대가 살아 있는 것)
4. 장 전 AI 관심 종목 목록
5. `0s`(장운영), `1h`(VI, 전체)는 `item=""`로 항상 등록

자리가 모자라 빠진 종목은 지금처럼 REST 폴링(1초 캐시·5초 루프)으로 처리한다 — **실시간은 "추가 경로"이고 폴링은 항상 남는 대체 경로**다.

#### C3-5. 틱 기반 모의 체결 규칙 (제안)

| 상황 | 규칙 | 근거·비고 |
|---|---|---|
| 시장가 매수/매도 | 접수 시점 최우선 매도(매수)호가(0B `27`/`28` 또는 0D `41`/`51`)로 체결. 수량이 1단계 잔량보다 크면 0D 10단계를 따라 내려가며 가중평균(호가를 다 먹으면 나머지는 마지막 단계 가격 + 슬리피지) | 0D 없는 종목은 최우선호가 + 슬리피지 상수(호가 단위 n틱) |
| 지정가 매수 | 접수 뒤 **체결가 < 지정가인 틱**이 오면 지정가로 전량(또는 부분) 체결. 체결가 = 지정가인 틱만 오면 큐 앞 순서를 모르므로 (a)·(b) 단계에서는 **체결하지 않는 보수적 규칙** | 지금 규칙(확인 가격 ≤ 지정가 → 확인 가격으로 체결)보다 보수적. 틱이 지정가를 "뚫고 지나가야" 체결 |
| 부분 체결 | 한 틱에서 체결되는 수량 ≤ 그 틱의 거래량(0B `15`) × 참여율 상수. 나머지는 다음 틱으로 | 참여율 값은 설계 파라미터(출처 없음), 시연은 100%로 시작 가능 |
| 손절·목표 | 체결 틱이 손절가 이하(목표가 이상)가 되면 즉시 시장가 청산 규칙 적용. "2회 연속 확인"은 튀는 폴링 값 대비였으므로 틱 모드에서는 "틱 1개 + 최우선호가 확인"으로 바꾼다 | `LOCAL_EXIT_CONFIRMATIONS`는 스윙 모드에서 그대로 |
| VI·단일가 | `1h` 발동~해제 사이, `0s` 장시작 전·장마감 동시호가 구간에는 연속 체결 규칙을 멈추고 대기(또는 해제 직후 첫 체결가로 체결) | KRX 장 운영: 0s 코드 `2` 장마감 알림 15:20~, `4` 장마감 15:30 [1]. (2026-10-04 확인: 2026-09-14 개편 뒤에도 KRX 접속매매는 09:00~15:20, 종가단일가는 15:20~15:30이다 [26]. 1차는 KRX만 쓰므로 NXT 정적 VI의 단일가 전환·`9068`=`4`(VI 연장)는 NXT를 붙일 때 반영한다 [27].) |
| 상·하한가 | `0g` 상한가·하한가(FID 305/306)를 넘는 지정가는 거절 | |
| 비용 | 수수료·거래세는 지금 엔진 값(`DEFAULT_COMMISSION`, `SELL_TAX_RATE`)을 그대로 쓴다. 단타는 왕복 횟수가 많아 **비용이 손익을 크게 좌우**하므로 화면에 비용 합계를 따로 보인다 | 현행 거래세율 0.2%가 2026년 실제 세율과 맞는지는 별도 확인 필요 **(2026-10-04 확인: 맞다 — 코스피·코스닥 모두 매도 0.20%. 증권거래세법 시행령 제5조 개정(2026-01-01 시행)과 농어촌특별세법으로 확인, 5장 11번) [36][37]** |
| 당일 청산 | 당일 청산 모드 주문은 장마감 동시호가 전(예: `0s`=`2` 15:20 알림 수신 시, 또는 그 전 설정 시각)에 남은 보유를 시장가로 강제 청산, 미체결 지정가 취소. 실시간이 죽어 있으면 REST 확인 가격으로 같은 일을 한다 | 시각은 설정값. 동시호가 참여(종가 체결) 방식은 후속 선택지 |
| NXT | 1차는 **KRX만**(`item`에 접미사 없음)으로 지금 체결 규칙·장 달력과 맞춘다. NXT 프리·애프터는 후속 | 지금 엔진은 KRX 코드만 쓴다 (`docs/design/DESIGN.md` 부록 A1) |

#### C3-6. 지금 5초 루프·1초 캐시와의 관계

- **웹 현재가**: `market.py`가 `paper:tick:{symbol}`의 수신 시각이 몇 초 안이면 그것을 쓰고, 아니면 지금처럼 REST(1초 캐시). → 화면이 많아도 REST 호출이 줄어 초당 5회 예산이 남는다 (8-2의 "묶음이 늘면 한도에 가까워진다" 문제 완화).
- **체결 확인**: 스윙 주문은 지금 5초 루프 그대로. 당일 청산 주문은 `run_engine` 안의 짧은 주기(또는 `XREAD BLOCK`) 틱 체결기가 처리한다.
  **DB에 주문을 쓰는 프로세스는 계속 `run_engine` 하나**로 둔다 (`select_for_update`·`trading.service` 경로 유지, 엔진 루프 하나 전제 8-6). ticker는 Redis에 쓰기만 한다.
- 화면 갱신은 지금 폴링(1초)으로도 충분하다. 틱을 화면에 흘리려면 SSE가 이미 `backend/reports`에 있으므로 같은 방식으로 붙일 수 있다 (후속).

#### C3-7. 장애(끊김) 시 복구 — AutoHealing과의 연결

| 장애 | 감지 | 복구 | 최종 실패 시 |
|---|---|---|---|
| 연결 끊김 | 수신 루프 종료·예외 | 지수 백오프로 재접속 → LOGIN → `paper:rt:want`로 REG 재등록 | 시도 수 상한 넘으면 "실시간 꺼짐" 상태 → 폴링만으로 동작 + 담당자 알림 (`notifications.service.notify`). (2026-10-04 확인: 월~토 07:50~07:55·일 05:00~05:15의 끊김은 키움의 정기 단절이라 정상 종료다 — 알림·장애 집계에서 제외하고 단절 시간대가 끝난 뒤(월~토 07:55, 일 05:15 이후) 다시 붙는 것으로 설계한다 — 단절이 실제로 언제 끝나는지는 추정 [24][32].) |
| 조용한 끊김 (연결은 살았는데 데이터가 안 옴) | 장중(`0s`로 판단)인데 거래 많은 구독 종목의 마지막 수신이 N초 넘음 | 강제 재접속 | 위와 같음 |
| 로그인 실패 (토큰) | LOGIN 응답 `return_code≠0`, `8005` 등 | 토큰 캐시 재확인 → 재발급 1회 (공식 클라이언트와 같은 방식 [1]) | 알림 |
| 등록 거절 (한도) | REG 응답 `return_code=1`, `1702` | 우선순위 낮은 종목부터 빼고 다시 등록 | 빠진 종목은 폴링 |
| 끊긴 구간 | 재접속 시 마지막 틱 시각과 현재 시각 차 | **진행 중 주문이 있는 종목만** `ka10084`(시각 지정) 또는 `ka10079`로 구간을 메워 체결 판정을 다시 돌림. 메우지 못한 구간은 체결하지 않음(보수적) | 사용자 화면에 "시세 지연 구간" 표시 |
| 토스(개발) 서버 배포 | `server-shutdown` 프레임 [11] | 재연결·재선언 | — |

- 지금 AutoHealing 과제(`docs/tasks/00-공통.md` 부록 A4)는 **LLM 호출 장애만** 다룬다 ("복구 로직은 리포트 워크플로우에만 해당"). 실시간 시세 끊김은 새 장애 유형(예: DR-FEED-01 끊김, 02 조용한 끊김, 03 토큰 무효)으로 **같은 틀(감지 → 재시도 → 대체 경로 → Circuit Breaker → 알림, 장애 주입·복구 지표)을 재사용**할 수 있다.
  대체 경로가 "REST 폴링"으로 분명하다는 점이 장애 복구 시연에 좋다. 단, 발표 전 일정에는 넣지 않는 것을 권한다 (4장).

### C4. 단계별 판정과 작업 목록

#### (a) 분봉·폴링 수준의 "데이트레이딩(당일 청산)" — **가능**

- 근거: 지금 1초 현재가 캐시·5초 루프·지정가 당일 유효 규칙이 이미 있고, 분봉은 키움 `ka10080`(1·3·5…60분, `base_dt`) [1]·토스 `candles?interval=1m`(최대 200봉) [13]로 받을 수 있다. 새 연결·새 의존성이 필요 없다.
- 작업:
  1. 주문·계획에 "당일 청산" 표시 (모델 열 + `docs/API.md` 먼저 고침)
  2. 장 마감 전 강제 청산·미체결 취소 (`run_engine`, 시각 설정값)
  3. 분봉 차트 API·화면 (`lightweight-charts`가 이미 있음), 분봉용 엔진 메서드(`KiwoomClient`·`TossClient` 같은 이름) + 가짜 클라이언트 테스트
  4. 단타용 리스크 파라미터(손절 폭·하루 최대 손실·하루 최대 거래 수) — 리스크 엔진이 정한다
  5. 비용(수수료·세금) 합계 표시
- 위험: 5초 루프 + 2회 연속 확인이라 손절이 늦게(최대 10초 이상) 잡힌다 → 시연 문구로 "분 단위 데이트레이딩"이라고 정확히 말해야 한다. 초당 5회 예산을 분봉 조회가 나눠 쓴다(종목당 1분 캐시 필요).
- 일정: 기술적으로는 발표 전 가능한 크기지만, 팀 일정(10/5~10/9 AutoHealing·리포트, 10/12 리허설, `docs/plans/TEAM_PAPER_TRADING_PLAN.md` 부록 A)과 겹친다. **발표 전에는 하지 않거나 1~3번만** 하는 것을 권한다. 평가 주제가 AutoHealing이기 때문이다.

#### (b) WebSocket 체결 기반 "초단기" — **조건부**

- 근거: 키움 명세에 0B·0D·0s·1h, 등록·해지·PING 규칙이 공식으로 있고 [1], 세션당 200종목 [3]은 팀 5명 규모에 충분해 보인다. 개발은 토스 WS(100건/연결, 2연결) [11]로 같은 설계를 먼저 돌려 볼 수 있다.
- 조건(모두 5장 실측 뒤): 200의 셈법, 토큰당 세션 1개와 REST 재발급의 상호작용, 재접속 동작, NXT 수신 여부, 약관상 팀 웹 표시 가능 여부. **키움 키 자체가 아직 한 번도 실측되지 않았다**는 점이 가장 큰 위험이다.
- 작업:
  1. `docs/DECISIONS.md`에 실시간 결정 장 추가(8-2 "실시간 = 폴링" 개정, 토스 WS 예외 3-1, 구독 우선순위, 체결 규칙), `docs/API.md`
  2. `data/kiwoom.py`·`data/toss.py` 실시간 변환 순수 함수 + 녹화한 틱으로 테스트 (외부 호출 없음)
  3. `backend`의 `run_ticker` 관리 명령 + 운영 compose 서비스 + `scripts/dev.sh` + CI·`.env.docker.example` 설정 키
  4. Redis 키(3-3), 구독 관리자(3-4)
  5. 틱 체결기(3-5)를 `run_engine`에 — 스윙 경로와 분리, 기존 executor 규칙은 고치지 않고 새 모드로
  6. 복구(3-7) + 장애 주입 시나리오 + 지표
  7. 화면: 실시간 상태 표시, 시세 지연 구간 표시
- 위험: 연결 장애가 체결 결과를 바꾼다(끊긴 구간 처리 규칙을 정직하게 보여야 함), LOSSY 시세(토스 명시 [11], 키움은 명시 없음), 운영 서버 IP·토큰 1세션 제약, 약관.
- 일정: **발표 뒤.** 실측 하루 + 구현·테스트 1~2주 규모로 추정(추정치).

#### (c) 호가·큐 위치까지 흉내 내는 "스캘핑" — **어려움**

- 근거: 0D는 호가 단계별 **잔량 합계** 스냅숏이고 개별 주문(큐 순서)·취소 흐름이 없다 [1]. 큐 위치는 "내 주문 앞 잔량 − 그 가격의 체결량 − 추정 취소량"으로 근사할 수밖에 없고 취소량은 알 수 없다.
  시세 프레임 유실 가능성(토스 LOSSY [11]), 우리 서버까지의 지연, 0B+0D를 모두 받으면 등록 예산이 줄어드는 문제가 겹친다.
  모의 결과가 현실과 크게 달라질 수 있어(유리한 체결 착시) 교육·시연 가치가 낮다.
- 작업(한다면): (b) 전부 + 큐 근사 모델 + 지연·유실 보정 + 실제 체결과 비교 검증 데이터. 검증할 실계좌 데이터가 없다(실주문 0건 규칙).
- 판정: 과제 범위에서 **하지 않는 것을 권한다.**

### C5. 확인 필요 항목 (실제 키로 다시 볼 것)

키를 받으면 `scripts/kiwoom_check.py`(REST 읽기 전용)와 같은 원칙(키·토큰 출력 금지, 계좌 실시간 `00`·`04` 등록 금지)으로 실시간 점검 스크립트를 따로 만들어 본다.

상태 표시(2026-10-04 갱신): **[확인됨]** 공개 1차 출처로 닫힘 · **[일부 확인]** 좁혀졌으나 남은 부분이 있음 · **[실측 필요]** 키가 있어야 앎 · **[약관 문서로 이동]**. 원래 문장은 그대로 두었다.

1. **200종목의 셈법**: 종목 수인가, 종목×항목(0B, 0D 각각) 수인가. 201번째 등록 시 응답(`return_code`, `1702` 여부).
   **[일부 확인: 공식 공지 #49와 FAQ #41이 "TR 종류에 상관없이 합쳐서 최대 200개"(연결·TR을 다 합쳐 200)라고 답해 종목×TR 합산으로 읽힌다(추정). 한도를 넘으면 오류가 아니라 "일부 종목 데이터 누락"이라고 적혀 있고(FAQ #8, 100종목 시절 문구) `1702`는 유량 오류군이다 · 출처 [23][29][31]]**
   **[실측 필요: 키 발급 뒤 `scripts/kiwoom_check.py`와 같은 원칙의 실시간 점검 스크립트 — 같은 종목의 0B·0D 이중 등록이 2로 세어지는지, 201번째 등록의 실제 응답]**
2. **토큰당 세션 1개**: 두 번째 세션을 열면 첫 세션이 끊기는가, 두 번째가 거절되는가. REST 호출과 WS 세션이 같은 토큰으로 공존하는가. REST 쪽 토큰 재발급이 WS 세션을 끊는가.
   **[일부 확인: "한 토큰으로 중복 연결은 불가능"(FAQ #41). REST와 WS가 같은 토큰을 쓰는 구조는 공식 SDK가 그렇게 만들어져 있다(`_login`이 REST와 같은 접근토큰을 보냄) · [1][31]. 토큰은 24시간 유효, 6시간 뒤 재요청이면 새로 발급하고 기존 토큰은 폐기(FAQ #25) · [34]]**
   **[실측 필요: 두 번째 연결의 결과(거절인지 기존 연결 종료인지), 토큰 폐기가 열려 있는 WS 세션을 끊는지]**
3. 서버 `PING` 주기, 무응답 시 끊기는 시간, 장 마감 뒤·주말에 세션이 유지되는가.
   **[일부 확인: 서버 PING에 클라이언트가 에코하지 않으면 서버가 연결을 끊는다(FAQ #15). 정기 단절은 월~토 07:50~07:55, 일요일 05:00~05:15이고 "정상 종료"라 close 이벤트로 재연결을 권장한다(공지 #46, FAQ #42). 이 시각 밖에서는 유지되는 것으로 읽힌다(추정) · [24][32][33]]**
   **[실측 필요: PING 주기와 무응답 허용 시간(공개 문서에 수치 없음), 장 마감 뒤·주말 유지 여부]**
4. `grp_no`를 여러 개 쓰면 등록 한도가 늘어나는가(아니라고 추정).
   **[확인됨 2026-10-04: 늘지 않는다 — 공식 FAQ #8의 예가 "그룹 1에 80종목 + 그룹 2에 40종목"을 비정상(합 120 > 100)으로 둔다. 한도는 그룹이 아니라 합계로 센다. `grp_no`는 화면·관심종목 단위로 목록을 따로 다루려는 용도 · [29][30]. 이 예는 100종목 시절 문구이고 FAQ #41(200)의 "전부 합쳐서"와 모순되지 않는다 · [31]]**
5. `0B` 수신 빈도: 체결 1건당 1메시지인지 묶여 오는지, 하루 메시지 수·바이트(데이터 양 산정).
   **[일부 확인: 명세 응답 예시의 `data`가 배열이고 공식 SDK도 `data` 항목마다 이벤트를 하나씩 펼치므로 한 메시지에 여러 건이 올 수 있는 형식이다 · [1]]**
   **[실측 필요: 실제 묶음 빈도, 하루 메시지 수·바이트]**
6. NXT: `_NX`·`_AL` 등록 시 프리(08:00~08:50)·애프터(15:30~20:00) 체결이 오는지, KRX 코드만 등록하면 NXT 체결은 빠지는지 (0B `9081` 거래소구분 값).
   **[일부 확인: 공식 FAQ #43의 예시가 `005930_AL`을 `0D`로 등록해 "정상수신"이라고 적는다. 개편(2026-09-14) 뒤 NXT 시간은 프리 08:00~08:50, 메인 09:00:30~15:20(그림 표기), 시가단일가 15:30~15:40, 애프터 15:40~20:00이고 KRX 애프터마켓은 16:00~20:00이다(위 문항의 "애프터 15:30~20:00"은 이 구조로 바뀌었다) · [26][35]]**
   **[실측 필요: 프리·애프터 시간대 체결이 실제로 오는지, KRX 코드만 등록할 때 NXT 체결이 빠지는지, `9081` 값(명세에 설명 비어 있음)]**
7. `1h` VI를 `item=""`로 등록하면 전 종목 VI가 오는지, 등록 한도에 세는지.
   **[일부 확인: 명세 예시가 `item` 빈 문자열이고, FAQ #3은 VI·CB 공지가 `SYSTEM`으로 내려온다고 한다. 연결 가능한 TR은 토큰별 10개(FAQ #41)라 `0B`·`0D`·`0s`·`1h`는 TR 4종을 쓴다 · [1][31][33]]**
   **[실측 필요: 전 종목 VI가 오는지, 등록 한도(200)에 세는지]**
8. `ka10079` 한 쪽 행 수(블로그 900)와 조회 가능한 과거 범위(당일만?), `ka10084`로 몇 분 전까지 메울 수 있는지, `ka10080` `base_dt`로 며칠 전까지 되는지.
   **[일부 확인: `ka10084`는 `tdy_pred`가 당일(1)·전일(2)뿐이라 당일·전일 두 날의 시각(`tm` HHMM) 지정까지, `ka10080`은 `base_dt` 인자가 있고, `ka10079`는 기준일 인자가 없다. 한 쪽 행 수와 과거 한도는 명세·SDK 예제·공지에 없다 · [1][28]]**
   **[실측 필요: 쪽당 행 수, 틱의 과거 범위, `base_dt`를 며칠 전까지 줄 수 있는지]**
9. 키움 「오픈 API 서비스 이용 약관」 원문에서 시세 이용 범위·제3자 제공 조항 (현재 폴링 서비스에도 해당). 토스 Open API 약관의 같은 조항.
   **[약관 문서로 이동] → A장**
10. KIS·LS 공식 포털의 실시간 등록 한도(대안 검토 시에만).
   **[선물 폐기(2026-10-04)로 확인하지 않음]** KIS·LS를 단타 대안으로만 볼 때를 위해 한 줄: 이번에도 공식 포털에서 한도 수치를 읽지 못했다(KIS는 2차 자료의 "체결·호가 합산 20건, 9월부터 60건 예정"뿐, LS는 수치 없음) → 대안으로 검토할 때 공식 문서로 다시 확인한다.
11. 현행 국내 증권거래세율이 엔진 값 0.2%와 맞는지.
   **[확인됨 2026-10-04: 맞다. 2026년 매도 세율은 코스피·코스닥 모두 0.20%이고 엔진의 `SELL_TAX_RATE = {"KR": 0.002}`와 같다. 코스피 = 증권거래세 0.05% + 농어촌특별세 0.15%, 코스닥 = 증권거래세 0.20%(농특세 없음), 코넥스 0.10%. 근거: 증권거래세법 시행령 제5조(대통령령 제36001호, 2025-12-31 공포·2026-01-01 시행 — 유가증권시장 1만분의 5, 코스닥 1만분의 20, 코넥스 1만분의 10, 부칙 제2조는 시행 이후 양도분부터 적용), 농어촌특별세법 제5조 제1항 제5호(유가증권시장에서 거래된 증권의 양도가액 1만분의 15)와 같은 법 시행령 제5조 제1항(유가증권시장) · [36][37]. 보도로도 같다 · [38]]**

#### D2-1. 키움 REST API: 국내 선물·옵션 시세 없음 [확인]

- 확인 방법: 공식 명세 `Kiwoom-Securities/Kiwoom-REST-API` `kiwoom/_data/kiwoom_api_spec.json`. `main` HEAD `953e5db`(2026-09-15)를 받아 337개 API 전체에서 `선물|옵션|파생|futures|KOSPI200|코스피200|FUT|OPT`를 검색했다. 이 커밋은 `docs/design/DESIGN.md` 부록 A가 기준으로 삼은 커밋과 같다.

#### D3-3. 일일정산·추가증거금·반대매매 [확인: 한국투자증권 「장내파생상품 거래설명서」 개정 2026-09-01, 심사필 제2026-0206]

#### D3-4. 모의거래에 넣을 최소 규칙 (제안)

1. 상품은 **미니 코스피200 선물 근월물 1개**만 연다. 1계약 크기가 작아 가상 자금 규모와 맞는다.
2. 증거금은 상품별 위탁률·유지율을 **날짜가 있는 설정 표**로 둔다(시행일·출처 열 포함, 월 1회 수동 갱신). 산식은 명목금액 × 율로 단순화하고, 화면에 "실제 거래소 산식과 다름"을 표시한다.
3. 주문 때 위탁증거금보다 주문가능금액이 적으면 거절한다. 주문가능금액 = 예탁 현금 + 미실현 손익 − 필요 위탁증거금.
4. **일일정산**은 정규장 종료(15:45) 뒤 1회 돌린다. 정산가격은 그날 정규장 마지막 체결가로 근사하고, 실제 정산가격을 받으면 그 값으로 바꾼다. 당일차금·갱신차금을 현금에 더하거나 뺀다.
5. **마진콜**: 정산 뒤 예탁 평가액이 유지증거금보다 작으면 `MARGIN_CALL` 상태로 둔다. 새 진입은 막고 청산만 허용한다. 다음 거래일 12:00까지 위탁 수준을 회복하지 못하면 엔진이 **12:00 시세로 전량 반대매매**한다(가상 계좌에는 입금이 없으므로 회복 수단은 청산뿐이다).
6. **만기**: 최종거래일 15:20 이후 남은 포지션은 최종결제가격으로 현금결제한다. 최종결제가격은 [확인 필요]이며, 확인 전에는 기초지수 종가로 가정하고 화면에 표시한다. 자동 롤오버는 하지 않는다.
7. 야간장은 처음에는 열지 않는다(정규장만).

### D5. 우리 구조에 붙인다면 (설계 수준)

#### D5-1. 원칙
- **현물 모의 계좌와 완전히 분리한다.** 회계 단위가 다르다. 현물은 매수 금액을 전부 지급하지만 선물은 증거금만 묶고 매일 정산한다. 섞으면 랭킹·자산 그래프·리스크 한도가 모두 틀어진다. `PaperAccount`와 별개로 팀원별 `FuturesAccount`를 두고 시작 예탁금도 따로 둔다. 랭킹도 따로 낸다.
- **안전 규칙은 그대로 둔다.** 선물 시세 클라이언트에는 조회 TR(현재가·호가·일봉·실시간 체결)만 넣는다. KIS 예제의 `order`, `order_rvsecncl`, `inquire_balance`, `inquire_deposit`, `inquire_psbl_order` 등 주문·계좌 계열은 옮기지 않는다. 코드 검색 금지어에 KIS 주문 경로(`/trading/order` 류, TR ID)를 추가한다.
- 브로커 추상화 규칙(`data/broker.make_client`, 내부 형식은 토스 형식)과 충돌하지 않도록 파생 시세는 **별도 클라이언트**(`data/futures_kis.py` 가칭)로 만든다. 변환은 그 파일 안에서만 한다. 엔진은 표준 라이브러리만 쓴다.
- KIS 키는 새 비밀 정보이므로 `.env`에만 두고 `.env.example`, `deploy/.env.docker.example`, CI 설정을 함께 고친다. Redis 키는 `paper:fut:*`로 둔다.

#### D5-3. 회계
- 예탁 평가액 = 현금 + 미정산 평가손익(직전 정산가격 대비).
- 주문가능금액 = 예탁 평가액 − 필요 위탁증거금 합계.
- 필요 증거금 = Σ |순수량| × 정산(또는 현재)가격 × 승수 × 율.
- 정산 때 손익을 현금으로 옮기고 포지션 기준가를 정산가격으로 갱신한다. 실현 손익과 정산 차금은 따로 보여 준다(교육 포인트).
- 수수료율은 설정값으로 둔다(실제 증권사 수수료 [확인 필요]). 파생상품 양도소득세는 표시만 하고 계산하지 않는다 [확인 필요].

#### D5-4. 리스크 엔진 확장 (`judge/risk.py` 옆에 선물 전용 함수, 결정론)
- **레버리지 한도**: 명목금액 합계 / 예탁 평가액 ≤ `max_leverage`. 교육용 기본값은 보수적으로 1~2배이고 값은 팀이 정한다.
- **건당 위험**: |진입가 − 손절가| × 승수 × 계약수 + 비용 ≤ 예탁 평가액 × `risk_per_trade`. 계약수는 이 식의 내림값이며 0이면 거절한다. 손절은 필수이고 숏은 손절가가 진입가보다 위여야 한다.
- 최소 손익비(기존 2.0)는 코드에만 둔다. AI 프롬프트에 노출하지 않는다는 규칙을 그대로 지킨다.
- 위탁증거금이 주문가능금액보다 크면 거절한다. 일일 손실 한도, 일일 매매 횟수, 계약당 최대 계약수도 둔다.
- 거절 조건: 만기 N거래일 이내 신규 진입(예: 2일), 가격제한 도달 상태, `MARGIN_CALL` 상태의 신규 진입, 야간장 시간.

#### D5-5. 체결 규칙 (모의 체결기 확장)
- 가격은 호가단위로 맞춘다. 시장가는 현재가에서 **불리한 방향으로 1틱 미끄러짐**을 준다. 지정가는 체결가가 지정가를 지나야 체결하고, 부분 체결은 없다.
- 거래시간은 08:45~15:45(최종일 15:20)이고 시가 단일가(08:30~08:45)는 열지 않는다. 장 밖 주문은 거절한다(현물처럼 다음 정규장 예약은 하지 않는다. 예약 체결 시 갭 손실이 레버리지로 커지기 때문이다).
- 손절·목표 감시는 기존 `sync`처럼 연속 확인 횟수를 쓴다. 숏은 방향을 뒤집는다.
- 반대매매·만기 결제는 엔진이 `requested_by="system"`으로 기록한다.

#### D5-6. 만기·롤오버
- 최종거래일 D-3부터 경고하고, D-N부터 신규 진입을 막는다. 15:20에 미청산분을 최종결제한다.
- 자동 롤오버는 하지 않는다. "근월 청산 + 차월 진입" **롤오버 제안**은 AI나 규칙이 만들 수 있지만, 실행은 사용자 확인 뒤 리스크 엔진을 다시 통과해야 한다.

#### D5-7. 장애 복구
- 일일정산은 (계좌, 계약, 거래일) 유일 키로 **멱등**하게 만든다. 엔진이 재시작하면 정산되지 않은 지난 거래일을 순서대로 정산한다.
- 정산가격이 없으면(시세 장애) 계좌를 `SETTLEMENT_PENDING`으로 두고 신규 진입을 막는다. 일봉 TR이나 KRX 일별 데이터로 보충한 뒤 정산한다.
- 마진콜 반대매매 시각에 시세가 없으면 다음으로 받은 시세로 미룬다. 미룬 사실을 기록·알림하고, 가격을 임의로 만들지 않는다.
- 기존 `OrderLock`과 같은 계좌 단위 잠금으로 체결·정산·반대매매가 겹치지 않게 한다.

#### D5-8. "AI는 제안만" 적용
- AI는 방향(롱/숏), 진입·손절·목표 **가격**, 근거만 낸다. 계약수·레버리지·증거금·체결 여부는 5-4·5-5의 코드가 정한다.
- AI는 마진콜 처리, 반대매매, 롤오버 실행을 하지 못한다. 숏 제안에는 "하락에 거는 거래이고 손실이 커질 수 있음"을 코드가 붙이는 고정 문구로 표시한다.
- 초보 대상 새 컨셉(`docs/plans/컨셉변경계획.md`)과 충돌할 수 있다. 선물 화면은 기본으로 숨기고 "고급·학습" 메뉴에서만 연다.

  - KIS 예제 저장소에는 주문 코드가 함께 있다. 복사하다 주문 코드가 섞여 들어오지 않게 리뷰와 금지어 검사를 해야 한다.
