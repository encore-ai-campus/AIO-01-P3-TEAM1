# 모매매 AI 리포트 워크플로우 설계서 ①

## 목적과 사용자 시나리오

대표 사용자 ‘민지’는 주식 리포트의 용어가 어렵지만, 실제 돈을 넣기 전에 종목을 살펴보고 정한 가격으로 사고파는 과정을 연습하고 싶다. 모매매는 종목별 자료를 나눠 조사하고, 근거를 바탕으로 리포트를 작성·검토한다. AI는 의견을 제시할 뿐, 주문 수량·한도·모의 체결은 규칙 코드가 판단한다.

- **정상:** 종목 신청 → 시세·재무·뉴스 조사 → 초안 작성 → 검토 통과 → 리포트 완성 → 사용자가 확인한 뒤 모의투자 계획 선택
- **재작성:** 검토 AI가 근거가 약한 부분을 발견 → 작성 AI에 수정 지시 → 다시 검토. 정해진 횟수 안에 통과하지 못하면 실패
- **실패:** 필수 조사 결과가 없거나 검토를 통과하지 못하면 뒤 작업을 건너뛰고 이유를 기록·안내

| 사용자 단계 | 뒤에서 일하는 구성 | 문제가 생겼을 때 보이는 것 |
|---|---|---|
| ① 만들기 | Orchestrator → 시세·재무·뉴스 Worker 병렬 실행 → Join Guard → 작성 Worker | 진행 상태 또는 필수 자료를 모으지 못한 이유 |
| ② 검토 | 검토 Worker의 PASS·RETRY·FAIL 판단 → 필요 시 재작성 → 조건에 따라 리스크 점검 | 재작성 진행, 검토 실패 또는 위험 경고 |
| ③ 실행 | 리스크 엔진 → 모의 체결기 → 알림. AI가 주문을 내지 않음 | 실행 불가·미체결·체결·청산 상태 |
| 공통 | YAML 실행 계획과 공유 State·Trace | 현재 단계와 순서가 있는 진행 기록 |

## 역할과 실행 순서

```text
리포트 신청
  → Runner가 대기 작업 한 건 선택
  → 시세·재무·뉴스 조사 병렬 실행
  → Join Guard가 필수 결과 확인
  → 리포트 초안 작성
  → 검토
      ├─ PASS  → 필요 시 리스크 점검 → 완료
      ├─ RETRY → 초안 재작성 → 재검토(최대 2회)
      └─ FAIL  → 실패 종료
```

`registry.py`는 YAML에 적힌 Worker, 실행 단계, 의존 관계, 필수·선택 구분과 Handoff 경로를 검증한다. Orchestrator는 그 계획에 따라 Worker를 실행한다. 조사 단계는 병렬이고, 작성과 검토는 순차 실행이다.

| Worker | 맡은 일과 입력 자료 | 출력 계약 | 주 모델 |
|---|---|---|---|
| `market_agent` | 장마감 가격·완성 일봉으로 시세, 추세, 지표 정리 | `MarketResult` | `gemini-3.8-flash` |
| `fundamental_agent` | OpenDART 재무·최근 공시 정리. 자료가 없으면 없는 이유를 표시 | `FundamentalResult` | `gemini-3.8-flash` |
| `news_agent` | 최근 뉴스 제목·증권사 헤드라인으로 시장 분위기 정리. 선택 Worker | `NewsResult` | `gemini-3.8-flash` |
| `report_agent` | 성공한 조사 결과를 모아 리포트 초안 작성 | `ReportDraft` | `gpt-5.6-luna` |
| `review_agent` | 초안의 주장과 쉬운 요약이 조사 근거에 맞는지 검토 | `ReviewResult` | `claude-opus-5-5` |
| `risk_agent` | 요청받았을 때 투자 유의 지정과 위험 신호를 점검해 경고 작성 | `RiskResult` | `deepseek-v4.1-flash` |

조사 Worker는 자기 분야의 근거만 정리하고 매수·매도 의견을 내지 않는다. 작성 Worker가 초안을 만들고, 검토 Worker는 초안을 직접 수정하지 않고 통과 여부와 수정 지시를 낸다. 리스크 Worker는 본문을 고치지 않고 경고를 더한다. 이 구분으로 역할의 중복을 줄인다.

## 공유 State, Join과 부분 실패

Worker는 리포트의 DB 상태를 직접 바꾸지 않는다. Orchestrator가 Worker 결과를 출력 계약으로 다시 확인한 뒤 `state.py`를 통해 결과·오류·진행 사건·비용을 저장한다. Trace에는 사건의 순서를 남겨 신청부터 종료까지의 흐름을 확인할 수 있다.

Join Guard는 다음 단계에 필요한 앞 단계 결과가 있는지 확인한다. 종목 리포트에서는 **시세와 재무가 필수, 뉴스는 선택**이다. 따라서 뉴스 결과가 없어도 필수 결과가 있으면 작성 단계로 진행할 수 있다. 필수 결과가 없거나 계약에 맞지 않으면 뒤 Worker를 건너뛰고 실패로 종료한다. 작성 Worker에는 성공한 조사 결과를, 검토 Worker에는 최신 초안과 조사 결과를 전달한다.

검토가 `RETRY`를 내면 수정 지시와 재작성 사건을 기록하고 작성 Worker를 다시 실행한다. 현재 종목 리포트 계획의 재작성 한도는 **2회**다. `PASS`면 마지막 초안을 사용하고, `FAIL`이나 한도 초과면 완성된 리포트로 표시하지 않는다. Worker 실행 비용은 리포트의 비용 합계와 종료 기록에 남긴다.

## Handoff와 입력 Guard

검토 결과가 리스크 점검을 요청하면 Orchestrator는 `review_agent → risk_agent` 경로가 계획에 있는지, 전달 횟수의 한도를 넘지 않았는지, 요청자 정보가 일치하는지, 전달 데이터에 비밀 값 형태가 없는지 확인한다. 허용된 경우에만 앞선 결과의 참조와 점검 제약을 리스크 Worker에 넘긴다. 거절하면 `handoff_blocked`를 기록하고, 이미 검토를 통과한 초안은 유지한다.

뉴스·공시처럼 외부에서 받은 글은 입력 Guard가 지시문·비밀 값 형태를 제거하고 길이를 제한한다. 무엇을 제거했는지는 진행 기록에 남긴다.

## 실패와 종료

실패할 때는 `join_blocked`, `review_failed`, `timeout`, `agent_failed`, `no_llm`, `engine_restarted`, `expired`, `exception`처럼 정해진 사유 코드를 기록한다. 화면과 알림은 그 코드로 사용자에게 이유를 설명한다.

`run_engine`은 반복해서 Runner를 호출한다. Runner는 대기 신청을 오래된 순서로 **한 건씩** 실행한다. 신청 후 24시간이 지난 대기 리포트는 AI를 실행하지 않고 `expired` 사유로 실패 처리하며 DB 기록은 남긴다. 엔진 재시작 때 이전의 실행 중 상태가 남아 있으면 실패로 정리한다.

## 협업 구조와 선정 이유

Worker와 Orchestrator는 엔진 프로세스 안에서 공통 입력·출력 계약으로 연결한다. Agent마다 별도 컨테이너를 두는 대신 웹·엔진·DB 등 서비스 역할별로 나눈다. 작은 팀에서 배포와 통신의 복잡도를 줄이면서도, YAML 계획·출력 계약·공유 State를 통해 각 Agent의 책임과 결과를 구분하기 위한 구조다.

이 설계서는 **현재 병합된 코드에서 확인되는 역할과 실행 흐름**을 설명한다. 담당 4의 복구 상세·복구 지표·장애 시험 결과와 AWS 실측 결과는 포함하지 않았다.
